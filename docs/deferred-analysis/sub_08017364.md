EEPROM save-restore routine, `[0x08017364, 0x0801756c)` = 520 bytes, called
once from Init1 (`sub_08000430`). Decompiled to **structurally byte-exact** C
(`src/engine/sub_08017364.c`, behind `#ifdef NON_MATCHING`); the asm slice
provides the matching bytes. The residual is a proven agbcc compiler-cut
difference, not a source-shape issue — see "The verdict" below.

This file supersedes the earlier analysis, which was wrong on two counts: the
`399/159` figure was stale, and its claim that `register u8 ok asm("r7")`
reproduces `cmp r7,#0` is false (on the current toolchain it emits garbage
testing `sp`). The save-system struct model (`include/save.h`) was the real
unlock.

## What it does

Seeds `gSaveData` (0x03003500) with defaults, masks the serial IRQ in REG_IE,
probes the EEPROM + validates the 8-byte save header (`sub_080172F4` /
`sub_080177A0`), rebuilds the header from current game state on a failed field
check, loads each populated slot (empty slot = initials "AAA"), then restores
`gIwram_34B0` (level) from `SaveHeader.level` and re-seeds `gIwram_34B4` to
`{1,1,5,5}`. Full subsystem map in `docs/subsystems.md` "EEPROM save system".

## Progress: 399 → 169 byte_diff, structurally exact

`compile_and_view_assembly.py sub_08017364` → byte_diff 169 / 74 insns, **size
520 (== target)**, i.e. the same instruction stream with only register
substitutions. Matched outright: prologue (3 high-reg save), the entire IWRAM
init block, the copy loop (`ldmia/stmia {r4,r6,r7}`, index in r5), the header
copy, and both `cmp r7,#0` ok-checks. The wins that got us there:

- **Struct model** (`save.h`) dissolved the address-CSE that made every field
  read `mov r0,r8; adds r0,#N; ldrb` — now it folds to `ldrb [rN,#N]`.
- **Loop restructure** — inlining `scratch[i]` so it doesn't live across the
  `sub_08017814` call freed r5 for the index and fixed the `ldmia` reg set
  (156 → 99). The old `src` local forced a callee-saved reg, displacing `i`.
- **`int ok`** (not `u8`) → clean `cmp r7,#0` (no u8 zero-extend garbage).
- **union `SaveHeader.tail`** → the header rebuild word store folds `str [r,#4]`.

## The verdict: local-alloc r0-funnel (compiler-cut), proven by instrumentation

The remaining diff is the validation field reads. Target spreads the high-reg
base copies across r3/r4/r1/r2; ours funnels them all to r0:

```
target:  mov r3,r8; ldrb r0,[r3,#3]   ours:  mov r0,r8; ldrb r0,[r0,#3]
         mov r4,r8; ldrb r0,[r4,#1]          mov r0,r8; ldrb r0,[r0,#1]   ...
```

Instrumented agbcc (private build, `fprintf` in `gcc/reload1.c`
allocate_reload_reg, removed after) proves this is **not reload**: only 6
reloads fire and their round-robin spreads correctly (start_lsr -1→0→1→2→3→4,
regs r0,r1,r4,r6,r7,r4). The funnel is the **main allocator**:

- `header` lives in r8 (high reg, forced by pressure). Thumb can't use a high
  reg as a memory base — `REGNO_OK_FOR_BASE_P` (thumb.h:493) rejects r≥8 — so
  each `header->field` copies r8 into a low-reg pseudo.
- `local-alloc.c` `find_free_reg` (line 1947) tries hard regs **r0-first** and
  returns the first not live across the pseudo's range. Each copy dies exactly
  where the `ldrb` result (r0) is born, so r0 is free → every copy takes r0.
- The baserom's agbcc cut allocated these to r3/r4/r1/r2. `find_free_reg`'s
  r0-first is deterministic; no source shape steers it (tried: `register`
  pins — grow size; `-fno-strength-reduce`/`-fno-cse-follow-jumps` — no-ops;
  old vs new agbcc — old marginally better; long-live-range `sav`; statement
  reordering — ≤7 bytes each, never the rotation; `agbcc_arm` — emits ARM, the
  function is Thumb). decomp-permuter base 5475, no convergence.

**Settled by a patch experiment (don't re-run):** patching `find_free_reg`'s
ascending scan to a reload-style round-robin in a private agbcc and recompiling
made it *worse* — size 540 (was 520), byte_diff 481 (was ~169 / 224 raw), and
it scrambled `header` out of r8. A *global* spread breaks the prologue/init/copy
loop that currently match, which proves the baserom allocates **r0-first like
ours for the bulk** of the function. So the field-read spread is NOT a
`find_free_reg` scan-order policy — it's localized to the high-reg base copies,
most likely the baserom's local-alloc assigning the `ldrb` *result* (r0) before
the base copy (so the copy can't reuse r0). That is a finer allocator-cut
difference no single knob reproduces.

**Local-minimum check (toy experiments, stock agbcc).** Decompilation isn't 1:1,
so a *different* structurally-exact form could in principle spread. Tested with
minimal toys (`register u8 *p asm("r8")`, validate four fields):
- Interleaved read-and-compare (the baserom's shape) → **funnels** the base
  copies to r0. Pinning `ok` to r0 just moves the funnel to r1 — occupying a
  register shifts, it doesn't spread.
- Reading all fields into locals *first* (simultaneously live) → agbcc **does
  spread** (r2/r3/r4/r0). So our agbcc *can* spread — but only in this
  read-all-first order, which is a *different instruction stream* than the
  baserom's interleaved read/compare.

**Corpus cross-check (strongest evidence).** `tools/agent/corpus_asm_search.py`
mines other agbcc decomps' git histories for this idiom (asm removed + C added
in the same match commit). Metroid Fusion's `ContinualXSpawnerIdle` is our
*exact* shape — one struct read field-by-field in **plain C, no pins** — and
agbcc parks the base in r8 and **funnels every copy to r0, matching its baserom
byte-for-byte**. The spreads in the corpus (e.g. `SaXCloseUpInit`) come from a
structurally different pattern: 20+ distinct global/MMIO addresses live at
once, forcing the spread. So the funnel is the *standard* agbcc output
for our shape, and Frogger's baserom spreading on a single-struct validation is
unusual — but NOT a different compiler (see below).

**Fork investigation (ruled out the compiler-cut theory — verified by building
the real compiler).** cvaos (Castlevania: Aria of Sorrow — Konami, like Frogger)
*does* spread our idiom and matched it. It uses `jiangzhengwenjz/agbcc` with
`-f2003-patch`, where we use `pret/agbcc`. So the natural hypothesis: we have the
wrong compiler. Tested properly — cloned and built the real `jiangzhengwenjz/agbcc`
from scratch and compiled our function with it:
- jzw/agbcc and pret/agbcc produce **byte-identical** `.o` and `.s` for
  sub_08017364 (verified with `cmp`). The forks differ only in flag-gated
  patches (`-f2003-patch`, `-fprologue-bugfix`, default off) and cosmetic
  hex-asm (`#0x18` vs `#24`, same bytes).
- `-f2003-patch` (cvaos's flag) has **zero effect** on our function — the `.o`
  is identical with and without it (the compare-with-shift patch doesn't trigger
  on our specific checks).

So the compiler/fork/flag is **definitively not** the difference: cvaos spread
this idiom with the *same compiler we have*, purely via **source structure**.
That confirms a local minimum — the spread is reachable with our exact agbcc from
a C shape we haven't found — and conclusively kills the compiler-cut theory.
(An earlier revision of this doc claimed `-f2003-patch` made our function worse
at byte_diff 318; that came from an unfaithful patched-combine.c build, not the
real jzw compiler, and was wrong.)

The baserom combines interleaved reads (result reused in r0) **with** spread
base copies — which needs the allocator to reserve r0 for the result *before*
allocating the base copy. Our agbcc allocates the copy first (it takes r0, the
result reuses it); the baserom allocates the result first. That qty-ordering is
not reachable from any source shape tried. So a matching form likely requires a
different agbcc cut — strong (experiment-backed, not proven-exhaustive)
evidence, not a single `find_free_reg` change.

## Session update — oracle-verified scoreboard, the spread IS reachable, and the ok-pin fold

Re-ran every hypothesis through the **real** oracle (in-tree build +
`compile_and_view_assembly.py`, not a hand-disassembled standalone `.o`).
Ground truth, all measured the same way:

| Variant | byte_diff | size | what it proves |
|---|---|---|---|
| **v8 (committed, pins: header r8, ok r7, savedIe r9, zero r2, fullByte r0)** | **169** | 520 | funnels (header pin) + folds `&headerBuf` (ok pin); still the LOW |
| unpin header only | 173 | 520 | **validation SPREADS** (corpus finding confirmed) but to wrong regs (r6/r7 vs target r3/r4) and the fold persists, so net +4 |
| unpin header + final-copy via `header` | 173 | 520 | the 3× `&headerBuf` CSE wasn't the fold trigger |
| + `-fno-rerun-cse-after-loop` | 467 | 500 | flag KILLS the fold (`add sp,#52`) but overshoots: header stays low, no r8 promotion, −20 bytes |
| all pins stripped (natural) | 428 | 496 | no fold, but prologue (3 high-reg save) + init + `ok`-in-r7 all collapse |
| v8 + pin `sav` r6 | 359 | 524 | pinning sav to the baserom's own reg ADDS an insn, shifts every branch |
| v8 + `savedIe = iePtr` after the probe call | 191 | 520 | structural reorder to match `mov r9,r5` timing — worse |
| pin all-but-{ok,header} (pressure) | 515 | 672 | over-pinning `i`/`saveBase` explodes the frame |

**The spread is reachable** — unpinning `header` reproduces the baserom's
`mov rLOW, r8; ldrb` spread structure (confirms the four corpus agents'
finding). It just doesn't *win* on its own because (a) the spread lands in
r6/r7 not the target's r3/r4, and (b) the `&headerBuf` const-fold survives.

**The fold is caused by the `ok asm("r7")` pin**, isolated by bisecting the
five pins (compile, grep `movs rN,#52` vs `add rN,sp,#52`): only `ok r7` flips
it. A callee-saved low-reg pin is sticky for the whole function, so the slot
loop can't recycle r7 the way the baserom does (`ok` is dead by the loop →
baserom reuses its r7 as `mov r7, sl` scratch). Under that pressure agbcc
rematerialises `&headerBuf` as the absolute constant `movs #52` — a real
miscompile (`header->slotMask` becomes `movs #53; ldrb [r0,#0]`, reading
address 0x35). Full write-up in `docs/codegen-notes.md` "Pinning a
callee-saved low reg can rematerialise a stack address as `movs #const`".

**It is a sharp register-coloring local minimum, independently confirmed by
permuter.** Every manual change above (pin or structural) *raises* byte_diff;
v8's 169 is the floor reachable by pins. A fresh decomp-permuter run from the
v8 base (permuter base score 5000; the recorded earlier failure was on a
5475-score base, i.e. far worse) escaped the minimum only marginally — best
4805 after ~3.4k iterations, and the winning mutations were cosmetic (brace
insertion, one `zero = ok` temp). No path to 0 emerged. Scaffold left in
`nonmatchings/sub_08017364/` for a future longer run.

The true match needs the baserom's **holistic natural coloring** —
sav→r6, i→r5, ok→r7 (range ends before the loop so r7 recycles), header→r8
(natural, not pinned, hence spread), savedIe→r9, saveBase→sl — none of which
is individually pin-forceable without disturbing the rest. That C source
shape has not been found; the asm slice continues to provide the bytes.

  r9 / saveBase sl must all be genuinely used). Every attempt so far either
  re-introduced the fold (ok pinned) or lost the high-reg promotion (ok free).
- A longer permuter run (it IS finding sub-5000 variants) with
