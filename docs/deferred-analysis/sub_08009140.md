## Function semantics

Checks `gIwram_3720._field_1A` against 0x23. If it matches, reads the
flags halfword `gIwram_3720._field_34` and adjusts bits:
- If bit 2 is set: clear bit 15 (f &= 0x7fff)
- Elif bit 15 (0x8000) is set: clear bit 15 and set bit 2 (f = (f & 0x7fff) | 2)
- Otherwise: no store
Then unconditionally calls `sub_080059C4(&gIwram_3720)`.

Root cause: agbcc local-alloc assigns r2 to `base` (pool load), r3 to `new_var`
(copy). Target uses r0 for `base` (pool load) and r2 for the copy. The `ands`
result register follows from which variable holds the AND accumulator: target
keeps mask (0x7fff) in r0 as accumulator (`ands r0, r1` = r0 &= r1), built
keeps flags (f) in r1 as accumulator (`ands r1, r0` = r1 &= r0).

## Next approach to try

The `ldr r0; adds r2, r0, #0` pattern occurs in other functions when a pool
literal is loaded via r0 (as a free scratch) and then the compiler needs to
preserve it in a callee-saved/callee-used register. A clue from sub_08008d14:
a pool load into r0 (with `adds r2, r0, #0` following) occurs when the
preceding instructions left r0 as the "most recently freed" register and
agbcc chose to use it as the pool load target.

This suggests the function might need some intermediate computation that USES
r0 before base is materialized, making r0 "the next free register" when the
pool load happens. Alternatively, maybe the `state` intermediate plays this
role with a different declaration form — `base` could be declared inside the
conditional check body rather than at the top.

Also worth trying: what if `sub_080059C4` is typed to return `struct IwramAt3720 *`
(even though it doesn't)? This could change how agbcc plans the call register.
