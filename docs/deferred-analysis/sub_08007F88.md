- Else: if tileClass in {7,8,11} -> return 1; otherwise
  `sub_0800803C(gIwram_3720._field_2, gIwram_3720._field_4,
                _field_8*24+11, _field_A*24+11)` (`n*24+11 = (n*3)<<19 +

## STATE OF THE ART — byte_diff 66 (Opus round; prior Sonnet plateau was 84)

The prior plateau (84) was caused by the **entry pointer being computed BEFORE
col/row**. The fix found this round: **do NOT make `entry` a local** (any
`struct ActorRecord *entry = ...` local is emitted at block entry and computed
first). Instead:
1. Cache ONLY `_field_D` in a local (`u8 d`) so CSE can merge the 5 entry-field
   reads (without it, an inlined `p35E0->_field_D*56` macro re-reads the field
   5x -> size explodes to 236; CSE will NOT merge a memory load off p35E0).
2. Inline the entry pointer as a MACRO `((struct ActorRecord*)((u8*)&gIwram_3720
   + d*56))` referenced in each field access. agbcc then evaluates col/row
   (cheap loads off the CSE'd `&gIwram_3720` base) FIRST and computes the entry
   offset lazily during arg2/arg3 — matching baserom's col/row-first order.
   84 -> 79.
3. col/row as `s16` locals read first -> 77.
4. A tightly-scoped `register u16 flags asm("r6")` read of `_field_10` inside a
   `goto`-based short-circuit of the `||` -> forces the 3-reg prologue
   `push {r4,r5,r6,lr}`, tileClass into r1 (`lsrs r1`), `_field_10` into r6.
   -> 72.
5. Swap the `+` operand order to `entry->_h24 + entry->_h2` (and `_h26 + _h4`):
   agbcc evaluates the `+` RIGHT operand first, so writing the higher-offset
   field on the LEFT makes the lower-offset (`_h2`/`_h4`) load emit first,
   matching baserom. -> 66.

ROOT CAUSE of the ordering (traced in `tools/agbcc-src/gcc_arm/calls.c`):
`precompute_register_parameters` (line 594) iterates args forward (i=0..3) and
for each arg with `rtx_cost(value,SET) > 2 && SMALL_REGISTER_CLASSES &&
reg_parm_seen` copies its COMPUTATION into a pseudo AT THAT POINT. args 2,3
(the `a+b` sums) are expensive -> their computation (incl. the entry pointer)
is emitted during precompute, BEFORE the cheap col/row args are loaded in the
final forward load loop (line 2026; `LOAD_ARGS_REVERSED` is NOT defined for
ARM, `PUSH_ARGS_REVERSED` IS). agbcc 2.9 has NO instruction scheduler
(`-fschedule-insns` is REJECTED), so the only way to get col/row first is to
make the entry pointer a CSE'd common subexpression that materialises lazily —
hence the inline-macro + cached-`d` trick. A separate `entry` local defeats it.

## Residual drift at 66 (diff_count 33) — pure local-register-allocation

Structure, logic, size (184), col/row-first order, 3-reg prologue, tileClass in
r1, h-field load order: ALL correct. Residual = ONE coherent allocator
preference: baserom keeps **r6 as a persistent callee-saved scratch** reused at
THREE disjoint sites; agbcc-mine uses caller-saved r3/r4 at two of them:

1. `_field_D` read into **r6 AFTER col/row** in baserom (`ldrb r6,[r5,#13]` at
   0x7fba); mine reads into **r3 BEFORE col/row**. Cascades the col/row index
   constants to r5/r4 (mine) vs r1/r3 (baserom) and the multiply source reg.
2. Else branch: baserom holds the `0xb0000` constant in **r6 ONCE** and reuses
   it for both arg2 and arg3; mine recomputes it (`movs r3,#176...` then
   `movs r4,#176...`) and uses r2 not r6 for the `#2` index.
3. Minor: the `_field_10 & 2` test emits `ldrh r6,[r5,#16]` one slot before the
   `movs r0,#2` const (eager `flags` read) — baserom emits `movs r0,#2` first.

All three share one root: baserom reserves r1=tileClass (live across both
branches) and r5=35E0 base, leaving r6 as THE 4th scratch everywhere a 4th reg
is needed. agbcc-mine prefers a free caller-saved reg at each site instead.
