## What it does (confidently decoded)

Collision/footprint probe for the active actor (`gIwram_35E0`). Calls
`sub_0800CD88(field_18, field_19, field_8, field_A)` -> tile-class byte
`tileClass`. Then:

- If `gIwram_35E0._field_1A != 0` OR `(gIwram_35E0._field_10 & 2) != 0`:
  read a 56-byte per-actor record `entry = &gIwram_3720 + _field_D*56`, and call
  `sub_0800803C(gIwram_3720._field_2, gIwram_3720._field_4,
                (s16)(entry[+2] + entry[+0x24]),
                (s16)(entry[+4] + entry[+0x26] - (entry[+0x29] >> 1)))`.
- Else: if `tileClass` is 7, 8, or 11 -> return 1 (blocked). Otherwise call
  `sub_0800803C(gIwram_3720._field_2, gIwram_3720._field_4,
                field_8*24+11, field_A*24+11)`. The `n*24+11` is agbcc's
  `((n*3)<<19 + 0xb0000) >> 16` (same idiom as `sub_08007874.c` line 29).
- Tail (both): `return sub_0800803C(...) != 0 ? 1 : 0`.

Struct add needed: `gIwram_35E0._field_1A` (u8 at offset 0x1A) — was added in the
attempt; offset confirmed by the `ldrb [r5,#26]` at 0x7fa0 and the xref reader at
`sub_080087B4`.

The two `sub_0800803C` call sites are byte-identical tails; baserom tail-merges
them into the join at 0x801e (`asrs r3,r3,#16; bl sub_0800803C; ...`). Writing
the call DUPLICATED in each branch (not one shared tail call) is REQUIRED — it
lets agbcc's cross-jump produce the `b 0x801e` join AND compute each branch's
`gIwram_3720._field_2/_field_4` args inline (baserom uses two separate pool
entries for `&gIwram_3720`, at 0x7fe4 and 0x8030 — i.e. NOT CSE'd across the
branches). With a single shared tail call, agbcc loads `_field_2/_field_4` once
AFTER the join (byte_diff ~144). Duplicating dropped it to ~85.

## Drift (best reached: byte_diff 84, diff_count 44–47)

Structure, logic, sizes (184 bytes) all correct. Residual is pure register
allocation in the `_field_1A`/`&2` entry branch:

1. **2-reg vs 3-reg prologue.** Baserom `push {r4,r5,r6,lr}`; my build
   `push {r4,r5,lr}`. Baserom uses **r6** (callee-saved) for the `&2` test
   field load, `_field_D`, and the entry `+4` (h4) read. agbcc colours those
   to r1 (caller-saved) and never needs r6, so it pushes one fewer register.
2. **col/row evaluated LAST, not FIRST.** Baserom's entry branch loads
   `&gIwram_3720`->r2, then reads `_field_2`->r0 and `_field_4`->r1 FIRST
   (args 0,1), THEN computes `_field_D`->r6 / entry->r4 / x->r2 / y->r3, keeping
   col/row live in r0/r1 across the whole entry math. My agbcc hoists the CSE'd
   `entry` pointer to the top and reads col/row at the END (right before the
   call). Root cause traced in `tools/agbcc-src/gcc_arm/calls.c`:
   `precompute_register_parameters` evaluates args forward (i=0..n) ONLY for
   `rtx_cost>2 && SMALL_REGISTER_CLASSES && reg_parm_seen`. The CSE-hoisted
   `entry` makes arg2(x) cheap at the call point so col/row's relative order
   flips. This is the dominant ~8-instruction block.
3. **tileClass in r2 (baserom r1).** Cascades from (1)/(2): `lsrs r1,r0,#24`
   (baserom) vs `lsrs r2` (mine); `subs r0,r1,#7` / `cmp r1,#11` likewise.
4. **`&2` test operand order.** Baserom `movs r0,#2; ldrh r6,[r5,#16]; ands r0,r6`
   (const first, field into r6). Mine `ldrh r1,[r5,#16]; movs r0,#2; ands r0,r1`.
5. **h2/h24 operand order.** Baserom reads `entry[+2]` before `entry[+0x24]`;
   mine reverses (agbcc evaluates the `+` right operand first). 1 instruction.
