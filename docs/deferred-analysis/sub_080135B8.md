# sub_080135B8 — deferred analysis

220-byte leaf function (no callees), `asm/disasm_0x080135b8.s` →
`src/engine/sub_080135b8.c` at 0x080135B8.

## What it does (fully understood)

Per-axis auto-scroll/pan tick. Two independent scroll controllers live in
IWRAM, same struct type (`struct ScrollAxis` below):

- block A = gIwram_6540 (horizontal axis: kinds 4/3, fields posX@0x34 / deltaX@0x2c)
- block B = gIwram_6480 (vertical axis:   kinds 1/2, fields posY@0x36 / deltaY@0x2e)

Struct offsets (cross-checked against the project's own `struct IwramAt6480`
in src/engine/sub_08013694.c, which names +0x04 field_4 / +0x0b field_b):
- +0x04 u32 lastTick   — snapshot of gGameStuff._unk00 at last step
- +0x09 u8  kind       — direction/mode (A: 3 or 4; B: 1 or 2; 0 = idle)
- +0x0b u8  interval   — minimum gGameStuff._unk00 delta between steps
- +0x2c s16 deltaX / +0x2e s16 deltaY — per-step velocity reported each frame
- +0x34 s16 posX / +0x36 s16 posY     — accumulated position

Each frame the reported delta is cleared (unconditionally, at the top); a
block only steps once `gGameStuff._unk00 - lastTick >= interval`. kind 4 grows
posX toward maxX (arg0) by stepX (arg1) when posX <= maxX; kind 3 unwinds it
when posX >= maxX; kind 1/2 do the same on posY with maxY(arg2)/stepY(arg3).
Signature: `void sub_080135B8(u16 maxX, u8 stepX, u16 maxY, u8 stepY)`,
confirmed by the only caller sub_08013694 which calls `sub_080135B8(0,0,0xa0,1)`.
The signed clamp compiles via `lsl #16` on BOTH operands (compare
`(s32)(s16)posX` vs `(s32)(s16)maxX`). The `(s32)(s16)maxX` MUST stay inline at
each compare (re-`lsls` per compare); hoisting/caching the shift WORSENS.
gGameStuff._unk00 is re-read for the final lastTick store (NOT cached in a local
`now`; caching it jumps the diff to 116). The `gs = &gGameStuff` base pointer IS
a required local (without it agbcc reloads the pool at block end → 198).

## Round 3 (Opus, this run) — STRUCTURAL ADVANCE: base improved 59 → 43

Two source-shape changes lowered the clean (NO-PIN) base from the Round-2
plateau (byte_diff 180, diff_count 59) to **byte_diff 51, diff_count 43**:

1. **Do the `deltaX=0 / deltaY=0` stores via the linker symbols DIRECTLY
   (`gIwram_6540.deltaX = 0; gIwram_6480.deltaY = 0;`), THEN assign the `a`/`b`
   pointers AFTER the stores.** In Round 2 the stores went through `a`/`b`
   (`a->deltaX=0`), which made agbcc materialise A's base in its home reg up
   front and emit a different pointer-copy shape. Storing via the symbol first
   reproduces the target's `ldr r0,=A; strh; ldrb kind,[r0,#9]; adds r3,r0,#0`
   scratch-then-copy-to-home pattern. This alone took 59 → 44.
2. **Assign `b = &gIwram_6480;` BEFORE `a = &gIwram_6540;`** (B-pointer first).
   Took 44 → 43. (Equivalent: swap the two zero-stores; same result.)

The clean, NO-PIN, NO-FLAG version below is the new best base. RESUME FROM IT.

- target reads `ldrb r5,[r0,#9]` (kind via the scratch base r0) BEFORE the

- target keeps gs-base in r0 through the subtraction (`ldr r1,[r0]; ldr

## ROOT CAUSE — fully traced to global.c find_reg (the agbcc CYGNUS 3-pass)

It ALL reduces to: does maxX's home reg become **ip** (target) or **r9**
(build)? Once maxX→ip, gs→r9 (next free), gs's `mov r9` defers (callee-saved
home keeps the value in the r0 scratch through the subtract → r2 is clobbered →
kind can't stay in r2 → kind→r5 → stepX→r6, stepY→r7). The whole 43-diff is
this one cascade.

agbcc gives maxX r9 (not ip) because of the CYGNUS "live range" 3-pass in
`global.c:find_reg` (symlinked at tools/agbcc-src/gcc_arm/global.c, ~line 1311):
- pass 1 uses `used_nopref` = used1 | ~regs_used_so_far | regs_someone_prefers,
  i.e. it ONLY allows registers that are ALREADY used-so-far AND not preferred
  by another pseudo. maxX (pseudo 22, allocated 10th of 12; order
  `45 42 43 63 91 124 152 27 37 22 44 32`) finds r9 already used-so-far and
  non-conflicting in pass 1, so it takes r9 and never reaches pass 2 (where
  first-fit in REG_ALLOC_ORDER `{3,2,1,0,12(ip),14,...,9,...}` would give it ip
  at position 4 before r9 at position 12). gs (44, lowest priority, allocated
  11th, ll=288) then takes the still-fresh ip in pass 2.
- To FLIP: make ip be `regs_used_so_far` (used by an earlier-allocated pseudo
  that dies before maxX's range) OR make maxX fail pass 1 entirely (no
  reusable non-conflicting reg) so it falls to pass-2 first-fit = ip. Neither
  was achievable by any pure-C shape, pin, or flag tried.

## Corpus sweep (2026-06-03)

**Outcome: IMPROVED (no true match). byte_diff 180 -> 116.** A fresh structural lever cut the documented base in half and, crucially, made the *instruction stream* match the target byte-for-byte except for register names. The residual is the exact coupled register-coloring decision the deferred doc already isolated; the corpus holds no transferable C-shape trick for it.

### The exact asm idiom that diverges
At function entry the baserom materialises each IWRAM controller pointer into a SCRATCH register, uses it for the unconditional `deltaX=0 / deltaY=0` stores AND the first `kind = a->kind` read, then COPIES it to a callee-saved home register:
```
135d4 ldr r0,[pc] (&gIwram_6540 -> scratch r0)
135d8 strh r1,[r0,#44]        ; deltaX=0 via scratch
135da ldr r2,[pc] (&gIwram_6480 -> scratch r2)
135dc strh r1,[r2,#46]        ; deltaY=0 via scratch
135de ldrb r5,[r0,#9]         ; kind via scratch, into CALLEE-SAVED r5
135e0 adds r3,r0,#0           ; copy scratch r0 -> home r3   <-- the idiom
135e2 adds r4,r2,#0           ; copy scratch r2 -> home r4
```
and the two high-value spanning values are split as: **maxX -> ip**, **gGameStuff-base -> r9** (cached `mov r9,r0` AFTER the gate load), **kind -> callee-saved r5** (which frees r5 and shifts stepX->r6, stepY->r7).

The documented clean base (180 / diff_count 59) instead loads the pool literals straight into home r3/r4 (no scratch-then-copy), funnels **maxX -> r9** and **gGameStuff-base -> ip** (the SWAP), and keeps **kind in scratch r2/r3** (so stepX/stepY shift down one).

### Why no trick transferred
The blocker is NOT a fold, addressing mode, or CSE idiom that a known C shape produces. It is a single coupled REGISTER-ALLOCATION outcome. The corpus's matching commits encode the *result* (the asm) but the C that produced it relied on the same allocno-priority math; copying their C structure (which is for different live-range shapes) does not reproduce our specific maxX-vs-gs priority tie-break. So there is no copyable trick here — confirmed by reading the C those commits added.

### What the new lever DID achieve (the improvement)
Introducing a separate scratch-pointer pseudo for the early uses — `struct ScrollAxis *pa=&gIwram_6540; pa->deltaX=0; kind=pa->kind; a=pa;` — made agbcc emit the target's `adds rHOME,rSCRATCH,#0` pointer-copy AND grew the output to **exactly 220 bytes (target size; the clean base was 216)**. byte_diff dropped 180 -> **116**, and a side-by-side of the built `.o` vs baserom shows the instruction sequence is now IDENTICAL through block A and block B — every remaining diff line is an ARGUMENT_MISMATCH register rename, not a different instruction. diff_count rose 59 -> 76 only because the (now-correct) extra copy instructions expose more rename sites; that is a better permuter seed, not a regression, because the permuter now only has to find a register relabeling rather than invent the copy structure.

### agbcc pass implicated (register-coloring)
`tools/agbcc-src/gcc_arm/local-alloc.c` + `global.c`. Dumped `.greg` via `old_agbcc -dg` on both bases. In the near-match RTL: `reg/v:SI 9 r9` is set from `r0` = the zero-extended maxX arg (insn 388); `reg/v:SI 12 ip` is set from `r0` with `REG_EQUIV (const_int 50352944)` = 0x03005330 = gGameStuff base (insn 84). So **maxX->r9, gs->ip** — exactly reversed from the target. Mechanism: LOCAL allocation (local-alloc.c) runs BEFORE global and claims ip for the block-local gs pseudo; by the time global-alloc (`find_reg` walking REG_ALLOC_ORDER `{3,2,1,0,12,14,4,5,6,7,8,10,9,...}`, ip=pos4 < r9=pos12) processes the spanning maxX pseudo, ip is already taken, so maxX falls to r9. The target is the opposite assignment of the same two registers. The greg sorted-order shows the gs block-pseudo has a SHORTER live_length than maxX, giving it higher `refs^2*log/live_length` priority -> it wins the local-alloc race for ip.
