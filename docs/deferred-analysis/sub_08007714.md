The prologue MATCHES exactly (including high-reg push/pop for r8/r9/sl, and the zero-extension of c/d via `(u16)(((u32)c << 16) >> 16)`).

The x-packing block MATCHES exactly.

**Stuck on height block** (registers r0 vs r3 for height intermediate):

Target emits:
```asm
ldrh r3, [r4, #4]      // height into r3
lsls r0, r3, #16       // hShift = height<<16 into r0
lsrs r3, r0, #16       // height back into r3
mov ip, r3              // save height in ip
lsrs r0, r0, #17       // halfH = hShift>>17
ldrh r4, [r4, #0]      // y (overwrites r4=rect)
subs r0, r4, r0
...
ldr r3, [pc, ...]      // 0x0000ffff mask (into r3, freed from height)
...
mov r0, ip             // restore height for packing
orrs r2, r0
...
```

My code emits (height in r0 instead of r3, hShift in r3 instead of r0):
```asm
ldrh r0, [r4, #4]      // height into r0 (WRONG!)
lsls r3, r0, #16       // hShift into r3
lsrs r0, r3, #17       // halfH directly (skipping >>16 ip-save)
ldrh r4, [r4, #0]      // y
...
ldr r4, [pc, ...]      // 0x0000ffff mask (into r4 because r3 still holds hShift)
...
lsrs r3, r3, #16       // height from kept-alive hShift
...
```

Root cause: agbcc's local-alloc assigns r0 to height (earlier-created pseudo, lower qty number, same priority as hShift due to hShift's long lifetime). The target binary had hShift with SHORT lifetime (allocated IMMEDIATELY after height, dying at >>17), giving it high priority → r0. In my C, hShift lives until `packed.height = heightShift >> 16` (after packed.y), making it long-lived → priority rounds to 0 → tie-breaking gives r0 to height.

## Levers tried

1. `register u16 ip_height asm("ip")` pin for height → IGNORED by agbcc for computed vars
2. `register struct CenterRect *r4_rect asm("r4")` pin → correct prologue but r0/r3 swap unchanged
3. `register u16 r3_h asm("r3")` pin → IGNORED for computed vars
4. Computed hShift immediately (packed.height before packed.y) → agbcc CSE-folds `hShift>>16 = height` and `hShift>>17 = height>>1`, generates `ldrh; lsrs r0,r3,#1` directly (16 mismatches, different problems)
5. `s32 heightShift` vs `u32 heightShift` → no change
6. `-fno-gcse` flag → no change
7. `-ffixed-r0`, `-ffixed-r3` → worse (breaks other register assignments)
8. Newer AGBCC_BIN → worse (23 mismatches)
9. `r = r4_rect` alias + `r->height` twice → compiler generates two separate ldrh instructions instead of the <<16 pattern (different structure, still 16 mismatches)
10. Explicit `((u32)height<<16)>>17` vs `height>>1` → CSE-folded to `lsrs r0, r3, #1`
11. `(u16)(((u32)c<<16)>>16)` pattern for c/d → WORKS for prologue ordering but not for height

## Key insight for next attempt

The target's C likely had `heightShift = (u32)rect->height << 16` with BOTH:
- `heightShift >> 16` (to save to ip/packed.height) computed CONSECUTIVELY with
- `heightShift >> 17` (halfH)

making hShift very short-lived (2-3 instructions). This gives hShift QTY_CMP_PRI > 0 → allocated first → r0. Height gets r3 → ip save.

The challenge: agbcc folds `(u16_val << 16) >> 16 = u16_val` and `(u16_val << 16) >> 17 = u16_val >> 1` for known-u16 values. The fold prevents the two-use pattern from materializing.

Possible approaches NOT tried:
- Maybe the original C had `s32 heightShift` (signed shift of u16 height — would overflow for h > 32767, but `(u32)hShift >> 16` and `(u32)hShift >> 17` still work). agbcc might NOT fold `(s32)(u16<<16) >> 16` because it could sign-extend for large values.
- Try splitting into a helper function that takes height as u32 and returns the packed representation.
- Try `asm("")` barrier between `heightShift` assignment and the two uses.
- Read agbcc's cse.c to find the exact fold being applied and whether there's a C pattern that blocks it.
