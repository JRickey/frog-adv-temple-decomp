**Stuck on height block** (registers r0 vs r3 for height intermediate):

Target emits:
```asm
ldrh r3, [r4, #4]      // height into r3
lsls r0, r3, #16       // hShift = height<<16 into r0
lsrs r3, r0, #16       // height back into r3
mov ip, r3              // save height in ip
lsrs r0, r0, #17       // halfH = hShift>>17
ldrh r4, [r4, #0]      // y (overwrites r4=rect)
subs r0, r4, r0
...
ldr r3, [pc, ...]      // 0x0000ffff mask (into r3, freed from height)
...

...
```

My code emits (height in r0 instead of r3, hShift in r3 instead of r0):
```asm
ldrh r0, [r4, #4]      // height into r0 (WRONG!)
lsls r3, r0, #16       // hShift into r3
lsrs r0, r3, #17       // halfH directly (skipping >>16 ip-save)
ldrh r4, [r4, #0]      // y
...
ldr r4, [pc, ...]      // 0x0000ffff mask (into r4 because r3 still holds hShift)
...
lsrs r3, r3, #16       // height from kept-alive hShift
...
```

Root cause: agbcc's local-alloc assigns r0 to height (earlier-created pseudo, lower qty number, same priority as hShift due to hShift's long lifetime). The target binary had hShift with SHORT lifetime (allocated IMMEDIATELY after height, dying at >>17), giving it high priority → r0. In my C, hShift lives until `packed.height = heightShift >> 16` (after packed.y), making it long-lived → priority rounds to 0 → tie-breaking gives r0 to height.

## Key insight for next attempt

The target's C likely had `heightShift = (u32)rect->height << 16` with BOTH:
- `heightShift >> 16` (to save to ip/packed.height) computed CONSECUTIVELY with
- `heightShift >> 17` (halfH)

making hShift very short-lived (2-3 instructions). This gives hShift QTY_CMP_PRI > 0 → allocated first → r0. Height gets r3 → ip save.

The challenge: agbcc folds `(u16_val << 16) >> 16 = u16_val` and `(u16_val << 16) >> 17 = u16_val >> 1` for known-u16 values. The fold prevents the two-use pattern from materializing.

- Try splitting into a helper function that takes height as u32 and returns the packed representation.
- Try `asm("")` barrier between `heightShift` assignment and the two uses.
- Read agbcc's cse.c to find the exact fold being applied and whether there's a C pattern that blocks it.

## Corpus sweep (2026-06-03)

**Outcome: DEFERRED.** Thorough corpus asm-idiom search + 14 informed structural attempts. No corpus trick transfers; byte_diff floor was 69 (coincidental alignment) / 75 (correct-structure base), never 0. Tree left pristine, `make check` passes, no commits.

### The exact asm idiom that diverges (the height block, [0x7752,0x775a))
The baserom reads the u16 `height` field ONCE and keeps the recovered value alive in a callee reg spilled to `ip`, because the rect pointer (in r4) is destroyed when y is loaded:
```
ldrh r3, [r4, #4]    ; height -> r3 (read ONCE)
lsls r0, r3, #16     ; hShift = height<<16 -> r0
lsrs r3, r0, #16     ; recover height -> r3  (the (x<<16)>>16 "recover")
mov  ip, r3          ; SPILL recovered height to ip
lsrs r0, r0, #17     ; halfH = hShift>>17 -> r0
ldrh r4, [r4, #0]    ; y (DESTROYS r4=rect; height safe in ip)
...
mov  r0, ip          ; restore height for packing
orrs r2, r0
```
agbcc instead refuses to materialize the redundant `<<16;>>16` recover for a provably-u16 field. With a `heightShift` variable it FOLDS `heightShift>>16` back to a field re-read and computes `>>17` directly (`lsls r3,r0,#16; lsrs r0,r3,#17`); with field reads it emits a direct `lsrs r0,r3,#1` halve and RE-READS the field for `packed.height` (`ldrh r4,[r4,#4]`, keeping rect alive in r4 and never spilling to ip). In short: **baserom preserves HEIGHT across the y-load (spill rect); agbcc preserves the RECT POINTER and re-reads/re-halves height (no ip spill).**

**Conclusion: the specific idiom — a u16 field `<<16` whose `>>16`-recover is kept LIVE (spilled to `ip`) alongside its `>>17`-halve, reading the field once — does NOT appear paired with C in any of the 23 agbcc mirrors.** The corpus has `(x<<16)>>16` zero-extends and `(x<<16)>>17` 15-bit masks in abundance, but never the recover-then-spill that this center→corner rect packer needs.

### Why the trick did not transfer
The matching SIBLING `sub_080076A4` (same TU, byte_diff 0, no c/d args) proves the recover+halve sequence is reachable from `r->height >> 1` + `packed.height = r->height` — but ONLY because that function has a SPARE callee reg (r4) to hold height across the y-load, so no `ip` spill is needed. sub_08007714 adds two args (c→r9, d→sl) and pins rect in r4, raising register pressure so height MUST spill to ip. agbcc, given the same C, chooses to keep rect in r4 and RE-READ height rather than spill it — the opposite of the baserom. Every C shape that forces the single-read-then-recover either (a) gets the `<<16;>>16` folded away (CSE proves `(u16<<16)>>16==u16`), or (b) introduces an extra live local that triggers stack spilling and breaks the high-reg prologue.

### agbcc pass implicated
- **Fold of `(u16_field<<16)>>16 → u16_field`**: `tools/agbcc-src/gcc_arm/combine.c`, `make_compound_operation` / `simplify_shift_const` driven by `nonzero_bits` / `set_nonzero_bits_and_sign_copies` (combine.c ~lines 737-802, 2135-2177). Because an `ldrh` field has `reg_nonzero_bits == 0xFFFF`, combine proves the shift pair is identity and eliminates the recover, choosing rematerialization (re-`ldrh`) over a live spill.
- **The keep-rect-vs-keep-height choice**: `tools/agbcc-src/gcc_arm/local-alloc.c` / `reload.c` register-coloring — given the recover is free (re-readable field), local-alloc prefers leaving rect in r4 and re-reading height, never generating the `mov ip` spill. This is the genuine register-coloring residual the doc named; it is downstream of the combine fold (if the recover were NOT free, the spill would appear).
