# sub_0800411C — deferred analysis

Mode-X game-state dispatcher at `0x0800411c` (768 B), handler for
`GAME_MODE_SCENE_20` (20) and `GAME_MODE_ATTRACT` (24). The "fuller"
sibling of `sub_08002844` (mode_15.c): same 9-state `switch (*statep)`
dispatcher driven by a `mov pc, rN` jump table, but with the case-0 setup
block (= the matching helper `sub_0800441C`) and the case-3 spawn block
(= the matching helper `sub_080044A4`) INLINED instead of called. 972-byte
stack frame with seven scratch buffers + a 4-byte ctrl pair.

VERDICT (classify_unmatchable): **ATTEMPT_MATCH** (`mov pc, r0` is the C
switch lowering, NOT unmatchable). NOT NAKED material. The dispatcher core,
frame layout, prologue, register ALLOCATION, and 8/9 cases match
byte-for-byte. The residual is a pure instruction-emit-ORDER divergence.

## Drift (Opus round-2 — supersedes the round-1 precompute hypothesis)

Best **byte_diff = 313, diff_count 90** with a clean 4-reg prologue
(`push {r4,r5,r6,lr}`). ~60 of the 90 diffs are `b.n`/`bl` target-offset
CASCADE from a tiny number of real instruction-pair swaps. The genuine
distinct divergences are only:

1. **Entry r0/r1 swap** (3 instrs, ~2 B). Baserom: `ldr r0,=0x3b9; add r0,sp;
   movs r1,#0; strb r1,[r0]` (addr in r0). Built `STATE=0;` gives addr in r1.
   The mode_15 idiom `register u8 *statep asm("r0"); u8 zero=0;
   *(volatile u8*)statep=zero;` DOES flip it to addr-in-r0, but in the full
   function it forces a 5-reg prologue (r7 push) — net worse. Cosmetic.

2. **Arg-evaluation ORDER (dominant; cases 0 and 3, 4 call sites).**
   Baserom emits the CONST arg then the buffer address:
   `movs r0,#3; add r1,sp,#612`. Built emits ADDRESS first:
   `add r1,sp,#612; movs r0,#3`. Register allocation is IDENTICAL otherwise
   (r4=pair11, r5=pair16, r6=0, same buf offsets) — ONLY these two moves swap.

3. **case 4 sub_08009C14 arg** — recompute `&state` (`ldr r0,=0x3b9; add r0,sp`)
   matches baserom's internals → byte_diff **301**, but pushes r7 (5-reg
   prologue). Reusing the cached `statep` → byte_diff **313** with the correct
   4-reg prologue. Sharp either/or; 313+4reg was kept as the cleaner base.

## ROOT CAUSE of #2 — CONFIRMED via agbcc-source instrumentation (round-1 was WRONG)

The round-1 note blamed `calls.c:precompute_register_parameters`. A private
instrumented `old_agbcc` (fprintf at the `copy_to_mode_reg` precompute site)
showed **ZERO precompute firings** for these args — precompute is NOT the cause.

The real chain:
- `expand_expr(&buf1)` (expr.c case ADDR_EXPR, ~line 8027) calls
  `op0 = force_operand(XEXP(op0,0), target)` on `(plus sp 612)`. Because the
  sp-offset 612 is not an `add`-encodable immediate path here, force_operand
  materialises it into a **pseudo** with a LOW insn-UID (created at expand).
- The CONST arg `movs r0,#3` is emitted later in the arg-load loop
  (`calls.c` ~line 2061, `emit_move_insn(reg, value)`), so it has a HIGHER UID.
- The Thumb list-scheduler breaks the (equal-priority) tie between the two
  independent moves by INSN_UID → the low-UID address `add` wins → addr-first.
- For const-first, the address pseudo must be **rematerialised at the use**
  (reload regenerates `add r1,sp,#612` AT the call, after `movs r0,#3`). That
  happens only when reload does NOT give the pseudo a hard reg.

## What TIPS reload between rematerialise (const-first) and hold (addr-first)

**Bisected to register pressure from the two-comparison loop tail.** An
isolated probe of the EXACT case-0 shape (5 buffers, pair11/16 hoisted to
r4/r5, volatile STATE, pendingMode=13) compiles **const-first**. Adding the
`while (gGameStuff.mode == 20 || gGameStuff.mode == 24)` tail (TWO compares
of the mode byte, REQUIRED by the baserom) flips it to **addr-first**. A
SINGLE compare stays const-first; the second compare's live range is the
straw that tips reload to hold the buf1/buf2 address pseudos in regs.

So const-first IS reachable (the baserom proves it, with the same two-compare
tail) — it is a sharp GLOBAL coloring/scheduling local minimum, NOT a wall.
The baserom hit the rematerialise side; agbcc from every clean source shape I
found hits the hold side.

## What DID land (KEEP for the next attempt — these all match baserom)

- **Frame layout MATCHES.** Declare ctrl as a 4-byte ARRAY `u8 ctrl[4]` (NOT a
  struct, NOT scalars — those sort to the TOP of the frame at 0x3c8; only a
  BLKmode array lands in the array group at 0x3b8). Order:
  `buf0[612],buf1[72],buf2[108],buf3[32],buf4[128],ctrl[4],pair11[8],pair16[8]`
  → exact baserom sp-offsets (buf0@0, buf1@612, buf2@684, buf3@792, buf4@824,
  ctrl@952/0x3b8, pair11@956/0x3bc, pair16@964/0x3c4).
- State addressing: `#define STATE (*(volatile u8*)&ctrl[1])` yields the
  baserom `ldr =0x3b9; add sp; ldrb/strb [+0]` recompute (0x3b9 is not an
  add-encodable sp offset, so the literal-pool recompute matches; a plain
  `ctrl[1]` gives `add sp,#952; [+1]`). No cached `statep` pointer — the
  baserom recomputes via the literal every loop iteration.
- case 3 spawn MATCHES: `register u32 nextState asm("r3")` + `(p3720->status & 8)`
  / `(gIwram_6110.inputFlags & 8)` with literal 8 (mirrors mode_15).
- **pair11/pair16 hoisting** into callee r4/r5: introduce `u8 *p11=pair11;
  u8 *p16=pair16;` at the TOP of case 0, and (CRITICAL) JUST BEFORE the spawn
  calls in case 3 (NOT at case-3 top — that over-extends the live range and
  REGRESSES to 454). case 4 hoists p11/p16 + a `statep` local for `*statep=7`.
  This made the sub_0800B7B0/sub_08004508 pointer args match exactly.
- Prologue `push {r4,r5,r6,lr}` matches when case-4 reuses `statep` for the
  sub_08009C14 arg (recompute form costs the r7 push).
