# Deferred analysis: sub_0801C69C

Range: [0x0801c69c, 0x0801c6e4) — 72 bytes, Thumb

## Function semantics

Clears DISPCNT bits (WIN0_ON bit 13, BG3_ON bit 11), zeros window H/V registers,
zeros palette[0], DMA-fills VRAM screenblock 31 (0x0600f800, 2048 bytes) with 0s.
DMA source is a stack local set to 0 (with DMA_SRC_FIXED so reads same addr repeatedly).

Called from a state-machine (at ROM 0x1a414, 0x1a488, 0x1a4aa, 0x1a5ba) with
`adds r0, r5, #0` — parameter `a` = r5 (which can be non-zero, e.g. 14).

## Drift: byte_diff 34, diff_count 11

The function has a `u8 a` parameter that causes `lsls r0,r0,#24; lsrs r0,r0,#24`
zero-extension at the very top (offsets 0x02-0x04 from function start). This is
confirmed by empirical testing: agbcc DOES NOT emit the extension for a dead u8 param,
so `a` MUST be used somewhere in the body.

Despite extensive analysis and testing, the exact C expression that:
1. Emits the zero-extension at the top
2. Keeps r0=a alive through the DISPCNT/WIN0H/WIN0V/palette section
3. Does NOT emit an extra `strh r0,[r1,#0]` dead store for `local=a`
4. Results in r2 being reloaded at the end (not r3 CSE'd)
...could NOT be determined.

Best attempts tried (and why they fail):

- `local = a; local = 0;` — keeps r0=a alive, forces r3 for DISPCNT base,
  palette writes use r2=0. But generates EXTRA `strh r0,[r1,#0]` for local=a
  AND local=0 uses wrong registers (movs r1,#0; mov r0,sp; strh r1,[r0,#0]).
  byte_diff 36 on `local=0;local=a` order.
  
- `*(vu16*)0x05000000 = a;` — keeps r0=a alive, r3 for DISPCNT, palette uses r0.
  byte_diff starts right: palette instruction is WRONG (r0 vs r2). `strh r0` not `strh r2`.

- `local = a; local = 0; REG_DMA3.src = &local;` — same dead store issue as above.

- Chain assignment `local = a = 0` — agbcc folds to local=0, no zero-extension.

- `asm("" : "+r"(a))` barrier — no zero-extension emitted.

- `asm volatile("" ::: "memory")` after DMA — doesn't prevent r3 CSE.

- `asm volatile("" ::: "r3")` — clobbers r3, forces push{r4,lr}, breaks prologue.

## Key structural findings

1. The zero-extension REQUIRES `a` to be actually used (agbcc optimizes dead params).
2. r3 = DISPCNT base at top (first access) because r0=a occupies r0.
3. r2 = 0 for WIN0H/WIN0V/palette zero-writes (from movs r2,#0).
4. Second DISPCNT access reloads into r2 (NOT CSE from r3) — unclear why agbcc breaks CSE.
5. local=0 via: `mov r1,sp; movs r0,#0; strh r0,[r1,#0]` — r1=sp comes FIRST,
   suggesting this is from a pointer pattern (`vu16 *p = &local; *p = 0;`)
   or from a preceding `local = a` that already set r1=sp.

## Hypothesis for next attempt

The `mov r1, sp; movs r0, #0; strh r0, [r1, #0]` sequence for local=0 suggests
the C might use a local pointer: `vu16 *p = &local; *p = 0;` where r1=p=sp comes
BEFORE r0=0. But this also doesn't use `a` visibly.

Possible the second DISPCNT access uses `a` in a mask expression that agbcc
constant-folds to 0xf7ff (e.g. `a >> 8` for u8 = 0), but agbcc still emits
the zero-extension before folding. NOT confirmed — tests with `a >> 8` in mask
showed agbcc optimizes it away entirely with no extension.

Another hypothesis: the function is compiled with a DIFFERENT flag (e.g., `-O1`
or no `-fhex-asm` for this one file). Not tested.
