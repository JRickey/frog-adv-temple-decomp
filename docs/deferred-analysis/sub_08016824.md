## Function summary

Tile-copy function: given a u8 index, looks up a 24-byte `TileBlitRecord` from
`gTileBlitTable_08306840` (at ROM 0x08306840, within the `sSpriteAnimBlock_06838`
blob), and copies tile data from ROM to VRAM screenblock 31 (0x0600f800).

Struct layout (24 bytes, same stride as the `BlitRecord` used in sub_08011478):
- `+0`  u16 colStart     (column offset in tilemap row, in u16 units)
- `+2`  u16 tileRow      (tile row × 64 bytes = byte offset in screenblock)
- `+4`  u16 colCount     (tiles to copy per row)
- `+6`  u16 rowCount     (number of rows to copy)
- `+8`  u8[8] pad
- `+16` const u16 **srcTable  (double-deref to get source u16* tile data)
- `+20` u32 pad

Outer loop: rows 0..rowCount-1. Inner loop: copies colCount u16 tiles from srcTable[0]
to the VRAM destination. After each row, advances vramDst by (32-colCount)*2 bytes
(padding to 32-wide tilemap row).

## Drift

**5 mismatches, byte_diff 8:**

1. `push {r4, r5, r6, r7, lr}` (target) vs `push {r4, r5, r6, lr}` (built)
2. vramDst computation addition order:
   - target: `adds r0, r0, r6; adds r1, r1, r0`  (tileRow*64 + vramBase, then + colStart*2)
   - built:  `adds r1, r1, r0; adds r1, r1, r6`  (colStart*2 + tileRow*64, then + vramBase)
3. `pop {r4, r5, r6, r7}` (target) vs `pop {r4, r5, r6}` (built)

**Root causes:**

**push/pop r7**: agbcc's prologue generation does NOT add r7 to the push/pop list when
`register T x asm("r7")` is declared in a non-do-while scoped block (even when r7 IS used
in the generated assembly). This contrasts with sub_0800b7b0 where slotsBase (r7) pin is
INSIDE a do-while body and IS saved. Putting loopStride (r7) inside the do-while causes
a conflict with the nextRow counter (agbcc assigns both to r7).

**vramDst order**: The expression `colStart*2 + tileRow*64 + vramBase` computes in
left-to-right order `(A+B)+C`. Target computes `A+(B+C)` — grouping `tileRow*64+vramBase`
first into r0, then adding colStart*2 from r1. Explicit parentheses in C cause the pool
literal (vramBase=0x0600f800) to be scheduled BEFORE tileRow is loaded (disrupting r4
reuse for tileRow). Without parentheses, the pool is scheduled too late (after the A+B merge).

## Next agent hints

1. **push/pop r7**: Try putting BOTH `register u32 loopStride asm("r7")` INSIDE the do-while
   AND separately handle the `adds r7, r3, #0` transition. The key insight from sub_0800b7b0:
   agbcc saves r7 only when the r7 pin is in a do-while loop body with heavy usage.
   The conflict: nextRow also gets r7 when inside do-while. Try pinning nextRow to r6 explicitly
   inside the do-while body WITH loopStride declared FIRST (before nextRow).

2. **vramDst order**: The target computes `(tileRow*64 + vramBase) + colStart*2`. For this:
   need pool (0x0600f800) loaded to r6 BETWEEN `lsls r0, r4, #6` and the r0+=r6 add,
   WITHOUT colStart*2 being merged into r0 first. Try expressing as two sequential assignments:
   `vramDst = (u16 *)((u32)entry->tileRow << 6);` then 
   `vramDst = (u16 *)((u32)vramDst + 0x0600f800 + (u32)entry->colStart * 2);`
   where colStart is added LAST (so the pool loads between tileRow*64 and the colStart add).

3. The `gTileBlitTable_08306840 = 0x08306840` linker symbol has been added to linker.ld
   (required for the C extern declaration to resolve).

4. **srcTable access**: Target uses `adds r0, r5, #0; adds r0, #16; adds r0, r3, r0; ldr r0, [r0]; ldr r4, [r0]`
   (5 instructions via tableBase+16+stride). Match this using:
   `u32 srcAddr = (u32)tableBase + 16; asm("" : "+r"(srcAddr)); src = **(const u16 ***)(stride + srcAddr);`
   (the asm barrier prevents agbcc from folding to `ldr [entry+16]`).
