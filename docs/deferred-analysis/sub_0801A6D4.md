# Deferred Analysis: sub_0801A6D4

**Range**: 0x0801a6d4 – 0x0801a774 (160 bytes, Thumb)
**Destination**: src/engine/sub_0801a6d4.c

## Function Summary

Scroll-rect camera clamp. For `count` 32-byte entries at gIwram_60A0[]:
computes camera scroll origin from player position (gIwram_3720._field_2 / _field_4),
clamped within bounds derived from each entry's tile-width/height fields.

## Drift

**Best byte_diff**: 3 code bytes (+ 6 pool reloc bytes that will match after linking).
**Total cmp -l differences**: 9 (3 at code offsets, 6 at pool).

All 3 code differences are the SAME type: commutative `adds` instruction encoding:
- Offset 0x24: `adds r4, r0, r2` (0x1884) vs target `adds r4, r2, r0` (0x1814)
- Offset 0x32: `adds r5, r0, r2` (0x1885) vs target `adds r5, r2, r0` (0x1815)
- Offset 0x5a: `adds r3, r0, r2` (0x1883) vs target `adds r3, r2, r0` (0x1813)

In all cases: r0 = ip+12 or ip+16 (bfc = base offset), r2 = stride = i*32 (pinned via `register asm("r2")`). The instructions compute the same value (r0+r2), but with Rn/Rm roles swapped.

**Levers tried**:
- `register u32 stride asm("r2")` pin → correct zero/stride register assignment (r1 for zero, r2 for stride)
- `register struct ScrollEntry *base asm("ip")` and `register struct IwramAt3720 *ent asm("r6")`
- `register u8 n asm("r8")`, `register u32 zero asm("r9")`
- Two-step: `bfc = base+12; ptr_c = bfc + stride` → correct function size (160 bytes), 9 diffs
- Inline: `(u8*)base + 12 + stride` → 164 bytes (extra `adds r0, r2, #0` copy)
- `stride + bfc` expression → same output as `bfc + stride` (GCC canonicalizes internally)
- `stride + ((u8*)base + 12)` with explicit parens → same 164 bytes
- `(u32)base + 12 + stride` (integer arithmetic) → same result
- `-fno-cse`, `-fno-schedule-insns`, `-fno-gcse`, `-fno-rerun-cse-after-loop`, `-fforce-addr`, `-O1`, OLD_AGBCC → all give 9 differences
- Permuter ran 160+ iterations, best score 945 but that corresponds to 54 raw byte diffs (WORSE)

**Root cause analysis**: In `expand_binop` (optabs.c line 424-441), the commutative swap only occurs when one operand is NOT a register. Both bfc (r0) and stride (r2) ARE registers, so no swap. The instruction is emitted as `adds Rd, op0, op1` where op0/op1 is the expand_expr order. The two-step form has bfc as TREE_OPERAND(0) → op0=r0 (Rn=r0). For target's `adds Rd, r2, r0`: stride must be op0=r2 (Rn=r2). This would require stride to be TREE_OPERAND(0) in the C AND not be reordered by GCC internals. We could not achieve this consistently.

**NOT tried yet**:
- `stride + bfc` form with bfc being a PSEUDO-REGISTER (not hard r0) at the time of the add — would change Rm/Rn if bfc is not yet allocated to a hard reg when the add is generated
- `-ffixed-r1` to prevent r1 from being used, possibly changing allocation
- Computing bfc into r3 (not r0) to see if `adds r4, r2, r3` would follow from targeting r4
- Looking at the instruction ordering at 0x5a for the third difference specifically (perhaps addressable separately)
