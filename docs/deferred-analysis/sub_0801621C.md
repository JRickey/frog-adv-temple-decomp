# Deferred analysis: sub_0801621C

**Range**: `[0x0801621c, 0x0801629c)` — 128 bytes, Thumb leaf  
**Destination**: `src/engine/sub_0801621c.c` (already scaffolded)  
**Callees**: none (pure leaf)

## Function Summary

Mode-4 frame-buffer DMA blit. Parameters:
- `r0` = dstX (u16 dst pixel column)
- `r1` = dstY (u16 dst pixel row)
- `r2` = src (u8 *, base of source bitmap)
- `r3` = desc (ptr to `{u8 x, u8 y, u8 width, u8 rows}` source rect)

Logic: selects the GBA Mode-4 back-buffer (VRAM frame 0 at 0x06000000 if
DISPCNT bit 4 is set, else frame 1 at 0x0600A000), computes dst row pointer,
computes src row pointer from desc, then DMA3-copies each row for `rows` rows.

## Best-effort C

```c
#include "gba/dma.h"
#include "gba/io.h"
#include "types.h"

#define DISPCNT_FRAME1 (1U << 4)

struct BlitDesc {
    u8 x;
    u8 y;
    u8 width;
    u8 rows;
};

void sub_0801621C(u16 dstX, u16 dstY, u8 *src, struct BlitDesc *desc)
{
    u8 *dst;
    u8 *srcBase;
    u8 *srcRow;
    u16 i;

    if (REG_DISPCNT & DISPCNT_FRAME1)
        dst = (u8 *)(0x06000000 + (u32)dstY * 240);
    else
        dst = (u8 *)(0x0600a000 + (u32)dstY * 240);
    dst += dstX;

    srcBase = src + (u32)desc->y * 240;
    srcRow = srcBase + desc->x;

    for (i = 0; i < desc->rows; i = (u16)(i + 1)) {
        REG_DMA3.src = srcRow;
        REG_DMA3.dst = dst;
        REG_DMA3.cnt = DMA_ENABLE | (desc->width >> 1);
        (void)REG_DMA3.cnt;
        srcRow += 240;
        dst += 240;
    }
}
```

## Drift

**Best byte_diff**: 10 bytes (5 halfwords in 2 patterns)  
**Compiler**: `old_agbcc -O2 -fno-expensive-optimizations`

The 10 differing bytes are all pure register coloring:

**Pattern A — then/else-branch result register (6 bytes, 3 halfwords)**:
- Mine: `adds r2, r0, r1` (then) and `adds r2, r0, r7` (else) — base result in r2
- Target: `adds r0, r0, r1` (then) and `adds r0, r0, r7` (else) — base result in r0

**Pattern B — merge instruction (2 bytes, 1 halfword)**:
- Mine: `adds r2, r2, r3` (in-place: r2 = base, add dstX)
- Target: `adds r2, r3, r0` (fresh: r2 = dstX + r0-base)

**Pattern C — srcRow computation registers (2 bytes, 1 halfword)**:
- Mine: uses r0/r1 in slightly different order for desc->y*240 computation
- Target: different r0/r1 usage for the multiply-by-240

## Root Cause

The if-else branches compute `VRAM + dstY*240` into r2 (because dst is allocated
to r2 and the branches directly fill dst's register in-place). The TARGET computes
this intermediate into r0, then the merge freshly creates dst via `adds r2, r3, r0`.

For the target's form, the allocator must:
1. Reserve r2 for dst (as a "fresh" assignment at the merge, not in-branch)
2. Keep the if-else computing base into r0 (the natural computation register)
3. Use the merge `adds r2, r3, r0` to create dst from dstX+base

**Why we can't get it**: `dst += dstX` form ties dst to the branch result register
(making them the same allocation → in-place). Single-expression `dst = base + dstX`
form gives the right branch code (r0 for base) but causes register pressure that
pushes src to r6 instead of r4 (wrong prologue).
