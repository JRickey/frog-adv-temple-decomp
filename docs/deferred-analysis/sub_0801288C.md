# sub_0801288C — deferred analysis

Tile-block blit: copies a `width*height` halfword tile rectangle from a ROM
descriptor's pixel source into the EWRAM staging buffer at the player's tile
origin, padding each row to the grid stride, then queues the EWRAM->VRAM
upload via `sub_080100E4` and clears a dirty byte.

ATTEMPT_MATCH (classifier). Structurally fully decoded; blocked only by
agbcc register-coloring of `colBase` (ip vs r1), which cascades into pool
layout. NOT a structural-impossibility — do NOT ship NAKED.

## Data / address map (all verified against baserom bytes)

- ROM descriptor `sTileBlit_6e64` @ `0x08306e64` (inside sSpriteAnimBlock_06838):
  - `+0x1c` u8 `width`  (=3 in baserom)
  - `+0x1e` u8 `height` (=3)
  - `+0x20` u8 `flags`  (=0x10; `flags>>4 == 1` selects the EWRAM/VRAM pair)
  - `+0x28` u32 ptr table; entry `[1]` (i.e. `*(u32*)(ptr+4)`) = the u16 pixel source
  - Add `sTileBlit_6e64 = 0x08306e64;` to linker.ld (mirrors sAnimDesc_6e08 idiom).
- Player tile origin: `*(s16*)(&gIwram_3720 + 0x692)` (= rowBase*1/3 source) and
  `+0x694` (= colBase source); each multiplied by 3 then narrowed to u16.
  rowBase = `*0x692 * 3`, colBase = `*0x694 * 3`.
- Dest base: `(flags&1) ? 0x02010000 : 0x02000000` (EWRAM staging).
- **Stride** = `*(u16*)(0x030060A0 + 0x1A)`  (gIwram_60A0; NOT 0x030064c0 — easy
  to conflate, the two bases are distinct).
- dst offset (halfwords) = `colBase * stride + rowBase`.
- Row advance after each inner row = `stride - w` (so total per row = stride).
- Tail: `sub_080100E4(flags&1, ewram, vram)` where the EWRAM/VRAM args are
  `(0x02010000, 0x0600E800)` when `flags&1`, else `(0x02000000, 0x0600E000)`.
- Sentinel: `*(u8*)(0x030064C0 + 0x0A) = 0` (gIwram_64C0 dirty byte).

## Drift

- Best: **byte_diff 124, diff_count 69** (size 236 vs target 240; the 4-byte
  delta is the outer-loop h-compare form).
- The decode is correct. The whole residual flows from ONE allocator choice:
  the target keeps **colBase in `ip` (r12)** through the setup, frees it after
  the `muls`, and **time-shares `ip`** to cache the `0x030060A0` grid pointer
  across the loop (`ip = r4` once at loop entry). Our build narrows colBase
  into **r1** and instead parks the grid pointer in `ip`/r7 from the start, so
  no time-share — and the differing register names + the extra grid-pointer
  load shift the entire pool layout (hence the large nominal byte_diff for a
  near-correct function). Secondary: ldrsh zero-index reg is r6 here vs r7 in
  baserom; outer-loop counter lives in r3 vs r0 (target precomputes i+1 in r4).
- **Key matching levers already FOUND (keep these — they are correct):**
  - `register u32 rowBase asm("r8")` + `register u8 h asm("r9")` pins (REQUIRED:
    without them agbcc never allocates r8/r9 and the `push {r6,r7}` save of the
    high regs disappears — size drops to 224/228).
  - **Deferred u16 narrowing of rowBase**: compute it into a plain `u16 rb`
    FIRST, then `register u32 rowBase asm("r8") = rb;` LATER. This is what makes
    agbcc split rowBase's `<<16 ... >>16` around the colBase computation, exactly
    matching baserom (0x1288c+0x1c..0x32). Assigning the pin directly (no `rb`
    temp) does eager narrowing and regresses (146).
  - Passing literal `1`/`0` (not `flags&1`) as the `sub_080100E4` select arg in
    each branch dropped byte_diff 141 -> 124.

## Levers TRIED that did NOT close it (pick a DIFFERENT one next time)

- `register u16 ... asm("r8")` (u16, not u32): ELIDES the narrowing entirely

  vs absolute `*(u16*)0x030060BA`: all park grid in ip/r7 from the start
  (124 / 127 / 144) — none reproduce the colBase-in-ip time-share.
- Swapping the multiply operand order (`stride * colBase`): no change (124).
- `int` vs `u8` outer loop counter `i`: no change (124).
- Per-TU `CC = OLD_AGBCC_BIN`: identical output (124) — not a compiler-version

## Opus attempt (round 23) — root cause identified: ip time-share mutual-exclusion

Re-derived from scratch. Confirmed the prior 124/236 basin AND found the EXACT
structural blocker, which is sharper than the prior note's "colBase ip vs r1".

### The real blocker (verified against baserom + the 124-build asm)

The baserom **time-shares `ip` between two disjoint live ranges**:
1. **Setup**: `ip = colBase` (`mov ip, r0` @0x80128ba) — held until the `muls`
   (`mov r0, ip; muls` @0x80128e0). colBase is in ip *because* at the `muls`
   point every low reg r1-r6 is live (stride, dst-base, grid, width, src-table,
   flags>>4), so colBase cannot occupy a low slot and spills to ip (call-used,
   no save). This is a NATURAL global-allocation outcome under low-reg pressure.
2. **Loop**: `ip = grid` (`mov ip, r4` @0x80128f4, at loop entry). grid lived in
   **r4 (low)** for the dst-init stride read (`ldr r4,[pc]=grid; ldrh r1,[r4,#26]`),
   then is evicted to ip at loop entry *because r4 is reused for the `i+1`
   precompute* (`adds r4, r0, #1` @0x80128f8). The loop tail reads stride via
   `mov r3, ip; ldrh r3, [r3,#26]`.

The 4-byte size delta (236 vs 240) IS this time-share: baserom loads grid into r4
then `mov ip, r4`; the 124-build loads grid straight into ip at function entry
(grid wins ip persistently because its priority refs/live-length beats colBase's),
so colBase falls to a low reg (r1) and there is no r4-intermediate / `mov ip, r4`.

**Why it is mutually exclusive in C:** to put colBase in ip for setup you need a
`register u32 colBase asm("ip")` pin (natural alloc always gives ip to grid first
— grid spans the loop, higher priority). But a NAMED ip pin reserves ip for that
variable's WHOLE lexical scope, so grid can no longer reuse ip in the loop → the
loop reloads grid from the pool each iteration (`ldr r1,[pc]=grid`) instead of the
`mov r3, ip` cache. agbcc's thumb.c saves r8/r9/r10 (not r12) — pinning ip itself
adds NO save; the +4 in the pin variants comes from grid spilling to **r10/sl**
(call-preserved → saved). `-ffixed-r10` removes that spill (grid→r4) and restores
size 240, but the loop STILL reloads grid from pool (ip reserved). So the pin
gets the right SIZE but the wrong loop body; natural alloc gets the right loop
body (ip-cached grid) but the wrong setup (colBase in a low reg).

## Corpus sweep (2026-06-03)

### Outcome: IMPROVED, 124 -> 26 byte_diff, exact size match (240/240). The previously-"unmatchable" ip time-share is now SOLVED in pure C.

The prior rounds (see the body of this doc) declared the setup<->loop `ip` time-share "mutually exclusive in C" and stalled at byte_diff 124. That conclusion was wrong: the trick exists, and it was sitting in the tree all along.

### The exact asm idiom that diverges
The baserom time-shares `ip` (r12) between two disjoint live ranges:
1. Setup: `mov ip, r0` @0x80128ba holds colBase, read back `mov r0, ip; muls` @0x80128e0.
2. Loop: `mov ip, r4` @0x80128f4 holds the grid pointer (0x030060A0), read in the loop tail as `mov r3, ip; ldrh r3,[r3,#26]`.
Plus the dst-select uses the idiom `movs r1,#1; adds r0,r3,#0; ands r0,r1` (constant 1 materialized into its OWN register before the AND), with the EWRAM base in r2.

### The trick that transferred (and where it came from)
corpusSource is the IN-TREE sibling `src/engine/sub_08012bc4.c` (sub_08012BC4) — a near-identical EWRAM tile-blit that is ALREADY a byte-perfect match (verified: compile_and_view_assembly reports byte_diff 0). It expresses the ip time-share in pure C as: a function-scope `register u32 f asm("ip")` used in setup, then INSIDE the `if (row<rows){ ... }` a SEPARATE block-scoped `register u32 loopState asm("ip") = (u32)state;`. agbcc reuses the physical r12 across the two non-overlapping lexical scopes -> the `mov ip,r0` (setup) / `mov ip,r4` (loop) time-share falls out naturally. The deferred doc's claim that a NAMED ip pin reserves the register for the whole scope is true only for a FUNCTION-scope pin; a BLOCK-scope pin inside the loop is exactly the escape hatch. Adapting that structure verbatim (colBase in the function-scope `asm("ip")`, grid in the loop-block `asm("ip")`) reproduced the time-share on the first compile.

The second lever, also from the sibling: the dst-select written as `{ register u32 one asm("r1"); one=1; if (flags & one) ... }`. This single change dropped byte_diff 170 -> 26 and fixed the size (236 -> 240): it forces the `adds r0,r3,#0; ands r0,r1` idiom AND steers the EWRAM-base/dst register cascade. Pinning `col asm("r3")` shaved a further 2 but regressed the prologue (dropped the r7 push) and inner-loop form, so it was NOT kept.

### Why the match did not fully close (the residual 24 diffs)
All 24 are pure register-coloring with the loop STRUCTURE already correct. Root cause is a single scratch tie-break: the `desc->height` temp lands in r2 (baserom: r0), and the two `ldrsh` zero-index regs land in r2/r0 (baserom: r7). Because the height byte transits r2, r2 is "recently used" and the dst-base immediate `movs r2,#128; lsls #18` instead picks r7 -> dst=r7 (baserom r2) -> src=r2 (baserom r1) -> col=r1 (baserom r3). One upstream tie-break cascades through four registers. Both candidate free regs (r0 and r2) are equally available at the height read; agbcc's global allocator just orders them differently.

### agbcc pass implicated
tools/agbcc-src/gcc_arm/global.c — `global_alloc`/`find_reg`, priority from `allocno_compare` (n_refs/live_length, lines ~210-700). The height-temp and ldrsh-zero are short-lived pseudos whose hard-reg pick is decided by allocno processing order; `find_reg` takes the first free reg in the preferred class. No C-level construct I found reorders that tie-break without side effects.

### Levers tried that did NOT close it (so the next agent skips them)
- Pinning dst asm("r2") and/or src asm("r1"): balloons to 248 bytes (the pin reserves the reg across the dst-select, forcing the EWRAM base into the pool + reload, and drops the r7 push). REVERTED both.
- Pinning col asm("r3"): byte_diff 26->24 but breaks the prologue push (loses r7) and turns the inner loop count-up into a `cmp r5,#0; beq` count-down form. Net structurally worse. REVERTED.
- -ffixed-r2 / -ffixed-r7: both far too blunt (those regs are needed throughout); 235-238 byte_diff. -fno-cse-follow-jumps / -fno-rerun-cse-after-loop / -frerun-loop-opt / -fno-force-mem: all no-change at 26. -fno-schedule-insns/-insns2: agbcc errors (unsupported).
- Reordering: height-before-width (29), flags-first (39), src=ptr[1]-earlier (39), rowBase-narrow-between-reads (46), rowBase+colBase*stride order (26 no-change). Unpinning ptr/row/nextRow/stride: all regress hard (25-225). The current pin set (rowBase r8, colBase ip, width r5, height r9, ptr/bank r6, flags r3, stride r1, row r0, nextRow r4, loop-grid ip) is the correct, minimal one.
