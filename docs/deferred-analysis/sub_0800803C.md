## What the function does (semantics fully reversed — solid)

`u8 sub_0800803C(s16 x, s16 y, s16 targetX, s16 targetY)` — steps
`gIwram_3720._field_2` (X sub-coord) and `._field_4` (Y sub-coord) toward
(targetX, targetY), at most 4 units per axis per call (clamped to the
remaining distance: 1, 2, 3, else 4). Returns 1 iff BOTH axes equal the
target after this call (compared as 16-bit), else 0.

Four independent `if` blocks in order:
  block1  if (x > targetX): switch((s16)(x-targetX)) { 1: f2-=1; 2: f2-=2;
          3: f2-=3; default: reload &gIwram_3720; f2-=4; }
  block2  if (x < targetX): switch((s16)(targetX-x)) { ... f2+=1..4 }
  block3  if (y > targetY): switch((s16)(y-targetY)) { ... f4-=1..4 }
  block4  if (y < targetY): switch((s16)(targetY-y)) { ... f4+=1..4 }
  tail    dy=f4; dx=f2; if (dx != targetX) return 0; if (dy == targetY) return 1; return 0;

## BREAKTHROUGH (round 17): byte_diff 36 with CLEAN PURE C, NO PIN

The prior near-match (byte_diff 249) was poisoned by a
`register struct IwramAt3720 *p asm("r5")` PIN. **Removing the pin and
accessing the global DIRECTLY** (`gIwram_3720._field_2`, no pointer local)
collapses the diff from 249 to **36**, and makes the remaining diff a
PERFECTLY UNIFORM 4-register rotation — every instruction is byte-identical
to the baserom except for a consistent register renaming.

The pin is actively HARMFUL: it forces the `&gIwram_3720` pool-load to be
scheduled EARLY in the prologue (because the pinned r5 is defined at its
source position), which shifts the zext register allocation. The baserom
loads the pool literal LAST in the prologue (after all three zexts) — which
only happens with the UNPINNED, direct-global structure.

The block1-default reload (`ldr r0,[pc]; ...; adds r5,r0,#0` — two separate
pool materializations of the same address) reproduces FOR FREE with direct
global access (no pointer local). An explicit `struct IwramAt3720 *p =
&gIwram_3720;` local does NOT reload (CSE folds it to one range → byte_diff
247, wrong). Direct-global is mandatory.

## The remaining diff: a uniform 4-register rotation (ROOT CAUSE, fully diagnosed)

Best-effort C (the byte_diff-36 base, below) assigns:
    BUILT:   ptr->r4, x->r5, targetY->r6, y->r7
    TARGET:  y->r4,   ptr->r5, x->r6,     targetY->r7
Every other byte matches. It is purely WHICH callee-saved register each of
the four long-lived quantities {zext(y), zext(x), zext(targetY), pointer}
gets.

### Why (proven by instrumenting agbcc's global allocator)

old_agbcc is built from `tools/agbcc-src/gcc/` with `-DOLD_COMPILER` (NOT
`gcc_arm/`). Its `global.c:allocno_compare` orders quantities by
`floor_log2(n_refs) * n_refs / live_length * size` (higher = allocated
first), tiebreak by allocno number. NO CYGNUS live-range term (that's only
in `gcc_arm/`). `find_reg` then assigns the lowest free callee-saved reg
(r4, then r5, ...).

Instrumented integer priorities (×10000) for the four quantities in the
byte_diff-36 base:
    pointer:  refs=40, len=4416, PRI=452   -> wins r4 (allocated 1st)
    zext(x):  refs=2,  len=48,   PRI=416   -> r5
    zext(tY): refs=2,  len=79,   PRI=253   -> r6
    zext(y):  refs=2,  len=81,   PRI=246   -> r7  (allocated LAST)
NO copy-preferences exist (`hard_reg_copy_preferences[]` empty for all four
— verified by a second instrumentation print). Allocation is PURE priority.

For the baserom's order (y > ptr > x > tY), **zext(y) must have the HIGHEST
priority (>452)**, i.e. it needs ~4 references (with len 81:
floor_log2(4)*4/81*10000 = 987 > 452; floor_log2(3)*3 = 3 is too few). But
in BOTH the baserom asm AND every C structure tried, zext(y) is referenced
exactly TWICE (born at prologue 0x8042, read once at block3 0x80de; block4
0x811e REUSES block3's `y<<16` shift via `asrs r1,r1,#16`). x is the same
(2 refs) but dies earlier (block2 vs block4), so x out-prioritizes y. The
baserom's allocation is therefore NOT reproducible by reference-count
priority alone with this compiler — the original source must have given
zext(y) more references (or a copy-preference) than the natural 4-if shape
produces, which no semantically-equivalent C structure recreates (the asm
fixes the block3/block4 shared sign-extension).
