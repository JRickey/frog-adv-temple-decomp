# sub_08013FD0 — Deferred Analysis

## Range
`[0x08013fd0, 0x08014020)` — 80 bytes, Thumb, in `asm/disasm_0x08013fd0.s`.
Destination: `src/engine/sub_08013fa0.c`.

## Function Summary
Calls `sub_08013C60` twice with data from two 16-byte entries in a ROM struct at
`0x08307518`, then calls `sub_08010A44(6, 2)` and `sub_08017000()`.

## Drift

**byte_diff: 31** out of 80 bytes. **diff_count: 18** instructions (see compile_and_view_assembly output).

The issue is **instruction ordering in argument setup**. The function sets up two
6-argument calls to `sub_08013C60(u32 a, u32 b, u32 c, u32 d, u8 mode, void *buf)`.

The **baserom** generates this sequence for each call:
1. `ldrb r0, [r4, #2]` → byte (5th arg) to r0  
2. `str r0, [sp, #0]`  → byte to sp[0]  
3. `ldr r0, [pc, #N]`  → IWRAM ptr (6th arg) to r0  
4. `str r0, [sp, #4]`  → IWRAM ptr to sp[4]  
5. `ldr r0, [r4, #0]`  → word0 (1st arg)  
6. `ldr r1, [r4, #4]`  → word4 (2nd arg)  
7. `ldr r2, [r4, #8]`  → word8 (3rd arg)  
8. `ldr r3, [r4, #c]`  → wordC (4th arg)  
9. `bl sub_08013C60`

Our code (with `register struct DmaDesc *desc asm("r4")` pin) generates:
1. `ldr r1, [r4, #4]`   (word4 first)
2. `ldr r2, [r4, #8]`
3. `ldr r3, [r4, #c]`
4. `ldrb r0, [r4, #2]`  (byte last among args needing registers)
5. `str r0, [sp]`
6. `ldr r0, .L7+4`       (IWRAM ptr)
7. `str r0, [sp, #4]`
8. `ldr r0, [r4]`        (word0)
9. `bl sub_08013C60`

**Root cause**: agbcc evaluates arguments left-to-right, loading r1-r3 for args 2-4 before
using r0 as scratch for the 5th (byte) and 6th (ptr) stack args. The baserom sequence
requires the 5th and 6th args to be set up BEFORE args 2-4, which is reverse of agbcc's
natural evaluation order.

The second call additionally uses `ldrb r4` (not `ldrb r0`) for the byte in our code,
because r4 (struct ptr) becomes available after the word loads.

## What to Try Next

The key insight: the baserom evaluates the **5th arg (byte) BEFORE args 2-4 (r1-r3)**.
This requires agbcc to set up stack args before register args.

1. Try a different calling convention: what if the 5th arg is actually a REGISTER arg 
   and word0 goes on the stack? Rearrange: `sub_08013C60(byte, word4, word8, wordC, word0, IWRAM)`
   — but verify against the callee's actual register usage in the body.
2. Try reading agbcc's ARM call-emission code in `tools/agbcc-src/gcc_arm/arm.c` 
   (function `arm_function_arg`, `output_move_fpa_in`, or wherever stack args are
   emitted) to understand when it emits stack arg stores vs register loads.
3. Try a struct where the byte field is at offset 0 (C perspective) and the word at
   offset 0 is accessed via a u32 cast — see if a different field ordering changes
   agbcc's argument evaluation priority.
