# Deferred analysis: sub_080070A0

**Range:** 0x080070a0 – 0x08007138 (152 bytes, Thumb, OLD_AGBCC TU)
**TU:** src/game/sub_08006b88.c (OLD_AGBCC)
**Struct stride:** 36-byte (0x24) entries, accessed at offsets 0,2,12,16,17,18,26

## Drift

Best byte_diff achieved: ~116/152 bytes (with r8/r9 register pins, 152-byte output).
diff_count: ~49 instruction-level mismatches (argument-register mismatches only; no size difference).

The function generates the CORRECT SIZE (152 bytes) with `register GameStuff *pGS asm("r8")` and
`register s32 mask asm("r9")` pins. But the register assignments inside the function body are wrong.

### Root cause: pool load register selection

The target loads the gGameStuff pool literal into **r2** (not r1):
```
adds r3, r1, #0    ; first → r3 (r1 freed)
adds r6, r2, #0    ; last → r6 (r2 freed — MOST RECENTLY freed)
ldr r2, [pc, #124] ; r2 = &gGameStuff (r2 chosen as most-recently-freed)
ldr r0, [r2, #0]   ; r0 = gGameStuff._unk00
...
mov r8, r2         ; r8 = &gGameStuff (LATE PIN after initial use)
```

Every variant tried (16+ in total) generates `ldr r1, [pc, N]` (pool → r1) instead.
The ordering `adds r3, r1, #0; adds r6, r2, #0` (first before last) IS reproduced correctly
in several variants, but old_agbcc still prefers r1 over r2 for the pool load.

### What was tried (this round, on top of the 14 variants in prior analysis)

1. **Pure gGameStuff macro + r9 pin**: r9=2 correct but no r8 save, gGameStuff reloaded each iter.
   Generated 132 bytes (too small, missing r8/r9 save). byte_diff=130.

2. **pGS=r8 pin, early assignment (pGS = &gGameStuff before entry0)**:
   Generates `ldr r1, .L35; ldr r2, [r1]; mov r8, r1` — r1 as pool intermediate.
   152 bytes, byte_diff=128.

3. **pGSTmp intermediate + r8 pin (tick first, pGS second)**:
   `pGSTmp = &gGameStuff; tick = pGSTmp->_unk00; pGS = pGSTmp`
   Generates `ldr r1, .L35; ldr r2, [r1]; mov r8, r1` (still r1!).
   Order `add r3,r1,#0; add r6,r2,#0` is CORRECT but pool still goes to r1.
   152 bytes, byte_diff=116.

4. **r3=first pin + r8=pGS pin + r9=mask pin**:
   Generates `add r6,r2,#0; add r3,r1,#0` (REVERSED — last before first!).
   Pool still uses r1. Extra cmp/bgt generated.

5. **No entry0 variable, access entries+first directly**:
   `add r3,r1,#0; add r6,r2,#0` order correct.
   Pool still uses r1 (not r2). 152 bytes, byte_diff=116.

### Why r1 is chosen over r2

Old_agbcc's register allocator selects r1 for the gGameStuff pool load even when:
- r2 was freed by `adds r6,r2,#0`
- r1 was freed by `adds r3,r1,#0`
- Both are free simultaneously before the pool load

The heuristic seems to be: old_agbcc uses r1 because it was the register that held `first` (arg1),
and the pool load for gGameStuff "inherits" the r1 register slot from the freed `first` argument.
The target's selection of r2 might be driven by a specific evaluation order in old_agbcc's RTL
(Register Transfer Language) that sees the gGameStuff macro as coming right after the `last`
argument is saved — placing the pool load in r2's "slot".

## Opus attempt (round 1)

**Best byte_diff achieved this round: 65** (down from the prior round's 116) —
a real improvement, but still register-coloring-only and not closable by source.

### Key breakthrough vs prior round: stop pinning pGS to r8

The decisive new finding: with **only `mask` pinned to r9** (pGS left a plain
`GameStuff *` local), old_agbcc spills `&gGameStuff` to a high reg *on its own*
because `gIwram_3720` writes and `e->stamp = pGS->_unk00` keep it loop-live.
This drops byte_diff from 116 → 69 immediately. Pinning pGS to r8 explicitly
(prior round's approach) is actively counterproductive: it forces an early
`mov r8, r1` + `mov r0, r8; ldr r0, [r0]` reload (2 extra moves) where the
target keeps the pool in scratch r2 and does the r8 save *late*
(`mov r8, r2` after the `subs`).

Best clean variant (for-loop, 152 bytes, byte_diff 69):
```c
void sub_080070A0(struct MoveEntry *entries, s32 first, s32 last)
{
    register s32 mask asm("r9");
    GameStuff *pGS;
    struct MoveEntry *e;
    s32 i;
    u16 active;

    pGS = &gGameStuff;          /* MUST be first stmt — gets the high-reg spill */
    e = &entries[first];

    if (pGS->_unk00 - e->stamp < (u32)e->ageMax)
        return;
    if (first > last)
        return;

    mask = 2;
    active = gIwram_35E0._field_10 & mask;

        s8 dy = e->deltaY;

        e->subY += dy;
        if (active != 0 && (e->flags & mask) != 0) {
            gIwram_3720._field_2 += dx;
            gIwram_3720._field_4 += dy;

        e->stamp = pGS->_unk00;
    }
}
```
(`do { … } while (i <= last)` shaves it to **65** but mangles the
`cmp r4,r6; bgt` pre-loop guard the target has, so the for-loop form is the
right base to permute from.)

### The THREE coupled register-allocation differences that remain

The instruction *sequence* is byte-exact; only register *names* differ, in
three coupled ways. None flip via source restructuring:

1. **`&gGameStuff` → ip, `active` → r8** (built) vs **`&gGameStuff` → r8,
   `active` → ip** (target). Both r8 and r9 are pushed either way (the
   prologue saves the r8/r9 pair because mask=r9), so r8 is "already paid for"
   — the target uses it for the longer-lived pointer; old_agbcc here prefers
   the caller-saved ip for the first long-lived value and shoves `active`
   into r8. **Pinning `pGS asm("r8")` does NOT override this** — verified:
   old_agbcc still emits `mov ip, r1` for the pointer and `mov r8, r0` for
   active, ignoring the pin (likely because the `= &gGameStuff` init creates a
   distinct pseudo it colours freely).

2. **`first` → r4 (built, merged with loop counter `i`)** vs **`first` → r3,
   copied `adds r4, r3, #0` to r4 for `i` (target)**. The target keeps `first`
   and `i` in *distinct* low regs even though `first` is dead after the copy;
   old_agbcc merges them into r4. This cascades entry0 from r5 (target) → r3
   (built) and the gIwram_3720 base from r5 (target) → r4 (built), accounting
   for ~10 of the 34 instruction diffs.

3. **deltaX (offset 17) signed read: `ldrb [r3,#17]` + `lsls/asrs` sign-extend
   (built)** vs **`movs r0,#17; ldrsb [r3,r0]` register-offset (target)**. The
   target uses register-offset `ldrsb` for BOTH delta reads; old_agbcc uses
   the immediate `ldrb`+shift form for the first and register-offset `ldrsb`
   only for the second. Read-order swap (dy-first) does not change this.

### The exact asm idiom that diverges
Three coupled register-coloring differences (instruction *sequence* is byte-exact; only register *names* differ):
1. **High-reg coloring swap.** Target: the long-lived `&gGameStuff` pointer → **r8** (saved LATE via `mov r8, r2` at 0x70bc, after the pool is first used as scratch r2), and the loop-invariant flag `active = gIwram_35E0._field_10 & 2` → **ip** (`mov ip, r0` at 0x70da). agbcc (both old_agbcc AND newer agbcc) does the **reverse**: pGS → ip (`mov ip, r1`), active → r8 (`mov r8, r0`). mask (constant 2) → r9 in both (correct).
2. **`first` kept distinct from loop counter `i`.** Target keeps `first` in r3 across the entry0 computation, then copies `adds r4, r3, #0` to a separate counter r4; this cascades entry0 → r5 (target) vs r3 (built) and the gIwram_3720 base → r5 (target) vs r4 (built). agbcc merges `first` and `i` into one reg (r4).
3. **Register-offset `ldrsb` for both delta reads.** Target: `movs r0,#17; ldrsb r0,[r3,r0]` for deltaX AND `movs r2,#16; ldrsb r2,[r3,r2]` for deltaY (ldrsb count = 2). agbcc emits immediate `ldrb r0,[r3,#17]` + `lsls/asrs` sign-extend for deltaX and reg-offset ldrsb only for deltaY (ldrsb count = 1).

### Why the trick does NOT transfer
The corpus searches prove the *shape* (pointer→r8, flag→ip) is reachable, but ONLY in functions with calls. In a **call-free** leaf, agbcc's `global.c` allocator assigns by allocno priority `floor_log2(n_refs)*n_refs / live_length * size` (allocno_compare), and `REG_ALLOC_ORDER` = `{3,2,1,0,12(ip),14(lr),4,5,6,7,8(r8),10,9(r9),...}` — i.e. caller-saved ip(12) is preferred OVER callee-saved r8. The `.greg` dump (obtained with `old_agbcc -dg`) shows pGS = pseudo 79, **9 refs / live_length 62** (priority ~0.44) and active = pseudo 29, **3 refs / 33** (priority ~0.09). pGS has the HIGHER priority, so it is allocated first and grabs the earlier-in-order ip; active falls to r8 (`Register 29 now in 8`). The target has these swapped, meaning in the target build active out-prioritised pGS — but nothing I could write raised active's refs/shortened its range above pGS's without breaking the function (pGS is genuinely dereferenced every iteration for `e->stamp = pGS->_unk00`, giving it the high ref count).

### agbcc pass implicated
`tools/agbcc-src/gcc_arm/global.c` — `allocno_compare()` (the priority formula, ~line 654-680) + `find_reg()` (`accept_call_clobbered`/`allocno_calls_crossed==0` path makes caller-saved regs freely available) + `REG_ALLOC_ORDER` in `config/arm/arm.h:833` (ip before r8). This is register *coloring/ordering*, not a fold (cse/gcse/combine) and not loop-reversal (loop.c). decomp-permuter (per the doc, ~1500 iters, base 2710 → 2370, never near 0) cannot move it because it perturbs statement order/scope, not the allocno priority of a structurally-forced pointer.

### RECOMMENDED NEXT ANGLE
The mechanism is now pinned to `allocno_compare`'s priority of the pGS pointer pseudo vs the active flag pseudo. Two untried, mechanism-targeted angles:
1. **RTL liveness inspection of the TARGET-shaped allocation, not the function-source.** The target's `mov r8, r2` is LATE and the pool sits in scratch r2 across the entire entry0 computation — this strongly implies the pGS *pointer* pseudo and the *tick-read* pseudo are SEPARATE in the target (pool→r2 is one short pseudo used for `ldr r0,[r2]`; the r8 pseudo only begins at `mov r8, r2`). If pGS's loop pseudo could be split from the initial tick read so its ref count drops below active's (3), priority would flip and it would land in r8 naturally. CSE merges the two `(GameStuff*)0x03005330` accesses (variant K confirmed this), so the split needs a CSE-defeating shape: e.g. read the initial tick through a *genuinely different* expression than the loop pointer (a volatile-qualified read, or a helper that returns the tick, or the gGameStuff macro for the first read + a distinct pointer local for the loop) such that agbcc does not coalesce them. This is the most promising lever and was only partially explored.
2. **An isolated own-TU file (already validated to reproduce 69) plus a `-fcaller-saves`/`-fno-caller-saves` or a `-fcse-skip-blocks` variant**, or trying the `arm_010110a.h` / `arm_990720.h` config-era agbcc snapshot if any is installed — the REG_ALLOC_ORDER is identical across the arm.h snapshots checked, but an allocno_compare tie-break difference in a different agbcc build could flip it. Do NOT re-derive the C structure (settled at the byte_diff-69 for-loop) or re-run permuter (proven exhausted). Keep the function as its asm slice until the split-pseudo angle (1) is tried.
