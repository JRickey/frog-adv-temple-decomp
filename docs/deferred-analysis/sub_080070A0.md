# Deferred analysis: sub_080070A0

**Range:** 0x080070a0 – 0x08007138 (152 bytes, Thumb, OLD_AGBCC TU)
**TU:** src/game/sub_08006b88.c (OLD_AGBCC)
**Struct stride:** 36-byte (0x24) entries, accessed at offsets 0,2,12,16,17,18,26

## Drift

Best byte_diff achieved: ~116/152 bytes (with r8/r9 register pins, 152-byte output).
diff_count: ~49 instruction-level mismatches (argument-register mismatches only; no size difference).

The function generates the CORRECT SIZE (152 bytes) with `register GameStuff *pGS asm("r8")` and
`register s32 mask asm("r9")` pins. But the register assignments inside the function body are wrong.

### Root cause: pool load register selection

The target loads the gGameStuff pool literal into **r2** (not r1):
```
adds r3, r1, #0    ; first → r3 (r1 freed)
adds r6, r2, #0    ; last → r6 (r2 freed — MOST RECENTLY freed)
ldr r2, [pc, #124] ; r2 = &gGameStuff (r2 chosen as most-recently-freed)
ldr r0, [r2, #0]   ; r0 = gGameStuff._unk00
...
mov r8, r2         ; r8 = &gGameStuff (LATE PIN after initial use)
```

Every variant tried (16+ in total) generates `ldr r1, [pc, N]` (pool → r1) instead.
The ordering `adds r3, r1, #0; adds r6, r2, #0` (first before last) IS reproduced correctly
in several variants, but old_agbcc still prefers r1 over r2 for the pool load.

### What was tried (this round, on top of the 14 variants in prior analysis)

1. **Pure gGameStuff macro + r9 pin**: r9=2 correct but no r8 save, gGameStuff reloaded each iter.
   Generated 132 bytes (too small, missing r8/r9 save). byte_diff=130.

2. **pGS=r8 pin, early assignment (pGS = &gGameStuff before entry0)**:
   Generates `ldr r1, .L35; ldr r2, [r1]; mov r8, r1` — r1 as pool intermediate.
   152 bytes, byte_diff=128.

3. **pGSTmp intermediate + r8 pin (tick first, pGS second)**:
   `pGSTmp = &gGameStuff; tick = pGSTmp->_unk00; pGS = pGSTmp`
   Generates `ldr r1, .L35; ldr r2, [r1]; mov r8, r1` (still r1!).
   Order `add r3,r1,#0; add r6,r2,#0` is CORRECT but pool still goes to r1.
   152 bytes, byte_diff=116.

4. **r3=first pin + r8=pGS pin + r9=mask pin**:
   Generates `add r6,r2,#0; add r3,r1,#0` (REVERSED — last before first!).
   Pool still uses r1. Extra cmp/bgt generated.

5. **No entry0 variable, access entries+first directly**:
   `add r3,r1,#0; add r6,r2,#0` order correct.
   Pool still uses r1 (not r2). 152 bytes, byte_diff=116.

### Why r1 is chosen over r2

Old_agbcc's register allocator selects r1 for the gGameStuff pool load even when:
- r2 was freed by `adds r6,r2,#0`
- r1 was freed by `adds r3,r1,#0`
- Both are free simultaneously before the pool load

The heuristic seems to be: old_agbcc uses r1 because it was the register that held `first` (arg1),
and the pool load for gGameStuff "inherits" the r1 register slot from the freed `first` argument.
The target's selection of r2 might be driven by a specific evaluation order in old_agbcc's RTL
(Register Transfer Language) that sees the gGameStuff macro as coming right after the `last`
argument is saved — placing the pool load in r2's "slot".

### Next attempt hints

- The crux: find a C construct that causes old_agbcc to load the gGameStuff pool literal
  into r2 (not r1). Possible approaches:
  1. **`-ffixed-r1` per-TU override**: Add `src/game/sub_08006b88.s: CFLAGS += -ffixed-r1`
     to Makefile. This prevents old_agbcc from using r1 as a scratch register, forcing the
     pool load to r2. Caveat: it might break other functions in the TU.
  2. **Isolate the function to its own TU**: Move sub_080070A0 to a new
     src/game/sub_080070a0.c file with a new per-TU OLD_AGBCC override. Then the register
     allocator starts fresh without other functions' interference.
  3. **Exploit the `tick = gGameStuff._unk00` + pool order**: When tick is first AND the
     function has only r8/r9 as explicitly pinned (no r3 pin), old_agbcc generates the
     correct first/last order (r3,r6) and uses r1 for the pool. The MISSING piece is why
     the target uses r2. This may require inspecting old_agbcc's RTL output (`-da` flag
     or similar) to understand when it selects r2.
  4. **Linker-assigned symbol for gGameStuff**: Replace `#define gGameStuff (*(GameStuff*)0x03005330)`
     with an extern symbol like `gGameStuff` (similar to the IWRAM extern pattern). This
     changes how old_agbcc handles the pool literal and might affect register allocation.
     BUT: this would change ALL uses of gGameStuff across the project and is a large change.

## Best-effort C

The best working C (152 bytes, byte_diff=116, purely argument-register mismatches):

```c
struct MoveEntry {
    s16 subX;   /* +0 */
    s16 subY;   /* +2 */
    u8 _pad04[8];
    u32 stamp;   /* +12 */
    s8 deltaX;   /* +16 */
    s8 deltaY;   /* +17 */
    u8 ageMax;   /* +18 */
    u8 _pad13[7];
    u8 flags; /* +26 */
    u8 _pad1b[9];
};

void sub_080070A0(struct MoveEntry *entries, s32 first, s32 last)
{
    register GameStuff *pGS asm("r8");
    register s32 mask asm("r9");
    GameStuff *pGSTmp;
    struct MoveEntry *entry0;
    u32 tick;
    u16 ip;
    struct MoveEntry *e;
    s32 i;

    pGSTmp = &gGameStuff;
    tick = pGSTmp->_unk00;
    pGS = pGSTmp;
    entry0 = entries + first;

    if (tick - entry0->stamp < (u32)entry0->ageMax)
        return;
    if (first > last)
        return;

    mask = 2;
    ip = gIwram_35E0._field_10 & mask;
    e = entry0;

    for (i = first; i <= last; i++, e++) {
        s8 dx = e->deltaX;
        s8 dy = e->deltaY;

        e->subX += dx;
        e->subY += dy;

        if (ip != 0 && (e->flags & mask) != 0) {
            gIwram_3720._field_2 += dx;
            gIwram_3720._field_4 += dy;
        }

        e->stamp = pGS->_unk00;
    }
}
```
