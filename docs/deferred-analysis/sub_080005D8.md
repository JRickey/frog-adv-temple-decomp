## sub_080005D8 — deferred analysis

Function at 0x080005D8, 160 bytes. dest: src/system/init1.c. Classifier: ATTEMPT_MATCH.

### Function semantics

A per-frame input handler (similar to sub_080004C4) that:
1. Reads REG_KEYINPUT, inverts to active-high `raw`
2. Computes jpKeys = raw & ~gIwram_3710.prevKeys
3. Stores jpKeys to gIwram_5358.justPressed
4. Maps only KEY_A and KEY_B (not the full 10-key remap of sub_080004C4):
   - If prevKeys did NOT have KEY_A set: mapped = (jpKeys & KEY_A) ? KEY_RIGHT : 0
   - If prevKeys did NOT have KEY_B set AND jpKeys & KEY_B: mapped = KEY_LEFT
5. Updates gIwram_3710.prevKeys = raw
6. Same mode-24 attract-loop logic as sub_080004C4

### Drift

Best byte_diff achieved: **45 bytes** (with `register u16 prevKeys asm("r3")` pin).

The target has this exact register layout:
- r4 = `mapped` (callee-saved, initialized `movs r4, #0`)
- r5 = KEY_A constant (1) (callee-saved, `movs r5, #1`)
- r6 = `raw` (callee-saved, from `lsrs r6, r0, #16`)
- r7 = `prev` pointer (callee-saved, saved from r1 via `adds r7, r1, #0`)

The compiled output has r4 and r5 swapped (r4=KEY_A, r5=mapped) AND prev goes directly to r7
instead of going through r1 first. This causes:
- `ldr r7, [pc, #N]` instead of `ldr r1, [pc, #N]` (prev load)
- `ldrh r3, [r7, #0]` instead of `ldrh r3, [r1, #0]` (prevKeys load)
- `adds r1, r6, #0; bics r1, r3` instead of `adds r2, r6, #0; bics r2, r3` (jpKeys)
- Extra `adds r2, r1, #0` copy to preserve jpKeys for KEY_B check
- `asrs r5, r1, #31; ands r5, r0` instead of `asrs r4, r1, #31; ands r4, r0` (ternary)
- Missing `adds r7, r1, #0` save-to-r7 instruction

The cascade root cause: `prev` gets directly allocated to r7 (callee-saved) from the start,
rather than temporarily living in r1 (caller-saved) and being moved to r7 when r1 is needed
for the KEY_B constant (movs r1, #2).

### Levers tried (in order)

1. **Baseline** (no pins): 48 bytes. r4=KEY_A, r5=mapped, r7=prev.
2. **register prevKeys asm("r3")**: 45 bytes (best). Fixes prevKeys register; does not fix prev/mapped.
3. **register mapped asm("r4") + register prevKeys asm("r3")**: 116 bytes (worse). Push changes to {r4,r5,r6,lr}; ternary generates branches instead of negs/orrs/asrs.
4. **register jp asm("r0") + register prev asm("r1")**: 137 bytes (worse). Prev in r1 but other issues.
5. **jpKeysShadow + prevKeys=r3**: 83 bytes (worse). Push changes to {r4,r5,r6,lr}; raw goes to r5.
6. **prevOld local (cache prevKeys before pointer)**: 76 bytes.
7. **Without named prev pointer**: 135 bytes.
8. **Various variable declaration orderings**: no improvement.

### Next lever to try

The remaining 45-byte gap is entirely about whether `prev` goes through r1 (temp)
before being saved to r7, or directly to r7. The `adds r7, r1, #0` instruction in the
target is the two-step load. The pattern to look for in corpus: agbcc generating
`ldr r1, =ptr; [uses r1]; adds r7, r1, #0; movs r1, #N` for a pointer variable.

Try: replacing `struct IwramAt3710 *prev` with a separate `struct IwramAt3710 *prev2`
that is ONLY used for the final `prev2->prevKeys = raw` store, and using `&gIwram_3710`
inline for the reads (forcing separate load each time). Also try expressing jpKeys as
`(u16)(raw) & ~(u16)(gIwram_3710.prevKeys)` without prev pointer at all, then using
a separate pointer only for the write. May help agbcc see that the pointer doesn't
need to survive the key-mapping region.

### KEY CORRECTION: prior permuter runs used the WRONG compiler

`src/system/init1.s` is compiled with **old_agbcc** (Makefile line ~111), NOT the
default agbcc. `tools/permuter_compile.sh` hardcodes `tools/agbcc/bin/agbcc` (the new
one). So the deferred analysis's "permuter base score 295 / best 245" was scored against
the wrong toolchain and is **not valid** for this function. Any future permuter run on
init1.c functions MUST swap in an old_agbcc compile wrapper (see below).

I re-ran the permuter correctly (old_agbcc wrapper, target.o == baserom bytes,
fully-preprocessed base.c so pycparser/bare-`cpp` parse it). ~3150 iters, -j4,
`--stop-on-zero --best-only`. Result: base score 9930 → best **4200**, **no score-0**.
The 4200 output reaches byte_diff **4** but is INVALID C: the permuter inserted a dead
top-level `return 0;` (UB — makes the whole function a no-op) and emptied the
`(now - lastTick) <= 10` branch (dropping its `return 0;`). Both mutations shrink the
instruction stream artificially. With valid semantics restored the diff is back to 45.
This is the same UB-dependent dead end the prior run hit, now confirmed on the correct
compiler — so the permuter genuinely cannot close this base.

Wrapper used (for the next agent — drop into a `/tmp` script, point the scratch

### Root cause, fully mapped (the ENTIRE 45-byte gap is one coupled cascade)

Confirmed via per-halfword diff that the only real body diffs (0x58-0x5e are just
unresolved pool literals in the standalone slice) all flow from a single agbcc
allocation decision: **does `prev` (&gIwram_3710) live in caller-saved r1 during the
read phase and promote to callee-saved r7 (`adds r7, r1, #0`) for the late store, or
go straight to r7?**

- Target: prev in r1 → (a) the `raw & ~prevKeys` temp can't use r1, lands directly in
  r2 (jpKeys, NO copy), AND (b) the `movs #1` KEY_A const can't use r1, so it's kept in
  callee-saved r5 — giving 4 callee regs r4=mapped, r5=const, r6=raw, r7=prev(promoted).
- Our build: prev straight to r7 → r1 free during compute → jpKeys lands in r1 then needs
  a copy to r2 (the extra `adds r2, r1, #0`), const goes to caller-saved r1 path /
  callee r4, mapped to r5. The r4↔r5 swap and the jpKeys copy are SYMPTOMS, not
  independent issues — all driven by prev's register.

### Levers tried this session (all regressed or stayed at 45)

- `register prev asm("r1")` ALONE: 51. Forces prev to r1 *permanently* (no promote) →
  raw displaced to r7, jpKeys copied to r4. The pin can't express "r1 early, r7 late".
- `register prev asm("r1")` + `register mapped asm("r4")`: 109, BUT the prologue through
  0x22 is **byte-perfect** (raw=r6, mapped=r4, prev=r1, jpKeys=r2 no-copy, const=r5).
  Fails only because pinning `mapped` flips the branchless `negs/orrs/asrs` ternary into
  a `cmp/beq/movs` branch. Closest prologue achieved — the ternary lowering is the
  blocker on this path.
- `register jpKeys asm("r2")` ALONE: 64. Gets mapped=r4 + jpKeys=r2 (no copy) right, but
  freeing the copy lets the const go caller-saved → drops to 3 callee regs → whole file
  shifts down one (raw=r5, prev=r6).
- `register jpKeys asm("r2")` + `register keyA asm("r5")`: 72. The keyA pin is IGNORED —
  agbcc rematerializes the small const (`movs r1,#1`) rather than honoring a callee-reg
  pin. Small-constant pins don't stick.
- `register raw asm("r6")`: BREAKS — pinning raw drops the `lsls/lsrs #16` zero-extension
  of `~REG_KEYINPUT`, shrinking the function (len 156). Never pin `raw`.
- Two-pointer split (prevRead for reads, inline `gIwram_3710.prevKeys = raw` for write):
  135 — the inline write forces a second pool load.
- Declaration reordering (prev before/after jp; prev declared last): 45-48, no help.
  agbcc allocates by IR live-range order, not declaration order.
- new_var jp-indirection (the legit half of the permuter's 4200 output) on clean C: 48.
  Only helps in combination with the UB `return 0`.

### Firm-defer assessment

This is a true agbcc *global*-allocation tie-break: the C surface offers no knob to say
"caller-saved r1 here, promote to r7 there", a `register asm("r1")` pin is too blunt
(permanent), and the only pin that fixes the prologue (`mapped asm("r4")`) breaks the
ternary lowering. The permuter — now proven to run on the correct old_agbcc — cannot
reach a valid score-0. Recommend leaving as an asm slice (do NOT ship NAKED+NON_MATCHING
yet; it's a clean asm slice today and that's more honest than a NAKED). If revisited:
the `prev asm("r1") + mapped asm("r4")` base is byte-perfect except the ternary — a
targeted fix for agbcc's `?:`-to-branch choice under a pinned destination (or a permuter
pass seeded from THAT base, scoped to the ternary region) is the single most promising
remaining avenue.
