## What the function does (verified)

Outer loop runs 4 iterations: slot index `i` = 0..3 (r9) and hitbox `type`
= 24..27 (r5), both incremented via the s16-wrap idiom; `type` via
`(savedTypeShift + 0x01000000) >> 24`.

Per outer iter:
  - entity slot = `slots + (s16)i * 8`; zero its field4/5/6 (u8) + field0 (u32).
    EntitySlot is an 8-byte record { u32 field0; u8 4,5,6,pad }.
  - inner loop over the type's hitbox points (count = (s8)table[type].count, j
    in r8): for each point call
    `sub_0800CB80(gIwram_35E0._field_18, 0, pt->x, pt->y, table[type].primaryFlags)`
    where pt = points[j] (x ldrsh +0, y ldrsh +2). primaryFlags is a u8
    (`ldrb [+8]`), confirmed from sibling sub_0800A83C's EntityHitboxFlagBytes.
Then two trailing byte-array-clear loops over IWRAM 0x03003610:
  - loop A: gIwram_3610[k] = 1 for k=0..254 (s16 wrap, increment as
    `i=(u16)((s16)i+1)`, NOT the `(i<<16)+0x10000` idiom — that's the form the
    target uses here and matches loop A).
  - loop B (m=0..13): clear [m+42], [m+154], [m*14+1], [m*14+12]
    (m*14 = ((m<<3)-m)<<1).

sEntityHitboxTable = { u32 count; u32 points; u32 flags } at 0x080c0b00 (12 B/entry).

### TWO KEY MECHANISMS DISCOVERED THIS ROUND (keep these — they are load-bearing)

1. **Table pool-load placement (the prior hoist blocker, SOLVED).**
   The target reloads `&sEntityHitboxTable` INTO r1 each outer iter (at the
   pointCount read) and copies to r7 (`adds r7,r1,#0`) — it does NOT hoist the
   pool load out of the outer loop. agbcc hoists it (single `ldr r7,[pc]` before
   the loop) whenever there are TWO references to the `sEntityHitboxTable`
   constant (one for pointCount, one for `table=`): CSE merges them into one
   pre-loop load. **Verified by instrumenting agbcc's loop.c move_movables (the
   probe NEVER fired — it is NOT loop-invariant motion; it is RTL-gen/CSE placing
   the single load before .L3).** FIX: use ONE symbol reference — a local
   `base = sEntityHitboxTable` whose value feeds BOTH the pointCount read AND
   `table = base`. Then the load materializes inside the loop. The 109 base does
   this via `register const EntityHitbox *base asm("r1"); initOffset = typeIndex*12;
   base = sEntityHitboxTable; pointCount = *(s8*)(initOffset + (u32)base);` then
   `table = base;`.

2. **Slots spill (the prior front-mismatch, SOLVED by UNPINNING table).**
   The target SPILLS `slots` to [sp,#4] (`sub sp,#8; str r0,[sp,#4]`, reloaded
   `ldr r2,[sp,#4]` each iter) and keeps r7=table SAVED + loaded in-loop. When
   `table` was pinned `register asm("r7")`, agbcc instead kept `slots` in the
   (pre-loop-free) r7 (`sub sp,#4; adds r7,r0,#0`) and overwrote r7 with table
   in-loop — a 2-byte front shift cascading through the whole function.
   **FIX: DROP the `asm("r7")` pin on `table` (declare it a plain
   `const EntityHitbox *table;`).** Unpinned, agbcc's allocator chooses r7 for
   table AND spills slots — exactly the target. This single change fixed the
   entire front (byte_diff 151 -> ~110). Forcing the spill via `volatile`/`+m`
   barrier instead BREAKS the prologue (drops r7 from the push list).

3. **typeShift barrier (kept).** `asm volatile("" : "+r"(typeShift));` before
   `type = typeShift >> 24` forces `asrs r5,r6,#24` (direct) instead of
   `asrs r6,r6,#24; adds r5,r6,#0` (in-place + copy). Worth ~14 bytes.

### Remaining residual at byte_diff 109 (all register-coloring / CSE, all small)

1. **jShift register r1 vs r2** (0x4c-0x4e): target `mov r2,r8; lsls r3,r2,#24`;
   built `mov r1,r8; lsls r3,r1,#24`. Pure coloring of the `j<<24` scratch.
2. **ldrb-vs-j-wrap scheduling** (0x86-0x90): target wraps j (lsrs/mov/asrs)
   BEFORE the pointCount ldrb; built schedules ldrb first. Instruction-scheduling;
   no schedule-pass knob in old_agbcc.
3. **next: block coloring** (0x96-0xae): identical structure, but the i-shift uses
   r0 in target / r1 in built, and the `(savedTypeShift+0x1000000)>>24` type
   compute uses a scratch r0 in target / computes in-place in r5 in built.
   Tried an explicit `nextTypeShift` scratch local — no change.
4. **loop B base+idx CSE** (0xdc..0x100, the BIGGEST remaining ~8 bytes): target
   keeps `idx` (r2), COPIES it (`adds r0,r2,#0`) for each of [+42]/[+154] and adds
   `base` (r4) LAST; and keeps `stride` (r1) reused for [stride+1]/[stride+12]
   (`adds r1,#12`). agbcc instead CSEs `base+idx` and `base+stride` once, then
   uses immediate `strb [r0,#1]`/`[r0,#12]` — 2 instrs shorter (this is the whole
   8-byte length deficit). Same CSE class the prior notes flagged for the inner
   loop. Tried: `(idx+42)+(u32)base` index-first, `(u32)base+(u32)(idx+42)`,
   `(s32)idx` cast, base barrier inside loop B (made it WORSE, +reload). None
   broke the `base+idx` fold.

    u32 count;
    u32 points;
    u32 flags;

    u32 points;
    u8 primaryFlags;
    u8 _padA[3];

    s16 x;
    s16 y;
} EntityHitboxPoint;

    u32 field0;
    u8 field4;
    u8 field5;
    u8 field6;
    u8 _pad7;
