## What the function does (verified)

Outer loop runs 4 iterations in lockstep: slot index `i` = 0..3 (r9) and
hitbox `type` = 24..27 (r5), both incremented via the `((x<<16)+0x10000)>>16`
s16-wrap idiom and `type = (savedTypeShift + 0x01000000) >> 24`.

Per outer iter:
  - entity slot = `slots + (s16)i * 8`; zero its `field4/5/6` (u8) and
    `field0` (u32). EntitySlot is an 8-byte record { u32 field0; u8 4,5,6,pad }.
  - inner loop over the type's hitbox points (count = `(s8)table[type].count`,
    j in r8): for each point call
    `sub_0800CB80(gIwram_35E0._field_18, 0, pt->x, pt->y, table[type].flags)`
    where `pt = (s16*)(j*4 + table[type].points)` (x at +0, y at +2, both ldrsh).
    typeShift = type<<24 carried in r6, saved to sl for the outer-tail
    `type = (sl + 0x1000000) >> 24` next-type compute.

Then two trailing array-clear loops over the byte array at IWRAM 0x03003610:
  - loop A: `gIwram_3610[k] = 1` for k = 0..254 (s16 wrap).
  - loop B (m = 0..13): clear `gIwram_3610[m+42]`, `[m+154]`, `[m*14+1]`,
    `[m*14+12]` (m*14 emitted as `((m<<3)-m)<<1`).

sEntityHitboxTable layout (from src/engine/sub_0800a83c.c / sub_0800b7b0.c):
`struct EntityHitbox { u32 count; u32 points; u32 flags; }` (12 B/entry).

Best reached: **byte_diff 147, diff_count 97** (down from 264 on first attempt).
The function is STRUCTURALLY CORRECT: the prologue/slot-zeroing top
(0x0..0x32) byte-matches, AND the entire back half (outer-loop tail + both
0x03003610 clear loops, ~0x92..end) byte-matches. ALL residual is in the
inner hitbox loop (≈0x34..0x90) and is register-coloring / local-CSE drift,
NOT wrong logic and (except the flags read) NOT wrong body length.

Specific unresolved tie-breaks (target → built):
  1. table base pool load: target `ldr r1,[pc] @0xb070` then `adds r7,r1,#0`;
     built picks `r3` (`ldr r3,[pc]; adds r7,r3`). typeIndex is correctly in
     r1 (pinned), dead after the `*12`, but agbcc won't reuse r1 for the pool
     — it grabs r3. This r1-vs-r3 choice cascades through the inner body.
  2. jShift (`j<<24`) is scheduled EARLY in the target (`mov r2,r8; lsls r3,
     r2,#24` right after typeIndex) but LATE in the built code.
  3. points addressing: target keeps `offset` (r4) and forms
     `(table+4)+offset` for points (materializing `table+4` via `adds r1,r7,#4`)
     and `offset+table` for flags — it does NOT share `table+offset`. agbcc
     CSE-folds `table+offset` and reads both `[+4]`/`[+8]` from one base
     (shorter body). Writing flags via the bare `sEntityHitboxTable` symbol
     (current best) breaks the CSE but costs an extra pool load → +1 instr,
     shifting the post-`bl` section by 2 bytes.
  4. j-increment (`((j<<16)+0x10000)>>16`) uses a different scratch register
     (target r0/r2, built r3/r4).

#include "types.h"

typedef struct EntityHitbox {
    u32 count;
    u32 points;
    u32 flags;
} EntityHitbox;

typedef struct EntityHitboxPoint {
    s16 x;
    s16 y;
} EntityHitboxPoint;

typedef struct EntitySlot {
    u32 field0;
    u8 field4;
    u8 field5;
    u8 field6;
    u8 _pad7;
} EntitySlot;

extern const EntityHitbox sEntityHitboxTable[];
extern int sub_0800CB80(int xTile, int mode, int x, int y, int flags);

void sub_0800AF50(EntitySlot *slots)
{
    u32 slotsStack;
    register s32 type asm("r5");
    register s32 i asm("r9");
    register s32 j asm("r8");
    register s32 typeShift asm("r6");
    register s32 savedTypeShift asm("sl");

    type = 24;
    i = 0;
    do {
        EntitySlot *slot;
        register s32 typeIndex asm("r1");
        register const EntityHitbox *table asm("r7");

        slot = (EntitySlot *)((u32)(((s32)(i << 16)) >> 13) + slotsStack);
        slot->field4 = 0;
        slot->field5 = 0;
        slot->field6 = 0;

            u32 offset;
            s32 xTile;

            j = (u32)((j << 16) + 0x10000) >> 16;
            pointCount = *(s8 *)((type * sizeof(EntityHitbox)) + (u32)table);
        } while ((s16)j < pointCount);

    next:
        type = (u32)((u32)(savedTypeShift + 0x01000000) >> 24);
        i = (u32)((i << 16) + 0x10000) >> 16;

    i = 0;

        *((u8 *)0x03003610 + (s16)i) = 1;

    } while ((s16)i <= 254);

        idx = (s16)i;

        *((u8 *)0x03003610 + (stride + 12)) = 0;

## Corpus sweep (2026-06-03)

**Outcome: deferred. byte_diff 147 -> 145 (real improvement, not 0). Tree reverted pristine, make check == 0.**

### The exact asm idiom that diverges
All residual is in the inner hitbox loop (offsets ~0x34..0x90 of the function). The function is otherwise byte-identical (prologue/slot-zeroing top and the entire back half — outer tail + both 0x03003610 clear loops — already match). Three intertwined divergences, in order of how the cascade flows:

1. **Pool register r1 vs r3.** Target: `asrs r1,r6,#24` (typeIndex in r1) -> `r0 = typeIndex*12` (consumes r1, r1 now dead) -> `ldr r1,[pc] @0xb070` REUSES r1 for the table base -> `adds r7,r1,#0` copies it to the callee-saved loop reg. agbcc instead grabs r3: `ldr r3,[pc]; adds r7,r3,#0`. Reproduced with the typeIndex pin present AND removed — agbcc's local-alloc/reload simply does not recycle r1 here.

2. **The CSE-fold of `offset + (u32)table`.** This is the killer. The target forms the points address as `offset + (table+4)` (`adds r1,r7,#4; adds r1,r4,r1; ldr r1,[r1,#0]`) and the flags address as `offset + table` (`adds r4,r4,r7; ldrb r1,[r4,#8]`) — TWO bases rooted at r7=table, NO second pool load, NO shared `offset+table`. agbcc reassociates `(table+4)+offset` into `table+offset` and CSEs it with the flags base, emitting one base `r2=offset+table` then `ldr [r2,#4]` (points) and `ldr/ldrb [+8]` (flags). Whenever flags references the `table` variable (r7) this fold fires (byte_diff 219); referencing the bare `sEntityHitboxTable` symbol breaks the fold but costs a second in-loop pool load (`ldr r1,[pc]`), which the target does not have. The target somehow got separate bases AND r7-reuse AND no fold — agbcc (same binary) will not.

3. **Split-shift instruction scheduling.** Target schedules `j<<24` early (`mov r2,r8; lsls r3,r2,#24` right after the xTile load) and the `>>22` late (`lsrs r3,r3,#22` after the points-pointer load), interleaving the points addressing between the two halves of `(j<<24)>>22`. agbcc emits the shift as one contiguous block late. `-fno-schedule-insns`/`-insns2` are rejected by this agbcc build (`old_agbcc: Invalid option`), so this is not directly tunable.

### Every regex searched + hit count
corpus_asm_search.py passes `--asm` raw to BOTH git's `-G` pickaxe (POSIX ERE — `\s` matches nothing) AND the Python re filter. **Use space-literals, not `\s`, or you get false 0-hit sweeps.** This cost the first three queries:
- `ldr +r[0-7], \[pc...\n...adds +r[0-7], r[0-7], #0` (multiline) — **0** (tool is line-based; multiline never matches).
- `ldrsh +r[0-7], \[r[0-7], r[0-7]\]` (register-offset point load) — **6+ (capped)**, all generic (berry_crush, pokenav, pokemon_jump). Too common to be specific.
- `adds +r[0-7], r[0-7], #4` --clean (field-base +4 materialization) — **6+**, generic (mzm hive, fe8u worldmap/bmudisp, tmc). No dual-base-no-CSE shape.

- `idiom=highreg-spread` --require-c — **5** (agb_flash, berry_crush sub_8022F04, dodrio, pokemon_jump). Confirms AF50's r8/r9/sl pins are NOT the funnel/spread class — those already match in AF50's prologue/tail; the residual is pure inner-loop CSE, not high-reg coloring.
- `asrs +r[0-7], r[0-7], #24` (sanity) — **0 with `\s`**, proving the git-ERE flavor bug above.
