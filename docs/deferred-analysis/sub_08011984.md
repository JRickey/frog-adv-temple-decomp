### The keystone: idx must land in ip(r12); agbcc puts it in r8 by a razor-thin margin

The baserom register map: **idx→ip, elems→r9, idx8(=idx<<3)→r8 (spilled to [sp,#12]
at loop entry, reloaded at tail), 60A0-loop-base→r8 (temporal reuse after idx8
spilled), 6480-base→sl (kept head→tail), 6540-base RELOADED each use (not kept).**

My builds consistently produce the SWAP: **idx→r8, 60A0/dst-base→ip.** Everything
else cascades from this one swap.

I built a private instrumented `old_agbcc` (probe in `gcc/global.c` `find_reg`
final-assignment + the `allocno_order` loop, gated on `getenv("AGBCC_DBG")`) and
traced the conflict-graph coloring on THIS function. The decision is
`global.c:allocno_compare`, priority = `floor_log2(refs)*refs / live_length` (×size):

- idx        : refs=4, len=95 → floor_log2(4)*4/95 = 8/95 = **0.0842**
- 60A0/dst   : refs=3, len=34 → floor_log2(3)*3/34 = 3/34 = **0.0882**

The 60A0/dst pseudo wins by 0.004, is allocated FIRST, and (being non-call-crossing)
prefers the cheap caller-saved **ip**. idx is allocated next and falls to r8. In the
baserom the order was reversed (idx won ip), which means the baserom's idx had a
*marginally higher* priority — i.e. idx referenced once more (refs 4→5 makes
8→10, 10/95=0.105 ≫ 0.0882) OR its live range ~6 shorter (len<90.5). Neither is
reachable from clean C: agbcc's CSE folds every attempt to add an idx reference
(`elems[idx+1-idx]`, `(elems+idx)[1]`, etc. all collapse to the existing base),
and idx is genuinely live head→tail (can't shorten without diverging — the baserom
ALSO keeps idx live to the tail). This is the exact "sharp register-coloring local
minimum no single source shape escapes" the CLAUDE.md sub_08017364 caveat names.

### 2026-06-06 Opus round 13 — confirmed the tie, found `-fno-rerun-cse-after-loop` flip

Rebuilt the instrumented `old_agbcc` (probe in `gcc/global.c` assignment loop:
`fprintf` each allocno's `order/pseudo/refs/len/crosscall/-> reg`). Confirmed the
exact tie on THIS function's coloring, on the clean baseline (192) shape:

- pseudo 271 = **60A0-base** : refs=3 len=34 → r12(ip)  [priority 1*3/34 = 0.0882]
- pseudo 23  = **idx**       : refs=4 len=95 → r8       [priority 2*4/95 = 0.0842]
- pseudo 22  = **elems**     : refs=4 len=100 → r9

`global.c:allocno_compare` orders 271 BEFORE idx (0.0882 > 0.0842); 271 grabs the
held-across-loop slot first. `find_reg` then linearly picks the lowest free hard reg
(it does NOT use REG_ALLOC_ORDER — that's only local-alloc). So 271→r12, idx→r8.
To flip, idx priority must exceed 0.0882: refs=5 (→0.105) OR len≤90 OR 271 len≥36
(3/36=0.083<0.0842). The gap is a SINGLE allocno-priority step.

**NEW working lever (best this round): `-fno-rerun-cse-after-loop`.**
Per-TU `src/engine/sub_0801185c.s: CFLAGS += -fno-rerun-cse-after-loop` (already used
by sub_0801a894.s) makes the rerun-CSE pass NOT collapse the dst/60A0 structure, which
changes pseudo 271's CSE shape so **idx (pseudo 23) lands in r12(ip)** and 60A0→r8 —
the baserom map. Direct byte-diff (built .o text vs baserom 0x11984+0x120):

- clean baseline (no flag):            byte_diff 192, fn size 280
- `-fno-rerun-cse-after-loop` ALONE:   **byte_diff 161, fn size 284**  ← best
- flag + any of {-fno-gcse,-fno-cse-follow-jumps,-fno-schedule-insns[2],
  -fno-expensive-optimizations,-fno-strength-reduce}: 191 (all worse)

The flag fixes the idx→ip keystone but introduces TWO new residuals (net 161, still
far from 0):
1. **Frame grows 16→20**: the flag forces ONE extra spill (a value lands at [sp,#0x10]
   in addition to idx8's [sp,#0xc]). baserom frame is 16.
2. **field_18 DSE still fires** (the first `field_18 = 0x02020000` store is dead-store-
   eliminated; fn is 4 bytes short — 284 vs 288). With the flag, idx→ip also pushes a
   NEW r4/r5 swap (6540-base↔next-ptr) and r8/r9 swap (idx8↔elems).

**field_18 DSE — root cause (NEW, definitive).** The baserom keeps BOTH field_18 stores
because the two stores use DIFFERENT base pseudos: first via r1, then `mov sl,r1`
(6480-base relocates to sl) because r1 is REUSED for the 60A0-base load at 0x119f6.
agbcc's flow-insensitive local DSE can't connect the two stores across the
register-reuse copy. In OUR builds the 60A0-base takes a FRESH reg (ip), so the
6480-base never relocates, stays in one pseudo, and DSE fires. So defeating the DSE
requires the 60A0-base to reuse the 6480-base's register — which is exactly the
register-pressure state we can't reach cleanly. Reading field_18 back as the dst base
(exp15) does NOT help: agbcc constant-forwards 0x02020000 then DSEs anyway (218/238).
