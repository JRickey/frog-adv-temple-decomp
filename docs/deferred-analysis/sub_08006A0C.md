# Deferred Analysis: sub_08006A0C

**Function**: sub_08006A0C (0x08006a0c, 104 bytes in ROM)  
**TU**: src/game/sub_08006948.c  
**Compiler**: OLD_AGBCC at -O2, plus `-fno-strength-reduce`

## Summary

A double-cmp pattern function (boolean materialization + fresh ldrh after alias-unsafe store).
The baserom was compiled by a version of old_agbcc with more conservative alias analysis
than the one in our toolchain. Two structural features can't be reproduced:

1. **Boolean materialization** (`cmp r0,#0; beq; movs r0,#1; b; movs r0,#0; cmp r0,#0; beq`)
   — old_agbcc at -O2 (our toolchain) merges the `flag = (expr); if (flag)` pattern into a
   single branch. `-fno-strength-reduce`, `-fno-gcse`, `asm("")` barriers, and ternary forms
   all fail to prevent the merge.

2. **Fresh ldrh after alias store** — `strh r5, [r4, #18]` (storing to _field_12 = key) should
   invalidate the cache of `r1 = [r4, #16]` (_field_10). The baserom old_agbcc does this;
   our old_agbcc keeps r1 cached (it knows offset 16 ≠ offset 18, so it doesn't invalidate).

## Drift

Best byte_diff: 73 (out of 92 baserom bytes compared; function is 104 bytes total in ROM).  
Expected: 100 bytes code+alignment (before pool word).  
Built best: 92 bytes code+alignment (12 bytes shorter).

The 12-byte gap comes from:
- Missing boolean materialization: +10 bytes (5 extra instructions: beq/movs/b/movs/cmp)
- Missing fresh ldrh in key==16 branch: +2 bytes (1 extra instruction)

## Levers tried

- `-fno-strength-reduce` in Makefile for this TU (**keep this — it prevents x&8 → lsrs form**)
- `u16 field = p->_field_10; flag = field & 8` — gives correct `movs r0, #8; ldrh r1` order ✓
- `v = 9; p->_field_10 &= -v` — gives `movs r0, #9; negs r0, r0` (no pool literal) ✓
  but still uses cached r1 in key==16 branch (fresh ldrh missing)
- `(field & 8) ? 1 : 0` — triggers strength-reduction even with -fno-str-reduce ✗
- `(field & 8) != 0` — same, triggers strength-reduction ✗
- `volatile u8 flag` — adds stack overhead (sub sp, #4 + strb + ldrb) ✗
- `asm("")` barriers — not effective, agbcc still CSE-merges ✗
- `asm volatile("" : "=r"(field) : "0"(field))` — triggers bit-isolation form ✗
- `-O1` — gives materialization but uses r1 (not r0) for bool, different encoding ✗
- `-fgcse` enabled — no effect ✗
- `register u8 flag asm("r0")` pin — no effect ✗

## Root cause

The game's old_agbcc version has more conservative memory alias analysis:
after `strh r5, [r4, #18]`, it invalidates ALL cached loads through r4 regardless of
offset. Our old_agbcc's alias analysis is offset-aware: store to [r4+18] doesn't
invalidate [r4+16]. This is why the baserom gets the fresh ldrh and we don't.

The boolean materialization is a separate issue: our old_agbcc at -O2 always folds
`flag = (expr); if (flag)` into a single test. The original compiler apparently didn't.

## Best-effort C (closest approach, 73 byte_diff)

This uses `-fno-strength-reduce` in the Makefile and the field/v variables to get
the most matching instructions, even though the bit-test result and the key==16
clear-bit path don't have the right encoding:

```c
u8 sub_08006A0C(struct StructA0C *p, u16 key)
{
    u8 flag;
    u16 field;
    int v;

    field = p->_field_10;
    flag = field & 8;
    if (flag) {
        if (key == 16) {
            p->_field_12 = key;
            v = 9;
            p->_field_10 &= -v;
            return 1;
        }
        if (sub_08000900() - p->_field_14 > 30) {
            v = 9;
            p->_field_10 &= -v;
            return 0;
        }
    }
    if (key == 16) {
        p->_field_10 |= 8;
        p->_field_14 = gGameStuff._unk00;
    }
    return 0;
}
```
