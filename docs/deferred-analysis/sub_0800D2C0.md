# sub_0800D2C0 — deferred analysis

Destination: own TU `src/engine/sub_0800d2c0.c`, linker entry before
`asm/disasm_0x0800d2c0.o(.text)`. Both callees are peeled:
`sub_0800D270` and in-ROM libgcc `__divsi3` at `0x08033D14`.
Classifier verdict: `ATTEMPT_MATCH`, not `STRONG_UNMATCHABLE`; do not ship

## Function model (confirmed from baserom asm)

Two parallel entity-scan loops keyed on `mode = sub_0800D270((s16)x,(s16)y)`:
- mode==1: scan `gEntities[i+3]` for `i` in `0..19` (s8 count-up).
- mode==2: scan `gEntities[i+23]` for `i` in `0..9`.
Per entity: skip if `status & 8`; `col=(u16)(e->x/24)`, `row=(u16)(e->y/24)`;
match when `(s16)col==(s16)ux && (s16)row==(s16)uy`; then
`e->status = 8 | status | 4` and write `gIwram_53A0[(u8)mapIndex] = 0`, where
mapIndex is the SAME tile-index computation as the matched sibling
`sub_0800D270` (`dcol=scol-3`; range-guard; `(srow-5)*8+dcol` else 0xFF).
`sub_0800D270` (already matched, `src/engine/sub_0800d270.c`) is the canonical
reference for the tail logic.

## STRUCTURAL PROGRESS THIS PASS (escape the prior plateau)

The prior note plateaued at byte_diff 251 with the WRONG comparison ordering
(col-div, compare-col, row-div, compare-row interleaved). The baserom actually
does **both divides first, then both compares** (asm 0xd306-0xd320 = two
`__divsi3` calls back-to-back; 0xd322-0xd338 = the two compares). Re-deriving
with that ordering collapsed most of the diff. Confirmed-correct source shape
(reaches mnemonic-diff ~88 insns, down from the prior structure):

- **Both divides first**: `col=(u16)(e->x/24); row=(u16)(e->y/24);` then
  `scol=(s16)col; if((s16)col!=(s16)ux) continue; srow=(s16)row;
  if((s16)row!=(s16)uy) continue;`  — the `(a<<16)==(b<<16)` compare idiom
  produces scol/srow via the `asrs` side-effect, matching the target.
- **Entity addr via byte-offset**: `(struct Entity*)((u8*)gEntities+(i+3)*56)`
  — keeps base = plain `gEntities` and emits the runtime `adds r1,#3`.
  `&gEntities[i+3]` folds base to `gEntities+const` and loses `adds r1,#3`.
- **Split the OR**: `t=8; t|=status; t|=4; e->status=t;` (defeats the
  `8|4 -> #12` constant fold; matches `movs #8; orrs; movs #4; orrs`).
- **scol-reuse** (`scol = scol - 3;` in place): keeps dcol in scol's register
  and matches the tail sub.
- **Per-TU flag**: `src/engine/sub_0800d2c0.s: CFLAGS += -fforce-addr` lowers
  the diff (148->… mnemonic) — keep it.

The clean readable version of the above (the `## Best-effort C` below) compiles,
builds, and reaches **byte_diff 259, diff_count 88** (vs target 400 bytes).
This is the recommended resume base — it is structurally near-identical; the
residual is a single coupled register-coloring knot.

## Remaining wall — register-coloring local minimum (instrumentation-confirmed)

Built a private instrumented `old_agbcc` (probe at `gcc/global.c`
`reg_renumber[...] = best_reg`) and read the live allocation for this TU. The
loop-carried trio competes for callee-saved r4-r7 (alloc order r4,r5,r6,r7):

```
pseudo35 (entity ptr e)  refs=20 len=88 -> r5   (matches target)
pseudo42 (status)        refs=12 len=72 -> r6   (TARGET wants r7)
pseudo288 (counter i<<24) refs=8  len=60 -> r7  (TARGET wants r6)
```

agbcc's `allocno_compare` priority is `log2(refs)*refs/live_length`:
status = 3.585*12/72 = 0.597 vs counter = 3*8/60 = 0.40. status outranks the
counter, so status grabs r6 first and the counter gets r7 — the OPPOSITE of
the baserom (status r7, counter r6). To flip it the counter needs priority
> 0.597, i.e. refs>=12 at len=60, OR status refs<=8.

Levers TRIED that do NOT flip r6/r7 (all leave status>counter or worsen the
coupled coloring — record so the next agent picks a DIFFERENT angle):
- `register u16 status asm("r7")` pin: 152 -> 186 (disrupts counter + e + tail).
- block-scoping status per loop: splits into 2 pseudos but moves `e` off r5
  (201). 
- `u32 status` (fewer u16 masks): refs stay 12, no change (148).
- loop `for(i=3;i<=22;...)` w/ base index: kills the `adds r1,#3` (182).
- `s32 i` instead of `s8 i`: 219 (loses the `<<24`/`asrs` count-up idiom).
- declaring status first (allocno tie-break): no change (priorities differ,
  tie-break never reached).
- `-fno-gcse`/`-fno-strength-reduce`/`-fno-rerun-cse-after-loop`/`-O1`/
  `-ffixed-r1`/`-ffixed-r2`: all neutral or worse. Only `-fforce-addr` helps.

Coupled with r6/r7 are two more coloring diffs that move together with it:
- **srow placement** target r4 (callee-saved, survives to `(rowB-5)*8`) vs
  mine r2/r3. The `rowA=srow; rowB=rowA;` copy-CHAIN (mirroring sub_0800D270's
  `row=(s32)y`) DOES push srow toward r4 (and emits the target's
  `adds r1,r4,#0`/`adds r0,r1,#0` preserve-copies) but trades against scol's
  placement (scol/srow swap r3<->r4), net ~same diff (140-158 depending on
  pin). 
- **copy-spread** `adds r2,r3,#0; subs r3,r2,#3` (3-operand sub via a dead
  scol copy) — a `regmove.c fixup_match` artifact that only fires when dcol is
  pinned to r3 (`register s32 dcol asm("r3")`), which then collides with the
  entity-address pool literal (target loads it to r1). Net best with this pin
  + rowA/rowB chain was mnemonic-diff 140 but with the new pool-reg collision.

Diagnosis: a sharp register-coloring local minimum in the loop-carried trio.
Every source-shape lever that fixes one of {r6/r7, srow r4, copy-spread} pushes
another out of place. This is exactly the `vendor/decomp-permuter` case
(statement-order / scope / temp mutation of register coloring), but the
permuter was UNAVAILABLE this pass: main's `vendor/decomp-permuter` is a broken
self-referential symlink (`.venv/bin/python` -> "Too many levels of symbolic
links"), so the worktree bootstrap could not provide it.
