## Function model (confirmed from baserom asm)

`void sub_0800D2C0(s16 x, s16 y)`. `ux=(u16)x` in **r9**, `uy=(u16)y` in **r8**,
`mode=(u8)sub_0800D270((s16)x,(s16)y)` in **sl/r10** (kept live through loop 1
because of the `if (mode != 2)` check that follows it). Two entity-scan loops:
- mode==1: scan `gEntities[i+3]` for `i` in 0..19 (s8 count-up, `i<<24` idiom).
- mode==2: scan `gEntities[i+23]` for `i` in 0..9.
Per entity (e = r5): skip if `status & 8`; `col=(u16)(e->x/24)` then
`row=(u16)(e->y/24)` (BOTH divides first, then the two `(a<<16)==(b<<16)`
compares — `scol=(s16)col` via the asrs side-effect in r3, `srow=(s16)row` in r4);
match → `e->status = 8|status|4` (split as `t=8;t|=status;t|=4` = two orrs); then
the SAME tile-index logic as `sub_0800D270`: `dcol=scol-3`; range-guard;
`(rowv-5)*8+dcol` else 0xFF; `gIwram_53A0[(u8)idx]=0`.

## STRUCTURE NOW KNOWN-CORRECT (escapes the prior plateau)

This pass re-derived the control flow from the baserom and found the prior
note's per-loop-duplicated tail was both over- and under-merged. The CORRECT
shape (verified instruction-for-instruction against the baserom) is:

1. **Two physically-separate loops** (bounds 19 / 9, offsets i+3 / i+23), each
   with its OWN OR + second-check block.
2. **A SINGLE shared final tail** at the END (baserom d412 `ret_ff: idx=0xFF`,
   d41c `compute: idx=(rowv-5)*8+dcol`, d422 `common: store`, d442 exit). BOTH
   loops `goto` it. In C: put the `ret_ff:/compute:/common:` labels in the
   SECOND loop's scope; loop-1 `goto`s forward into them.
3. **2nd column check REUSES dcol** (NOT a fresh `(u16)scol`): baserom is
   `if ((u16)dcol > 8)` re-truncating the held dcol (r3), not recomputing.
4. **ONE `rowv` variable**, not separate rowA/rowB.
5. **dcol-from-copy**: `dcol = scol - 3` should emit `adds r2,r3,#0; subs r3,r2,#3`
   (a regmove `fixup_match` copy-spread), not a 3-operand `subs r2,r4,#3`.

The known-correct C is in `## Best-effort C` below. With this structure the
function compiles to **376 bytes / ~172 insns** vs the baserom's **400 bytes /
195 insns**, `byte_diff 259` (compile_and_view_assembly.py). `-fforce-addr` and
its absence both give 259 (the flag trades the loop-2 base-hoist for nothing).

## THE WALL — a 24-byte structural deficit from coupled agbcc micro-decisions

The residual is NOT one knot — it is THREE coupled agbcc artifacts the C cannot
force, each costing insns, which together make the candidate 24 bytes SHORT, so
the function never reaches 400 bytes (this also defeats the permuter — see below):

### (a) Loop-2 hoists constant 8 into the dead `sl`, NOT the base (root cause)
Baserom loop-2 entry does `movs r1,#8; mov sl,r1` (sl=8, mode now dead) and the
OR uses `mov r0,sl; orrs r0,r7`; the gEntities base loads FRESH each iter
(`ldr r3,[pc]; adds`). This makes loop-2's body TEXTUALLY DIFFER from loop-1's
(loop-1 OR is `movs r0,#8` immediate, mode still live so sl busy) — which is the
ONLY thing that stops agbcc's **cross-jump / tail-merge** (`gcc/jump.c`,
on at -O2, no `-fno-` switch) from collapsing the two identical post-compare
bodies into one. In MINE the bodies ARE byte-identical, so cross-jump merges
loop-1 INTO loop-2 (loop-1 just `beq`s to loop-2's body), deleting loop-1's
OR+second-check entirely → ~13 insns short. WITH `-fforce-addr` agbcc instead
hoists the BASE into sl (wrong invariant); WITHOUT it, NOTHING is hoisted (8
immediate, base fresh) — neither reproduces "hoist 8, base fresh". The baserom's
choice is a register-reuse-of-dead-`mode`-pseudo artifact, not a cost-driven
LICM, so no source shape or `-fXXX` tried reproduced it. THIS is the lever to
crack next: make loop-2's OR differ from loop-1's so cross-jump can't merge, in
a way that emits `mov r0,sl` for the 8.

### (b) `(u16)dcol` re-truncation is CSE-merged
Baserom re-extracts `(u16)dcol` for the `>8` check (`adds r0,r3,#0; lsls;lsrs;
cmp #8`) because the first `(u16)dcol`'s value lived in a SCRATCH reg (r0) that
died. agbcc CSE-merges my two `(u16)dcol` casts (held in r1, survives) into one.
Tried & FAILED to split: `(u16)(dcol&0xffff)`, `(u16)(dcol+0)`,
`(u16)(scol-3)` recompute, `-fno-gcse`, `-fno-cse-follow-jumps`,
`-fno-rerun-cse-after-loop` — all fold back to the single held value. Needs the
first `(u16)dcol` forced into a scratch reg the row-checks clobber.

### (c) copy-spread `adds r2,r3,#0; subs r3,r2,#3` missing
Mine emits the 3-operand `subs r2,r4,#3`. This is a regmove fixup that (per the
prior note) only fires with `register s32 dcol asm("r3")`, which then collides
with the entity-address pool literal. Coupled to scol/srow's r3/r4 placement.

## Register coloring (re-confirmed with a fresh instrumented agbcc)

Built a private `old_agbcc` with an `fprintf` at `gcc/global.c` `find_reg`'s
`reg_renumber[...] = best_reg`, dumping pseudo/refs/len/best_reg/copypref. Live
allocation for the v_dup base:
```
pseudo35 e       refs=20 len=88 -> r5  (matches target)
pseudo44 status  refs=12 len=72 -> r6  (TARGET wants r7)   copypref=-1 pref=-1
pseudo290 i<<24  refs=8  len=60 -> r7  (TARGET wants r6)   copypref=-1 pref=-1
```
`allocno_compare` priority = `floor_log2(refs)*refs/len`: status =
3.585*12/72 = 0.597 > counter = 3*8/60 = 0.40, so status is allocated FIRST and
grabs r6 (first free callee-saved after r5=e); counter gets r7 — the OPPOSITE of
the baserom. To flip, the counter needs priority > 0.597 (refs≥12 at len=60 →
0.717) OR status refs ≤ 8 (→ 0.333). Levers TRIED that do NOT flip r6/r7:
- `register u16 status asm("r7")` pin (on v_dup): flips r6/r7 (status→r7,
  counter→r6 confirmed in the trace) but CASCADES — `ux` leaves r9, `mode`
  leaves sl, base hoisted into sl; byte_diff 259 -> **360**. Coupled coloring.
- block-scoping `status` per loop: splits to 2 pseudos (refs=14 each!) that take
  r5, pushing `e` OFF r5 to r6 (worse — `e` MUST be r5).
- `u32 status` / OR-combine `status|8`: refs stay 12, no flip.
- full `-fXXX` sweep (`-fno-force-addr -fcaller-saves -fno-caller-saves
  -fomit-frame-pointer -fno-schedule-insns{,2} -fno-peephole -f{,no-}rerun-loop-opt`):
  status stays r6 in every one.
status, srow(r4), and the copy-spread are ONE coupled coloring knot — fixing one
pushes another out (same conclusion as the prior note, now also true on the
cleaner v_dup structure).
