## What the function does (verified from asm)
Takes (s16 x, s16 y). Calls `mode = (u8)sub_0800D270(x, y)`.
- mode==1: scan entity records `gIwram_3720 + (i+3)*56` for i in 0..19.
- mode==2: scan records `gIwram_3720 + (i+23)*56` for i in 0..9.
For each record whose `_h34 & 8 == 0`, compute `col=(s16)(_h2/24)`,
`row=(s16)(_h4/24)`; if `(u16)col==(u16)x && (u16)row==(u16)y`, set
`_h34 |= 8|4` (built as `t=8; t|=flags; t|=4;` two orrs — matches), then a
col/row range gate identical to `sub_0800D270`'s body, and on success write
`gIwram_53A0[(u8)((row-5)*8 + (col-3))] = 0` (clamped to 0xFF). Then `return`.
The two branches share the final write block but keep separate range-check tails
(asymmetric branch encoding: ret==1 ends `bgt;b 0xd41c`, ret==2 ends `ble 0xd41c`).

The 56-byte record loop index `(i+3)*56` is the same `(N+K)*56` stride idiom as
the matched sibling `src/engine/sub_0800d0f8.c`. Struct fields: `_h2`(+2),
`_h4`(+4), `_h34`(+0x34) flags (bit 8 = active/skip; sets 8|4 on match).

loop-back). Remaining drift is all register-coloring + one compare idiom:

1. **flags/saved-i register swap (r6<->r7).** Target: flags in r7, spilled loop

   `register u16 flags asm("r7")` BREAKS the prologue: agbcc then maps the 3
   high-reg saves (sl,r9,r8) to r4,r5,r6 and treats r7 as a free (UNSAVED) reg →
   prologue drops to `push {r4,r5,r6}` instead of the target's `push
   {r4,r5,r6,r7}`. So the r7 pin is a dead end; the swap must come from natural
   allocation pressure, not a pin.
2. **The compare emits 1 fewer insn than target.** Target stores `col=(u16)(div)`
   (lsrs r4) and the equality compare materializes `col<<16` and `ux<<16` and
   compares the `<<16` forms (`cmp r0,r1`), reusing `col<<16`'s `asrs r3` as the
   `(s16)col` for `dcol`. My `col=(s16)div; (u16)col==ux` compares directly
   against r9 (no `<<16`), 1 insn shorter per compare × 4 compares ≈ the 36-byte
   gap. Tried: `col=(u16)div` + `(s16)col==(s16)ux` + `dcol=(s16)col-3` → size
   climbs toward 376/372 but byte_diff/diff_count get WORSE (the row range tests
   then re-derive `(s16)row` each time instead of reusing the compare's side
   product; target computes `(s16)row` ONCE in the 2nd compare (`asrs r4`) and
   reuses it for every row test). Couldn't get agbcc to reuse that signed form.
3. **arg-setup scheduling.** Target interleaves `lsls r0,#16; lsls r1,#16` then
   extracts, using r3 as the `(u16)y` temp (`lsrs r3,r1,#16; mov r8,r3`). Mine
   computes ux fully then uy, reusing r2. Minor (≈3 insns).
4. **index multiply uses r0 (target) vs r1 (mine)** — falls out of (1)/(3).

### Outcome

### The exact asm idiom that diverges
Baserom (d310-d346) computes `col = (u16)(_h2/24)` and `row = (u16)(_h4/24)`, then for each equality test materializes BOTH operands as their `<<16` forms and compares those:
```
d322: lsls r0,r4,16   ; col<<16
d324: mov  r3,r9      ; ux
d326: lsls r1,r3,16   ; ux<<16
d328: asrs r3,r0,16   ; (s16)col  <-- SIDE PRODUCT of the same lsls, kept live
d32a: cmp  r0,r1      ; compare the <<16 forms (== is shift-invariant)
...
d344: adds r2,r3,#0 ; d346: subs r3,r2,#3   ; dcol = (s16)col - 3, REUSES the asrs at d328
```
The `(s16)row` asrs (d334) is likewise reused for every row range test. The prior best-effort C compared `(u16)col == ux` (a narrow compare against the already-u16 r9), which emits a direct `cmp r0,r9` with NO `<<16` and therefore never produces the reusable `asrs` — so dcol/row tests re-derived `(s16)col`/`(s16)row` each time, costing ~36 bytes.

### Regexes searched (corpus_asm_search.py, default all-mirrors)
- `asrs\s+r[0-7],\s*r[0-7],\s*#16` (Thumb-`s`/`#`-form): **0 candidate commits** across all 23 mirrors. The pickaxe is `git log -G` (POSIX ERE) — `\s`/`#` literal `#` are fine but the pret asm format has NO `#` and writes `asrs r1, 16` (2-operand) — so this regex finds nothing.
- `lsl[s]? +r[0-7], +r[0-7], +#16`: pickaxe finds candidate commits (pokeemerald 2, firered 1, rhythmtengoku 2) but the in-diff line-filter (same regex) matches 0 removed lines — confirms pret stores `lsls r0, r0, 16` (no `#`). **0 hits.**
- `asr[s]? +r[0-7],( +r[0-7],)? +#?16` (format-agnostic): **407 candidate commits in pokeemerald alone** — the s16 sign-extend idiom is ubiquitous; too broad.
- `asrs +r[0-7], +r[0-7], +16` (3-operand distinct-dest, the reuse form): **181 candidate commits in pokeemerald** — still too broad (every `(short)x` cast).
- Final precise filter via raw `git show -U0` over the first 120 candidates, grepping each removed-asm body with a Perl multiline pattern `lsls rA,rB,16 \n .. \n asrs rC,rD,16 \n cmp rE,rF`: **2 hits** — `pokeemerald@08a3533682` and `pokeemerald@4e396207d3`.

### Top corpus hits examined
- **pret/pokeemerald@08a3533682** (`sub_80C57FC` in src/frontier_pass.c) — THE structural answer. `u8 sub_80C57FC(s16 x, s16 y)` loops over a struct array comparing `field.yStart <= y && field.yEnd >= y && field.xStart <= x && field.xEnd >= x`. The s16 PARAM is sign-extended ONCE (`lsls r1,16; asrs r5,r1,16`) and reused for every compare; struct fields are `ldrsh` fresh. The takeaway: comparing two genuinely-`s16`-typed C values (not `(u16)` of one) is what makes agbcc emit the `lsls;asrs;cmp` reuse form. Our function is the mirror image — the computed div result plays the once-extracted role, the param the fresh-loaded role, and `==` lets the compare stay on the un-asr'd `<<16` form.
- **pret/pokeemerald@4e396207d3** ("document more of trainer card") — same `lsls;lsls;asrs;cmp` cluster but ordering compares (`cmp r0,r4` etc.); confirmed the idiom but less directly transferable than 80C57FC.

### Whether the trick transferred
YES for drift #2. Rewriting the compare as `(s16)col == (s16)ux && (s16)row == (s16)uy` on plain (un-pinned) `u16 col,row` locals reproduced the baserom compare region byte-for-byte: col/row stored `(u16)` via `lsls;lsrs`, the equality compares on `col<<16`/`ux<<16`, the `asrs` side-products kept live and reused for `dcol = (s16)col - 3` (`subs r1,r3,#3`) and the row range tests. Two earlier failed shapes confirmed the boundary: `(u16)col == ux` (narrow) and an explicit `scol=(s16)col` single-assignment BOTH lost the reuse (diff_count 221) because they truncate before the compare. De-pinning `col` from `register asm("r4")` was also load-bearing — pinned, agbcc dropped col's `(u16)` store-truncation as dead (`adds r4,r0,#0`), breaking the symmetry with row; unpinned, both truncate (`lsls;lsrs`) like baserom.

### agbcc pass implicated (residual = register-coloring)
`tools/agbcc-src/gcc_arm/local-alloc.c`, `qty_compare_1` / `QTY_CMP_PRI` (line ~1488): priority = `floor_log2(n_refs)*n_refs*size/(death-birth)`, ties broken by qty number (first-use order). The residual ~273 byte_diff is dominated by ONE tie: the saved loop-counter (`i<<24`, baserom r6 via `adds r6,r2,#0`) vs `flags` (baserom r7). agbcc swaps them (flags->r6, saved-i->r7), and that propagates to the whole index/counter chain using r0/r1 instead of baserom's r1/r2 (`asrs r0,r2,#24` vs `asrs r1`, `movs r1,#2` vs `movs r2,#2`). Pinning `flags asm("r7")` does NOT work (confirmed again with the new structure): agbcc then maps the 3 high-reg saves to r4/r5/r6 and treats r7 as free, dropping the prologue to `push {r4,r5,r6,lr}` (baserom pushes r7 too). `-ffixed-r6`/`-ffixed-r7` no-op (those are the high-save destinations). The second residual is arg-setup scheduling (baserom interleaves `lsls r0,16; lsls r1,16` for x/y; agbcc does x-then-y) — agbcc 2.x has no `-fno-schedule-insns` (invalid option), so it's not flag-controllable.
