# sub_080155F0 — deferred analysis

Four-way screen-scenery dispatcher at 0x080155f0 (620 bytes, asm slice
`asm/disasm_0x080155f0.s`, dest `src/engine/sub_080155f0.c`). Fully understood
semantically (see `asm/data/scenery_1b62aa.s` header, which documents this exact
function); a clean readable C implementation exists and is byte-close, but stalls
in a sharp agbcc CSE + register-coloring + compare-canonicalization local minimum.
VERDICT from classify_unmatchable.py = ATTEMPT_MATCH (NOT STRONG_UNMATCHABLE), so
NAKED is not appropriate — this is clean game logic that should match.

## Semantics (confirmed)

- Dispatch byte = `gIwram_6110.gateByte` (0x03006110 + 0x2b = 0x0300613b),
  values 0..3 select one of four (low, high) BG-tilemap variant pairs; default
  returns.
- Per case (inlined 4x): read selector `s16 *(gEntities + 0xb70)`
  (= `gEntities[52].field_10`); compare against cached byte `(u8*)0x03003610`
  offset 0xb; if changed, DMA the chosen variant (sel!=0 -> high, else low)
  into EWRAM scratch 0x02010000 (REG_DMA3 cnt = DMA_ENABLE|0x8000), readback
  cnt, write the new selector byte to the cache, then `sub_080100E4(1,
  0x02010000, 0x0600e800)` streams it to BG screenblock 29.
- Shared tail: `r4` = the case's palette pointer table (tableC = 0x08307e8c +
  caseIdx*8). Compares gGameStuff._unk00 (0x03005330) against u32 at
  gEntities+0x1a60; if `< 8` return; else store, then a 0..1 rolling counter at
  gEntities+0x1a5b indexes the palette table and DMAs the palette into palette
  RAM 0x05000140 (cnt = DMA_ENABLE|0x20).
- The four ROM low/high variant anchors already have global labels in
  `asm/data/scenery_1b62aa.s`: sScenerVariantMode{0..3}{Low,High}_*. tableC at
  0x08307e8c is an array of 8 ROM palette pointers (not yet extracted/labeled).

## Drift

Best byte_diff: **456** (object .text 0x208 = 520 bytes vs target 620). Stuck at
456 +- ~5 across ~15 fundamentally-different structural and flag approaches.
Three independent divergences, each an agbcc decision the target made differently:

1. **Cache-reload CSE (the big one, ~40 bytes over 4 blocks).** The target
   RE-LOADS `gEntities` and REBUILDS the 0xb70 offset (`ldr =gEntities; movs
   #0xb7; lsls #4; adds; ldrh`) for the cache write, even though it read the same
   address for `sel` a few instructions earlier. agbcc CSEs the address
   computation and reuses the register (mine: `ldrh [r5]`, 1 insn). This CSE is
   robust: NOT broken by scoped/separately-named base locals (`u8 *q =
   (u8*)gEntities` in an inner block — still 455), NOT by `vu16`/`vs16` volatile
   reads (463/456), NOT by `asm("" ::: "memory")` barrier between the DMA stores
   and the reload (457), NOT by -fno-gcse / -fforce-addr /
   -fno-expensive-optimizations. The DMA `.src`/`.dst` stores are non-volatile
   (only `cnt` is `vu32`), so the volatile `cnt` readback does not barrier the
   read CSE in agbcc 2.x. NEXT AGENT: this is the lever to crack. Read
   gcc_arm/cse.c — find what invalidates the value-numbering table entry for a
   constant-base + register-offset memory ref. A permuter run from the 456 base
   (statement reorder/var-scope) is the designated tool but its .venv is MISSING
   in this environment (main has no vendor/decomp-permuter/.venv either).

2. **DMA-src select shape.** Target branches and loads REG_DMA3 base in EACH
   branch (`bne; ldr =DMA; str low; b; ldr =DMA; str high`); the ternary
   `sel ? hi : lo` instead emits a conditional-move (`adds r0,hi; cmp; bne; adds
   r0,lo; str [r2]`) with a single DMA-base load. Explicit `if/else` for the
   store churned other registers (531). Temp `chosen` pointer = 457.

3. **Register coloring + compare canonicalization.** Target prologue
   `push {r4,r5,lr}` (low=r4, high=r3, selptr=r2, cache=r5, paletteTable=r4
   into the tail); mine uses an extra callee-saved reg (`pop {r4,r5,r6}`),
   different assignment (low=r6, high=r4, selptr=r5, cache=r3). The time gate
   `now - *lastTick < 8` canonicalizes to `cmp #7; bls` regardless of `< 8` vs
   `>= 8`-inverted or -fno-strength-reduce; target has `cmp #8; bcc`. Tail
   palette index: target `lsls #24; lsrs #22` (byte-extract+scale), mine `lsls
   #2` (idx known u8 from ldrb); `(u8)idx` cast did not force the re-mask.

Levers tried (all -> ~456): ternary vs explicit if/else vs temp-chosen-ptr for
DMA src; named `u8 *base3720` local vs inline `(u8*)gEntities + off` (the named
local is REQUIRED to get the `movs #0xb7; lsls #4` offset build instead of a
folded 0x03004290 pool literal); scoped inner base locals; struct-member form
`gEntities[52].field_10`; vu16/vs16 volatile reads; asm("" memory) barrier;
compiler swap to AGBCC (newer) — no help; CFLAGS -fno-gcse, -fforce-addr,
-fno-expensive-optimizations, -fno-strength-reduce — no help; inverted `>= 8`
time gate; `elapsed` temp; `(u8)idx` index cast. Permuter: UNAVAILABLE (.venv
missing). Corpus grep for the DMA-ternary idiom: no hits (unusual pattern).

The sibling `src/game/sub_0800534c.c` (sub_08005404) is the matching reference
for the `gEntities + 0xb70` selector-counter idiom and confirms the `movs
#0xb7; lsls #4` offset-build (it matches). The difference is that sub_08005404
reads gEntities+0xb70 only along one path; this function reads it twice in one
basic block and agbcc CSEs them whereas the baserom did not.
