## sub_08032904 — deferred decomp

Range: [0x08032904, 0x0803299c) — 152 bytes, Thumb.  
Destination: `src/system/sub_08032894.c` (append after `sub_08032894`).  
Compiler override: OLD_AGBCC_BIN (same file as sub_08032894).

## Function summary

Sound channel initializer: calls `sub_0802E724(ch)` (silence/reset), then
`sub_0802E7C4(pan, ch)` (pan apply), then initialises three regions in
`gpSoundSystem`:
- `ss->chDirty[ch] = 0` (offset 0x10 + ch\*4)
- `*(u16*)(ss + 0xac + ch*2) = hwCtrl` (5th stack arg)
- At `ss + 0x8c + ch*8`: store 0xff00 at +4, ctrl byte at +7, 0 at +6
- If `ch <= 2`: initialise the ChannelState at `ss + 0x20 + ch*36`
  (same field layout as SoundSlotInit in sub_08032894.c):
  - compute acc = word_00 + word_1c, store to word_22
  - set word_00 = step<<8
  - zero 11 other halfword fields

Signature: `void sub_08032904(s32 ch, u32 step, u32 pan, u32 ctrl, u16 hwCtrl)`

## Drift

**Best byte_diff: 67, diff_count: 22**

The root cause is a single compiler behavioral difference: the 5th stack
argument `hwCtrl` (`u16`, passed as word on stack) is **eagerly preloaded** into
r6 by old_agbcc at function entry, while the baserom keeps it on the stack and
loads it **lazily** at point of use using `mov r4, sp; ldrh r4, [r4, #28]`.

Because r6 is taken by hwCtrl, a cascade of register mismatches follows:
- ch still goes to r7 (correct)
- pPool still goes to r5 (correct, via `register SoundSystem **pPool asm("r5")`)
- step goes to r8, ctrl to r9 (correct, via `register ... asm("r8/r9")`)
- ch8 goes to r4 (correct, via `register u32 ch8 asm("r4")`)
- BUT: r6 is occupied by hwCtrl (wrong), so later:
  - `movs r2, #0` (should zero r2 for the chMode+6 byte store) is NOT generated
  - chMode construction uses `r1 += r4; r1 += 0x8c` (2 insn) instead of
    `r0 = r4 + 0x8c; r1 += r0` (3 insn via r0 intermediate)
  - 0xff00 constant goes into r2 (not r0)
  - ctrl byte store uses `mov r0, r9; strb r0` (not r6)
  - zero byte store uses r3 (not r2) — because r2 was never pre-zeroed
  - step<<8 uses `mov r2, r8` (not `mov r6, r8`)
  - ch36State chOff goes into r4 instead of r1 (fixed with pin)

The BL address offsets also mismatch because the extra preload instruction
shifts the PC by 2 bytes, changing the BL encoding.

## Levers tried

- `register s32 savedCh asm("r7")` — agbcc generates r7=ch but does NOT add r7
  to the push list (corruption of caller's r7). Pin with immediate init `= ch`
  or deferred `savedCh = ch` both behave the same way. DOES NOT WORK as a pin.
  Fix: use plain `s32 savedCh` (non-pinned) with `register SoundSystem **pPool
  asm("r5")` — this forces ch into r7 naturally (r5 taken by pPool → r6 is next
  free → r7 for ch... but only if another variable takes r6 first).
- `register SoundSystem **pPool asm("r5")` — REQUIRED to get ch into r7.
  Without it pPool goes to r4 and ch goes to r6.
- `register u32 ch8 asm("r4")` — REQUIRED to get the correct 3-register ch36State
  computation (`add r4, r4, r7; lsl r4, r4, #2; add r4, #0x20`).
- `register u32 chOff asm("r1")` inside the ch36State block — REQUIRED to get
  `add r1, r4, r7; lsl r1, r1, #2; add r1, #0x20` instead of using r4.
- `u16 hwCtrl` parameter type — generates `ldr + lsl + lsr` preload (wrong).
- `u32 hwCtrl` parameter type — generates `ldr` preload (wrong, different).
- Moving `hwOff = 0xac` before BLs to "fill" r6 — compiler folds the constant,
  no callee-saved register allocated for it.
- Adding extra live-across-BL variables to fill r6 — any such variable gets
  r6, which just shifts hwCtrl to another register (still preloaded eagerly).
- Permuter: base score 1460, best found 1255 after 45 seconds (215 iterations).
  Permuter cannot fix fundamental preloading difference.

## What the next agent should try

The baserom compiler (original gcc 2.9-arm variant) chose NOT to preload the
5th stack argument into a callee-saved register, instead loading it lazily via
`mov r4, sp; ldrh r4, [r4, #28]` when needed. Our old_agbcc eagerly loads it.

Ideas for the next attempt:

1. **Remove the r5 pin and restructure**: If pPool uses a `SoundSystem **` local
   (not pinned to r5), the compiler might assign a different allocation where
   hwCtrl naturally stays on stack. Try all combinations of:
   - with/without r5 pin for pPool
   - with/without r4 pin for ch8
   - different hwCtrl type (u8, u16, u32)

2. **hwOff idiom**: SoundChannel_Init (the sibling) uses `u16 hwOff` as a
   non-constant to prevent the compiler from folding 0xac into the address add.
   Try the exact SoundChannel_Init pattern for the hwCtrl address construction —
   maybe the `idx2` pin on r2 combined with hwOff as u16 changes hwCtrl handling.

3. **Leaf-function pattern**: the hwCtrl param is stack arg #5. If any callee
   (sub_0802E724 or sub_0802E7C4) is declared `void func(void)` (wrong but
   matching trick) — the compiler might not see the BL as clobbering regs and
   skip the preload. Try changing extern declarations to different signatures.

4. **Different function structure**: what if the prologue order matters?
   In the baserom: ch→r7, step→r8, pan→r4, ctrl→r9 (step BEFORE pan). My code
   generates pan before step. Try placing `savedStep = step` (or some r8 pin)
   BEFORE the pan assignment — maybe this changes register pressure just enough.

5. **Using gcc 2.9 older variant**: the baserom was compiled with the original
   GCC 2.9-arm compiler. Our old_agbcc might be a slightly different revision.
   Check if there's any way to use an older binary.

## Best-effort C

The code is correct (matching structure) — just wrong register allocation.
Build the function with these pins and the C below produces byte_diff 67:

```c
#include "types.h"
#include "macros.h"

extern void sub_0802E724(s32 ch);
extern void sub_0802E7C4(u8 pan, s32 ch);

typedef struct SoundSystem {
    u8 _pad00[0x10];
    /* 0x10 */ u32 chDirty[4];
    u8 _pad20[0xf8];
    /* 0x118 */ void *slot;
} SoundSystem;

#define gpSoundSystem (*(SoundSystem **)0x030065e0)

void sub_08032904(s32 ch, u32 step, u32 pan, u32 ctrl, u16 hwCtrl)
{
    register u32 savedStep asm("r8") = step;
    register u32 savedCtrl asm("r9") = ctrl;
    register SoundSystem **pPool asm("r5");
    register u32 ch8 asm("r4");
    SoundSystem *ss;
    SoundSlotInit *chState;
    u8 *chMode;
    u16 hwOff;
    u16 acc;
    s32 savedCh;

    savedCh = ch;
    sub_0802E724(savedCh);
    pan = (u8)pan;
    sub_0802E7C4(pan, savedCh);

    pPool = &gpSoundSystem;
    ss = *pPool;
    ss->chDirty[savedCh] = 0;
    hwOff = 0xac;
    {
        register u32 idx2 asm("r2") = (u32)savedCh * 2;
        *(u16 *)((u8 *)ss + hwOff + idx2) = hwCtrl;
    }

    ch8 = (u32)savedCh * 8;
    chMode = (u8 *)ss + ch8 + 0x8c;
    *(u16 *)(chMode + 4) = 0xff00;
    *(u8 *)(chMode + 7) = savedCtrl;
    *(u8 *)(chMode + 6) = 0;

    if (savedCh > 2)
        return;

    {
        register u32 chOff asm("r1") = (ch8 + (u32)savedCh) * 4 + 0x20;
        chState = (SoundSlotInit *)((u8 *)*pPool + chOff);
    }

    acc = chState->word_00 + chState->word_1c;
    chState->word_22 = acc;

    chState->word_00 = savedStep << 8;
    chState->word_02 = 0;
    chState->word_1c = 0;
    chState->word_1e = 0;
    chState->word_20 = 0;
    chState->word_14 = 0;
    chState->word_16 = 0;
    chState->word_04 = 0;
    chState->word_06 = 0;
    chState->word_0c = 0;
    chState->word_0e = 0;
    chState->word_12 = 0;
}
```

Note: `SoundSlotInit` is already defined in the same file (`sub_08032894.c`) —
the struct fields at offsets 0..0x22 are the correct layout for the ch36State
accesses. No new typedef needed if appending to the same file.
