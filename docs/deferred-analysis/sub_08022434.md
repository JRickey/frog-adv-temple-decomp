## What CRACKED the 572 plateau (the three keys — KEEP these)

1. **`u8 i` loop counter (NOT `s32`).** The masked `(u8)(i+1)` increment
   (`lsls #24; lsrs #24; ... cmp #1; bhi`) DEFEATS agbcc's pointer-induction-
   variable / general-induction-var optimization. With `s32 i` agbcc strength-
   reduces `slot = &gEntities[69+i]` into a `p += 56` pointer giv kept in a high
   reg, stealing r8 from `i` and cascading 182 diffs. `u8 i` forces the baserom
   form (recompute `i*56 + 0x03004638` each iteration from `i` in r8).
   `for (i = 0; i < 2; i++)` with `u8 i` matches the increment exactly.
   `-fno-strength-reduce` does NOT help (the giv is created by a different pass).

2. **`resetY = k + 0x80` at the LOOP TOP (LICM-hoisted), with `k` a separate
   variable decoupled from the gate.** This is the ONLY structure that produces
   `0x2ef` in sl via the register-reuse `adds r0, #0x80` (baserom 0x28) instead
   of a folded literal `0x2ef`. The gate must use the LITERAL `0x26f` (which CSE-
   merges with `k = 0x26f`); `k` assigned right before the loop. Computing resetY
   in the PREHEADER folds `k+0x80 -> 0x2ef` literal (byte_diff 608); computing it
   in case 2 prevents the hoist (686). Loop-top is the unique sweet spot.

3. **Pin the y-gate read to r1: `register s32 yg asm("r1") = gEntities[0].y;`**
   Without it the gate puts y in r0 / k in r1 (swapped vs baserom y=r1/k=r0),
   +7 diffs. With it the gate registers match exactly. (This is the ONLY lever
   in the byte_diff-5 C and it is pure C / status would still be "matched".)

## The IRREDUCIBLE 4-byte residual (root cause, fully diagnosed)

Diff at byte_diff 5 (the ONLY diff):
```
  +0x0026  DELETION    target: mov r9, r2     built:
  +0x002c  INSERTION   target:                built: mov r9, r2
```
baserom preheader order: i->r8, **gEntities->r9 (mov r9,r2)**, then 0x2ef->sl.
built  preheader order: i->r8, **0x2ef->sl** (adds r0,#0x80; mov sl,r0), then
gEntities->r9.

ROOT CAUSE (confirmed by reading `tools/agbcc-src/gcc_arm/loop.c` AND the
`-dr`/`-dl` RTL dumps): BOTH `0x2ef`(resetY) and the `gEntities` symbol base
(r9) are LOOP-INVARIANT MOVABLES. `scan_loop` collects movables in forward
source-scan order (`last_movable->next = m`), and `move_movables` emits each via
`emit_insn_before(loop_start)` in that list order — so the FIRST-collected
movable lands EARLIEST in the preheader. resetY (loop top) is collected before
the `gEntities` base (first used in case 0, physically after resetY), so
`mov sl` is emitted before `mov r9`. In the RTL dump the resetY `+128` is
insn 1284 and the gEntities copy is insn 1292 — order fixed at loop-opt, before
register allocation. The movables list is NOT sorted by savings (verified in
loop.c), so it is pure scan order.

To flip the order, a PLAIN `gEntities[N]` (symbol -> r9) reference must be
SCANNED before `resetY = k + 0x80` in the loop. But:
- The slot uses `gEntities[69+i]` which agbcc compiles to the `gEntities+0xf18`
  ABSOLUTE LITERAL (a *different* movable from the plain `gEntities` base), so
  putting slot first does not birth the r9 movable.
- The only plain-gEntities (r9) accesses are deep in the conditional case bodies
  — relocating one to the loop top changes behaviour.
- Sharing a single `gEntities` pseudo across gate+loop via a pointer (`e0[69].x`)
  changes the addressing mode (`[ptr,#imm]` vs `gEntities+0xf1a` literal) and
  regresses (byte_diff 471).
- baserom evidently keeps `gEntities` LIVE from the gate (no loop movable) so its
  r9 copy is an alloc copy emitted at the gate, BEFORE the resetY movable. agbcc
  given this C re-hoists gEntities as a fresh loop movable instead.
