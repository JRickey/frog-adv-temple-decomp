# sub_08005D10 — deferred analysis

Entity-pool animation-advance loop at 0x08005d10..0x08005ed8 (456 bytes,
asm slice asm/disasm_0x08005d10.s, dest src/game/sub_08005d10.c).

Two independent passes (Sonnet, then Opus escalation) have reached the SAME
plateau (byte_diff 261 / diff_count 48 under old_agbcc + `-fno-gcse`). The
logic, control flow, and struct layout are FULLY CORRECT and verified. The

divergences that no clean-C shape reproduces under EITHER bundled agbcc.

## What it does (confirmed)

`void sub_08005D10(s32 slot, s32 endSlot)` — iterates `gEntities[slot..endSlot]`
(stride 0x38) advancing each entity's animation frame. Cousin (matches):
`sub_08020F3C` (src/engine/sub_08020f3c.c) — same subsystem, but NOT a loop, so
it sidesteps the loop-giv divergences below.

- Gate: `s64 ret = sub_08006830(&gIwram_6110, slot, endSlot); if (ret==0) return;`
  Declare the callee `extern s32 sub_08006830(...)` (NOT long long); the
  s32->s64 widen-on-assign emits the baserom `asr r1,r0,#0x1f; orr r0,r0,r1`.
- `now = gGameStuff._unk00;` (held in sl naturally).
- 4 loop induction vars, ALL reproduced correctly by the best-effort C:
  r8=offset (+=0x38), r5=e ptr (+=0x38), [sp,#20]=field28 ptr (+=0x38),
  r9=i (+=1). Per-branch: status-bit-2 set / (now-stamp)<delay / else-advance.
  See the prior note's field map and the best-effort C below — all accurate.

## Drift (best: byte_diff 261, diff_count 48; old_agbcc + `-fno-gcse`)

There are exactly THREE residual divergences. NEW this pass: the prior note's
"stamp giv" theory was WRONG — the real function DOES reuse the offset giv (r8)
for the stamp (`ldr =sym; add r0,r8; str`), so there is NO spurious 5th giv.
The three real issues all reduce to TWO agbcc behaviors: the `SYMBOL+CONST`
fold, and a couple of local-alloc coloring picks.

1. **`SYMBOL + 0x20` constant-fold — the ONLY size-affecting diff.**
   Baserom stamp store (3 sites): `ldr r0,[=gEntities_03003720]` (BARE 0x3720)
   `; adds r0,#0x20 ; add r0,r8 ; str sl,[r0]`. Both bundled agbcc binaries
   (old_agbcc AND agbcc) ALWAYS fold `gEntities_03003720 + 0x20` into the pool
   literal `0x03003740`, dropping the `adds #0x20` (so our output is 1 insn
   SHORTER per site → 3 deleted `adds #0x20` + a different pool word → the
   BL-offset / branch-target cascade that inflates byte_diff to 261).
   Verified in isolation (private agbcc probes) that NO clean-C form yields
   `ldr=sym(bare); adds#0x20; add reg`:
     * `sym + off + 0x20`, `sym + (off+0x20)`, `(u32)sym + 0x20 + off`,
       `p = sym+0x20; p+off`  → ALL fold `sym+0x20` into the pool.
     * `u32 a = off + 0x20; sym + a`  → keeps sym BARE, but emits
       `add #0x20 (to off, runtime); ldr=sym; add` — WRONG ORDER + an extra
       `mov` when off lives in r8.
     * `p = sym; p + 0x20 + off`  → keeps sym BARE but uses STORE DISPLACEMENT
       `str [r1,#0x20]` (no explicit `adds #0x20`), also 1 insn short.
     * a dedicated `stampOff`/`stamp` pointer giv  → keeps sym BARE but adds a
       real 5th giv (`+=0x38` in the tail), which baserom does NOT have.
   i.e. agbcc either folds the constant into the symbol, or makes it a store
   displacement, or reorders to `(off+const)+sym` — it never materialises the
   full address as `ldr=sym; adds#const; add roff`. This is a genuine
   instruction-selection gap, not a source-shape problem.

2. **Preheader giv-init ordering — PURE COLORING (same insn count, 11 vs 11).**
   Baserom: `…offset; mov r8,r0; adds r0,#0x28; ldr r1,=base; adds r0,r0,r1
   (field28); str [sp,#20]; adds r5,r1,#0; add r5,r8 (e)`. agbcc:
   `…offset; mov r8,r0; ldr r0,=base; add r0,r0,r8 (e FIRST); add r1,r0,#0;
   add r1,#0x28 (field28=e+0x28); str [sp,#20]; add r5,r0,#0 (e)`. Same ROOT as
   #1: field28's giv add_val `base+0x28` folds, so agbcc computes `base+offset`
   (=e) first and derives field28=e+0x28, while baserom keeps base bare in r1
   and computes field28=`(offset+0x28)+base`, e=`base+offset` independently.
   No source association ((offset+0x28)+base, base+(offset+0x28), e=field28-0x28,
   field28-first decl, (u32) casts) flips it — they all either reassociate back
   to e-first or add casts that worsen the cascade (335–388).

3. **AnimDesc table-ptr load coloring — PURE COLORING.** Baserom
   `ldr r1,[r1,#0]; adds r4,r1,r0` (ptr in transient r1, desc→r4). agbcc
   `ldr r4,[r1,#0]; adds r4,r4,r0` (ptr loaded straight into r4). local-alloc
   picks r4; operand-order swaps and a `tablePtr` temp split do NOT change it
   (323) — both compilers, downstream of #2's register pressure.

    u8 *field28;
    u8 *base;
    u32 offset;
    u32 now;
