## KEY BREAKTHROUGH — defeats the tail-merge (use this next time)

The baserom keeps DUPLICATED branch bodies un-merged (block1: case0,case1 both
`value=5`; block2: case2,case1 both `sub_08000764(5)+3`). agbcc -O2 ALWAYS
tail-merges identical branch bodies via the final `jump_optimize(JUMP_CROSS_JUMP)`
(toplev.c:4099, unconditional at optimize>0; no flag isolates it). docs/codegen-
notes "64-bit OR-store tail-merging" called this unmatchable — but for THIS
const/call-body shape it IS escapable:

  - `asm("" : "+r"(value));` after EACH duplicate assignment blocks cross-jump
    WITHOUT a stack spill (a plain `volatile` un-merges but adds str/ldr [sp]
    round-trips the baserom lacks). RTL-verified: `.greg` keeps branches
    separate, the final cross-jump merges them; the fence prevents that merge.
  - `register s32 value asm("r0")` then pins value to r0 (baserom uses r0).
  With both: **block 1 matches BYTE-FOR-BYTE** (movs r0,#5 / movs r0,#5 /
  movs r0,#6 / strh r0,[r4,#0xc], even the mid-fn pool word at the right spot)
  and **block 2 un-merges with value in r0** (cmp#2;bne;movs r0,#5;bl;adds r0,#3;
  b / cmp#1;bne;movs r0,#5;bl;adds r0,#3;b / movs r0,#3;bl).

## Drift — the residual 148

Two coupled remaining clusters (entity-write tail, asm offset 0x44 + 0x52..0x9a):

1. **gateByte 2nd read**: baserom `adds r4,#43; ldrb r0,[r4]` (advances r4 in
   place; `control` dead after). agbcc keeps r4 and computes via
   `adds r0,r4,#0; adds r0,#43; ldrb r0,[r0]`. Coloring choice.
2. **block 2 per-branch base load**: baserom emits `ldr r1,=0x03003720` INSIDE
   each rand branch (two DISTINCT pool literals at 0x2a594/0x2a5a8), so r1=base
   reaches the join already loaded; the shared join then `ldr r2,=0x6aa;
   adds r1,r1,r2; strb r0,[r1]`. agbcc instead defers ONE base load to the join.
   Every tried way to put `entities=(u8*)base` per-branch (before rand / after
   rand / between rand and +3 / with a 2nd fence on entities / pinned r1) either
   regressed (164/180/184) or didn't move the load into the branch.
3. **entity-write coloring**: with the base load deferred, agbcc holds base in
   r2 + computes 0x6b0/0x698 via `movs#0xd6/0xd3; lsls#3; adds` (GOOD, matches
   baserom's offset materialization) but colors r2 vs baserom's r1, and reuses
   `subs r3,#16` for 0x69a where baserom loads a separate 0x69a pool literal.
   This is downstream of (2): if the per-branch base load lands in r1, the join
   coloring should fall into place.
