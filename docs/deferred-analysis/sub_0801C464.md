# Deferred analysis: sub_0801C464

Range: 0x0801c464..0x0801c4f8 (148 bytes, Thumb)

## Function summary

Fills two 3x3 tile blocks in VRAM (screenblock 31 at 0x0600f800) with
sequential tile indices. Block 1 starts at row 16 col 1 (offset 0x402) with
tile base 0xB100; block 2 at row 16 col 20 (offset 0x428) with tile base
0xA109. No function calls -- pure register arithmetic loops.

## Status

ATTEMPT_MATCH (classifier). Pure loop arithmetic -- no BL calls, no high-reg
cross-BL issue. Reached **byte_diff 21 / diff_count 12** with the C below.

## Drift

**Best byte_diff: 21, diff_count: 12**

Two systematic differences remain:

### 1. Both loops: row*64 register choice

Target: `lsls r1, r3, #6` (row*64 -> r1), then `lsls r0, r3, #1` (row*2 ->
r0) **before** either is consumed.

Built (new agbcc AND old_agbcc): `lsls r0, r3, #6` (row*64 -> r0), used
immediately in `adds r5, r0, r7`, THEN `lsls r0, r3, #1` reusing r0.

Root cause: agbcc computes `vramRow = row*64 + rowOff` sequentially, putting
row*64 in r0 (the first free register) and immediately using it. For row*64
to go to r1, r0 must be occupied at that point.

Approaches tried to force r0 occupation:
- col=0 uses r2 (not r0), so doesn't occupy r0
- `u8 row2 = row*2` first (explicit): puts row*2 in r0 first, then row*64
  -> r1 SECOND. BUT then asm order is `lsls r0,r3,#1; lsls r1,r3,#6` which
  is ALSO wrong (target has row*64 in r1 and row*2 in r0, i.e., target emits
  lsls r1 BEFORE lsls r0 in asm order).
- `u32 row64; u32 row2`: explicit intermediates force both shifts before use,
  but with WRONG register assignments. When row64 declared first -> r0,
  row2 -> r1. When row2 declared first -> r1 (wrong), row64 -> r0 (wrong).
  The permuter gets closer (min score 700 from base 1015) but no score 0.

The target's `lsls r1,r3,#6` before `lsls r0,r3,#1` (interleaved, with r1
for row*64) suggests agbcc evaluated row*2 FIRST (allocating r0) and then
row*64 (needing r1 since r0 busy), but EMITTED them with row*64 first in
the instruction stream. This is an instruction-scheduling vs allocation
ordering mismatch that cannot be expressed naturally in C.

### 2. Loop 2 structural asymmetry

Target outer loop 2 body:
```
movs r2, #0       ; col = 0
lsls r1, r3, #6  ; row*64 -> r1
lsls r0, r3, #1  ; row*2 -> r0
adds r5, r3, #1  ; r5 = row + 1  <- EARLY counter backup
adds r4, r1, r7  ; r4 = vramRow  (in r4, not r5 like loop1!)
adds r0, r0, r3  ; r0 = row*3
mov r1, r9        ; r1 = tileBase2
adds r3, r1, r0  ; r3 = tileBase2+row*3  <- OVERWRITES row counter!
```
Then inner loop uses r4 (vramRow) and r3 (tileRow). Loop tail recovers r3
from r5 via `lsls r0, r5, #24; lsrs r3, r0, #24`.

This requires: (a) nextRow=row+1 saved BEFORE vramRow is in r4 (not r5),
and (b) tileRow overwrites r3 (row) without truncation. If row is u8,
`row = tileBase2 + row*3` truncates. If row is u32, the allocation shifts.

## Levers tried (both sessions)

- `register u32 vramBase asm("r6")` -- fixes r6/r7 swap for VRAM vs rowOff
- `register u32 ipBase asm("ip")` -- enables ip-retained-across-loops
- `asm volatile("" : "+r"(ipBase))` -- prevents ip+0x28 hoisting into loop1
- old_agbcc per-TU override -- produces IDENTICAL output to new agbcc
- Permuter 2000 iters (-j4, 45s): base score 1015, best 855 (session 1)
- Permuter 45s run (-j4): base score 1015, min 700, no improvement saved (session 2)
- `register u8 col asm("r2")` pin -- breaks truncation, worse result
- `register u8 row asm("r3")` pin -- adds u8 zero-extension, worse
- `register u32 vramRow asm("r5")` / `asm("r4")` -- pushes rowOff to sl
- nextRow in loop 2 at various positions (before/after vramRow) -- uses sl
- Explicit `u32 row64; u32 row2` intermediates in inner scope -- both shifts
  computed before use (good!) but wrong register assignments, byte_diff 30-32
- `tileRow = row*2` first to occupy r0 then `vramRow = row*64+rowOff` -- row
  ends up in r4 instead of r3, worse

## Best-effort C

```c
#include "macros.h"
#include "types.h"

void sub_0801C464(void)
{
    register u32 tileBase1 asm("r8") = (u32)0xb1 << 8;
    register u32 tileBase2 asm("r9") = 0x0000a109;
    register u32 ipBase asm("ip");
    register u32 vramBase asm("r6");
    u8 row;
    u8 col;
    u32 rowOff;
    u32 vramRow;
    u32 tileRow;

    row = 0;
    ipBase = (u32)0x80 << 3;
    rowOff = ipBase + 2;
    vramBase = 0x0600f800;
    do {
        col = 0;
        vramRow = (u32)row * 64 + rowOff;
        tileRow = tileBase1 + (u32)row * 3;
        do {
            *(vu16 *)((u32)col * 2 + vramRow + vramBase) = (u16)(tileRow + col);
            col++;
        } while (col <= 2);
        row++;
    } while (row <= 2);

    row = 0;
    asm volatile("" : "+r"(ipBase));
    rowOff = ipBase + 0x28;
    vramBase = 0x0600f800;
    do {
        col = 0;
        vramRow = (u32)row * 64 + rowOff;
        tileRow = tileBase2 + (u32)row * 3;
        do {
            *(vu16 *)((u32)col * 2 + vramRow + vramBase) = (u16)(tileRow + col);
            col++;
        } while (col <= 2);
        row++;
    } while (row <= 2);
}
```

This matches all structural elements except:
- In both loops: `lsls r0, r3, #6` instead of `lsls r1, r3, #6` for row*64
- In loop2: symmetric structure vs asymmetric baserom loop2
  where r5=nextRow, r4=vramRow, r3=tileRow (row overwritten)

Pool layout matches (0x0000a109 and 0x0600f800), prologue/epilogue correct,
register savings correct (r8, r9 only), size correct (148 bytes), ip usage
correct. This is a near-match blocked by instruction scheduling.
