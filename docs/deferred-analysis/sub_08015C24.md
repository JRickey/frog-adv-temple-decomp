# Deferred analysis: sub_08015C24

Range: [0x08015c24, 0x08015cbc) — 152 bytes, Thumb.

## Summary

EWRAM tilemap blit — copies a rows×cols block of u16 tiles from a caller-supplied
src pointer into one of three EWRAM buffers (0x02000000/0x02010000/0x02020000)
at (dstX, dstY) scaled by the scene tile stride. The stride is
`SceneScrollState.tileWidth` at IWRAM 0x030060A0 offset 26 (offset 26 = `tileWidth`).
Signature: `sub_08015C24(u8 bank, u16 dstX, u16 dstY, u8 cols, u8 rows, const u16 *src)`
  bank=r0, dstX=r1, dstY=r2, cols=r3, rows=[sp+20]→r4, src=[sp+24]→r6.
Pure leaf function (no callees). classify_unmatchable: **ATTEMPT_MATCH** (NOT
STRONG_UNMATCHABLE — NAKED is NOT appropriate; this is a coloring local minimum).

## Drift — Round 5 (Opus): NEW BEST byte_diff 16 (was 19) — clean readable C + ONE pin

The Round-4 documented best was byte_diff 19 (clean, no pins). Round 5 reached **byte_diff
16 / diff_count 14** with the readable C below (ONE `register asm("r2")` pin on the state
pointer). All 14 residual diffs are ONE coupled local-vs-global register-coloring cascade.

### What the Round-5 base FIXED vs the old 19-version (do NOT regress these)

1. **No `default: goto outer`.** The switch has NO default — all paths (incl. the
   implicit default) fall through to the multiply, matching the baserom where every
   case converges at 0x15c66. (The old 19-version's `default: goto outer` produced 2
   spurious `b.n` diffs at 0x28/0x2e. Removing it alone regressed coloring to 63 unless
   combined with the state-pin + multiply-reorder below.)
2. **state=r2 pin + sx/sy pre-extract → stride lands in r7 (not r2).** Pre-extracting
   `sx=(s16)dstX; sy=(s16)dstY;` BEFORE the state load vacates the dstY param reg (r2),
   so pinning `state asm("r2")` does NOT spill. With state held in r2, the stride load
   `ldrh r7,[r2,#26]` goes to r7 (the baserom's choice) instead of reusing r2. This also
   yields the preheader copy `adds r7,r2,#0` (loopState=state) — the old 19-version
   instead RELOADED the literal (`ldr r7,[pc]`).
3. **Multiply reorder `sy*stride + sx` (NOT `sx + sy*stride`).** Evaluating the product
   first makes agbcc keep sx in r1 and put the product in r0 (the accumulator), matching
   the baserom's `muls r0,r7; adds r0,r1,r0` operand assignment.
4. **`loopState = state` assigned INSIDE the `if (row<rows)` block** (not before it), so
   the copy `adds r7,r2,#0` lands at 0x5c (after the `cmp r0,r4; bcs`) exactly like the
   baserom, not unconditionally before it.

### The 14 residual diffs — ALL one coupled coloring tie (the wall)

```
final diff (byte_diff 16):
  0x42-0x44  sx narrowing scratch:  target lsls r0,r1,#16; asrs r1,r0,#16  (uses r0 scratch, result r1)
                                     built  lsls r1,r1,#16; asrs r1,r1,#16  (in-place, single reg)
  0x48-0x4a  state-load position shifted by one insn (cosmetic, follows from the scratch choice)
  0x50       adds r0,r1,r0  vs  adds r0,r0,r1   (commutative product+sx operand order)
  0x5e-0x80  THE BIG ONE: col↔nextRow = r2↔r1 swap (8 diffs)
             target: col=r2, nextRow=r1   built: col=r1, nextRow=r2
```

### Root cause — CONFIRMED via instrumented old_agbcc (Round 5)

Built a PRIVATE debug `old_agbcc` (probed `qty_phys_reg` assignment in
`gcc/local-alloc.c`; sandbox in /tmp, deleted after — NEVER touched the shared symlink).
Ground truth:

- **`col` is a LOCAL-alloc quantity** (live only in the inner-loop BB). **`nextRow`
  (row+1, saved across the inner loop because the inner loop clobbers r0=row) is a
  GLOBAL-alloc quantity** (spans multiple BBs).
- `thumb.h` defines NO `REG_ALLOC_ORDER`, so `find_free_reg` (local-alloc.c ~L1947)
  picks the **lowest-numbered free reg** in ascending order. local-alloc runs BEFORE
  global-alloc.
- At col's allocation (local pass), both r1 and r2 are free in the inner BB → col grabs
  **r1** (lowest). nextRow (global pass, later) then avoids r1 → gets r2. This is the
  built coloring.
- The baserom wants col=r2 (reusing the r2 just vacated by the `adds r7,r2,#0` copy of
  state→loopState) and nextRow=r1. i.e. the baserom gives col the JUST-FREED r2 rather
  than the lowest-free r1 — a "reuse-recently-freed" preference our local-alloc does not
  reproduce for col (it DOES apply it to nextRow, the global quantity).
- QTY_CMP_PRI (`log2(n_refs)*n_refs*size/(death-birth)`) makes col (high inner-loop refs,
  short life) the higher-priority quantity → allocated first → lowest free reg = r1.

### Levers tried in Round 5 — ALL FAILED to flip col r1→r2 without a worse cost

- `col asm("r2")` pin: gets col=r2 BUT agbcc then const-folds `col=0` into the inner
  guard (`cmp r3,#0; beq` instead of baserom `movs r2,#0; cmp r2,r3; bcs`). The fold is
  INHERENT to the `register` keyword's value-tracking; net byte_diff 17 (neutral). Could
  not suppress with -fno-cse-follow-jumps / -fno-cse-skip-blocks / -fno-rerun-cse-after-loop
  / -fno-expensive-optimizations / -fno-thread-jumps (all stayed 17).
- `nextRow asm("r1")` pin: fixes col→r2 BUT coalesces `row` into r1 too (via
  `row=(u8)nextRow`), so row leaves r0 → 4 new diffs. Adding `row asm("r0")` on top
  SPILLS (row=r0 collides with bank/dst at entry).
- Swap statement order (`nextRow=row+1` before `col=0`): nextRow grabs the freed r2,
  col STILL gets r1 → 18 (worse). `row++` vs explicit nextRow: identical 16 (agbcc
  generates the same save internally).
- Use `col` instead of `cols` post-loop (extend col life to lower its priority): still
  col=r1, plus the `subs` now reads col's reg → 16, no net help.
- Flag battery (all stayed 16): -fno-strength-reduce, -fno-schedule-insns(,2),
  -fno-force-mem, -fforce-addr, -fno-omit-frame-pointer, -fno-peephole, -fcaller-saves,
  -fno-defer-pop, -fno-gcse. Compiler swap old_agbcc→agbcc(new): no change (16).
- Permuter (CORRECT base.c via project pipeline, base score 125 ≈ matches diff_count;
  5 min, 7500+ iters, -j4 --stop-on-zero --better-only): best 115, ZERO real improvement.
  Confirms a sharp coloring minimum the permuter cannot escape by reordering.

### Key insight for the NEXT attempt (the ONLY job left)

Flip col from r1 to r2 in the inner loop WITHOUT the const-fold the pin causes. The
mechanism wanted: col must reuse the r2 just freed by the `adds r7,r2,#0` copy, i.e.
local-alloc must prefer the recently-freed reg for col over the lowest-free r1. Ideas
NOT yet tried:
  (a) Make r1 UNAVAILABLE during col's life by some natural means so col falls to r2
      WITHOUT a pin (no const-fold). r1 holds sx during the multiply but sx dies before
      the loop; need something else live in r1 across the inner BB.
  (b) Instrument `find_free_reg`'s `used` set + the per-qty allocation ORDER for col vs
      nextRow specifically (Round 5 probed final assignment, not the `used` mask at col's
      birth). Confirm whether nextRow's GLOBAL r2 is visible to col's LOCAL pass — if so,
      reshape so nextRow's global quantity claims r1 first.
  (c) Try to suppress the col-pin const-fold via a source form where col's init is not
      provably 0 at the guard (e.g. the inner loop's first iteration is peeled, or the
      guard reads a value laundered through a non-const expression).
This is a legitimate firm-defer for codex / a deeper local+global allocator trace.

## Best-effort C (byte_diff 16 / diff_count 14 — the Round-5 base to build on)

```c
#include "macros.h"
#include "types.h"
#include "iwram.h"
#include "gba/dma.h"

struct SceneScrollState_15C24 {
    u8 _pad00[26];
    u16 tileWidth;
};

void sub_08015C24(u8 bank, u16 dstX, u16 dstY, u8 cols, u8 rows, const u16 *src)
{
    u16 *dst;
    struct SceneScrollState_15C24 *state;
    s32 sx, sy;
    u8 row;

    switch (bank) {
    case 0:
        dst = (u16 *)0x02000000;
        break;
    case 1:
        dst = (u16 *)0x02010000;
        break;
    case 2:
        dst = (u16 *)0x02020000;
        break;
    }

    sx = (s16)dstX;
    sy = (s16)dstY;
    {
        register struct SceneScrollState_15C24 *st asm("r2") = (void *)0x030060A0;
        dst += sy * st->tileWidth + sx;
        state = st;
    }

    row = 0;
    if (row < rows) {
        struct SceneScrollState_15C24 *loopState = state;
        do {
            u8 col = 0;
            if (col < cols) {
                do {
                    *dst++ = *src++;
                    col++;
                } while (col < cols);
            }
            dst += loopState->tileWidth - cols;
            row++;
        } while (row < rows);
    }
}
```

byte_diff 16 / diff_count 14. The whole residual is col=r1 (want r2) + the coupled
nextRow=r2 (want r1) + the sx-narrowing-scratch / adds-operand-order tail that follows
from it. Start from THIS base; the ONLY job is flipping col r1→r2 cleanly (see "Key
insight").

## Drift — Round 6 (Opus): re-derived from scratch, same floor (byte_diff 16)

Re-derived the C cold (not tweaking Round 5) and independently landed the SAME byte_diff
16 / diff_count 14 floor with the same residual. Confirmed the wall is real, plus two

### NEW FINDING 1 — Round-5's flag battery was partly invalidated by a tooling caching bug

`compile_and_view_assembly.py` runs `make`, which only rebuilds the TU's `.s`/`.o` when the
**`.c`** is newer — it does NOT rebuild when only a per-TU `Makefile` `CFLAGS`/`CC` line
changes. So a flag test that doesn't also touch the `.c` reads the PREVIOUS build and reports
a STALE byte_diff (looked like "flag had no effect → still 16"). Any Round-5 flag conclusion
that stayed exactly 16 is suspect for this reason.

Round-6 re-ran the whole battery with a forced `rm -f src/engine/sub_08015c24.s
src/engine/sub_08015c24.o` before each diff. Honest results (clean base, state-pin only):
  - `-fno-strength-reduce`: 16 (no change, genuine)
  - `-fno-gcse` / `-fcaller-saves` / `-fno-cse-follow-jumps` / `-frerun-loop-opt`: **38** (worse)
  - `-fno-schedule-insns(,2)`: build error (drop)
  - `-fno-peephole`/`-fno-defer-pop`/`-fforce-mem`/`-fforce-addr`/`-fno-function-cse`/`-fno-omit-frame-pointer`: 16
  - compiler swap old_agbcc→agbcc(new): **84** (much worse — `mov ip,r2` spill returns)
None flip col r1→r2. So the flag surface is genuinely exhausted (now verified, not stale).

### NEW FINDING 2 — `register`-keyword pins on the loop COUNTERS are categorically off the table

The baserom does NOT value-track the counter's zero-init into its guard:
`movs rN,#0; cmp rN,rBound; bcs` (materialize 0, then compare). agbcc with a `register`
declaration DOES value-track the constant 0, folding `if (v < bound)` (v==0) into
`cmp bound,#0; beq`. Confirmed on all three counters (forced rebuild each):
  - `register u8 col asm("r2")`: col→r2 (8 col diffs vanish) BUT inner guard folds
    `cmp r3,#0; beq` → net **17**. UNSUPPRESSIBLE by any CSE flag
    (-fno-cse-follow-jumps / -fno-cse-skip-blocks / -fno-rerun-cse-after-loop /
    -fno-expensive-optimizations / -fno-thread-jumps all stay 17). The fold is at RTL
    expand from the `register` keyword's constant value-tracking, NOT in a CSE pass.
  - `register u8 row asm("r0")` (+ nextRow asm("r1")): col is fixed (the 0x5e-0x62 col
    diffs vanish!) BUT the OUTER guard now folds `cmp r4,#0; beq` → net **30**.
  - `register u8 nextRow asm("r1")` alone: **18** — `row = nextRow` copy-coalesces row
    into r1 (`movs r1,#0; cmp r1,r4`), exactly the Round-5 observation.
  - An `asm("" : "+r"(col))` fence to launder col's 0 past the fold: **70** (the fence
    wrecks the inner-loop narrow placement). Dead end.

Conclusion: because the ONLY pure-C mechanism to force a specific register is the
`register` keyword, and that keyword ALWAYS triggers the zero-init fold on a counter
whose guard tests `counter < bound`, **col/row/nextRow cannot be pinned without paying a
fold that costs more than the coloring win.** The pins are not a path.

### Allocator root cause — re-confirmed against the THUMB compiler source (gcc/, not gcc_arm/)

The matching compiler is built from `tools/agbcc-src/gcc/` (`-DOLD_COMPILER` = old_agbcc).
`gcc/thumb.h` defines NO `REG_ALLOC_ORDER`, so both `local-alloc.c::find_free_reg` and
`global.c::find_reg` scan hard regs **ascending (lowest-free wins)**. col is a LOCAL-alloc
quantity (inner-loop BB only) → allocated in local-alloc, which runs BEFORE global-alloc →
grabs the lowest free reg = **r1**. nextRow spans the inner loop (set before, read after) →
crosses BBs → GLOBAL → allocated later → conflicts with col's r1 → gets **r2**. The baserom
is the mirror image (nextRow=r1, col=r2), which requires nextRow to be allocated FIRST.
That needs either (a) nextRow LOCAL — impossible, it provably crosses the inner-loop BBs —
or (b) col GLOBAL — would require reading col after the inner loop, but the post-loop math
uses the PARAM `cols` (not col), and substituting col breaks the cols==0 case
(`dst += stride - cols` must still subtract cols when the inner loop is skipped). No C
shape reconciles this.

### What is genuinely left to try (for codex / an allocator-level attempt)

1. Instrument `gcc/local-alloc.c::find_free_reg` to print the `used` mask + per-qty
   allocation ORDER at COL's birth specifically (Round 5 probed final assignment in
   gcc_arm/, the WRONG tree — the Thumb compiler is gcc/). Confirm whether nextRow's
   eventual global r2 is in any way visible to col's local pass, and whether forcing
   nextRow to be processed in local-alloc (some no_conflict / combine note) is reachable.
2. A non-`register` way to occupy r1 across col's inner-loop life so `find_free_reg`'s
   `used` mask excludes r1 → col falls to r2 WITHOUT any fold. The blocker: every value
   naturally live there (dst r5, src r6, cols r3, loopState r7) is already off r1, and
   the only thing the baserom keeps in r1 (nextRow) is global/allocated-after. Need a
   value that is (i) live across the inner loop, (ii) local, (iii) higher priority than
   col, (iv) class-compatible with r1 — and emits no extra instruction. Not found.

This remains a legitimate firm-defer (next_tier=codex / allocator trace). The C floor
below is byte_diff 16; it is structurally correct and matches everything except the one
coupled col↔nextRow coloring tie and the tail that follows from it.
