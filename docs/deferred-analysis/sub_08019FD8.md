# sub_08019FD8 — deferred analysis

Per-room screen reset (engine cluster, src/engine/sub_08019e6c.c slice).
Verdict from `classify_unmatchable.py`: **ATTEMPT_MATCH** (no structural
impossibility; `push {r4, r5, lr}` prologue, no `mov pc`, no libgcc-only BL set).

The C is **structurally complete and correct** — same size (204 bytes), same
instruction *count*, same control flow, same pool constants. The only divergence
is a **sharp constant-0 register-coloring local minimum** (the exact class the
CLAUDE.md sub_08017364 caveat warns about). Best achieved: **byte_diff 66,
diff_count 14**, and EVERY one of the 14 cells is either the placement of a
second `movs rN,#0` or an r4/r5 swap or a knock-on PC-offset shift from that one
extra-early `movs`.

## Behaviour (what the function does)

1. `sub_0800A05C()` — OBJ/OAM/entity software reset.
2. DMA3 fixed-source fill of BG3 screen block: src=&zero(stack u16), dst=0x06000000,
   cnt=`DMA_ENABLE|DMA_SRC_FIXED|0x8000`. `REG_BG3CNT = 0x1F08`.
3. Blank window regs via a walking u16* from `&REG_WIN0H`: WIN0H=0, +4 WIN0V=0,
   +4 WININ=0, +2 WINOUT=0 (the `*win=0;win+=2/1` walk reproduces the
   `strh; adds r0,#4/#2` chain exactly — DO keep literal `0`, NOT the `zero`
   variable; `*win = zero` reloads from the stack slot and breaks the match).
4. `REG_DISPCNT &= ~DISPCNT_WIN0_ON; REG_DISPCNT &= ~DISPCNT_WIN1_ON;` (0xdfff, 0xbfff).
5. `gIwram_3550._data[6] = 0; [7] = 0;`
6. DMA3 stream from the 24-byte ROM table at 0x080C1254 (+4), indexed by
   `gIwram_34B0._data`: src=`*(idx*24 + tableBase+4)`, dst=0x06008000,
   cnt=`DMA_ENABLE|0x2000`. Uses the same `asm volatile("" : "+r"(tableBase))`
   opaque-base idiom as the already-matching sibling `sub_08019EF0` in this file
   (keeps the +4 a runtime `adds`, not a folded pool constant) — that part matches.
7. `gIwram_34C0.cursor = 0; .delay = 0; .holdFlag = 0;`
8. `gIwram_6110.inputFlags ^= 8;`
9. `sub_08020BAC(); sub_08020B88(15);`

## Drift

best byte_diff = **66**, diff_count = **14**, size = 204 (matches).

The whole diff reduces to ONE register-allocation decision: how agbcc splits the
single CSE'd constant-`0` value-number into its two callee-saved registers (r4, r5)
across the two DMA blocks.

- **Target webs:** r4 = {`zero`-store rhs, the 4 window writes, `cursor`, `delay`};
  r5 = {`gIwram_3550[6]`, `gIwram_3550[7]`, `holdFlag`} and `movs r5,#0` is emitted
  **late**, right before the gIwram_3550 stores (+0x4a).
- **Our webs:** r4 = {`zero`-store, window, `gIwram_3550`, `holdFlag`};
  r5 = {`cursor`, `delay`} and BOTH `movs` are hoisted to the top (+0x08), which
  is the source of the +4 PC-offset knock-ons on every subsequent pool `ldr`.

i.e. the question is purely *which zero-pair shares the early/wide register with
the window writes*: target pairs **cursor+delay** with the window (r4) and isolates
**gIwram_3550+holdFlag** as the late r5; agbcc's coloring instead pairs
**gIwram_3550+holdFlag** with the window (r4) and isolates cursor/delay (r5).
This is decided in `global.c` graph-coloring (ordered by spill cost), downstream of
`local-alloc.c update_equiv_regs` constant-equivalence — agbcc CSE-merges ALL `0`
constants into one value-number regardless of how the C names them, so no
source-level renaming/splitting reaches the decision.

### Levers tried (none reached 0)

- **All-literal `0` everywhere** → 66 (baseline).
- **Named zero locals** (`u16 zero` + `u32 zero2` for gIwram_3550/holdFlag; or
  `w0` for window+cursor+delay + `z5` for gIwram_3550/holdFlag) → 66 (agbcc CSEs
  them all into one value-number; naming is invisible to the allocator).
- **Reorder gIwram_34C0 stores** (holdFlag first) → 68. **Move gIwram_3550 after
  DMA#2** → 111 (changes physical order; asm has gIwram_3550 *before* DMA#2).
- **Pointer-anchor for gIwram_3550** (`u16 *p = gIwram_3550._data`) → 66.
- **`*win = <var>`** (reuse a zero variable for the window walk) → reloads `zero`
  from stack (`mov r0,sp; ldrh`), 166. DO NOT use a variable for the window writes.
- **register pins**: `register u32 zero2 asm("r5")` → 168 (forces the 0x1F08 BG3CNT
  temp and/or the 0x040000D4 DMA base out of their registers — the pin cascades
  because r5 is needed transiently by the BG3CNT `ldr`/`adds` before the late zero).
  `register int w0 asm("r4") + z5 asm("r5")` (with `zero = w0`) → 168 (the `&zero`
  address-taken store won't reuse the pinned w0; `movs r1,#0; strh r1` appears).
  `&zero` being address-taken blocks pinning the wide zero.
- **opaque barrier** `asm volatile("" : "+r"(zero2))` on the gIwram_3550/holdFlag
  zero → 73 (reserves r5 from the top, displacing the DMA base from r3 to r4).
- **per-TU CFLAGS**: `-fno-gcse`, `-fforce-addr`, `-fno-cse-follow-jumps`,
  `-fno-cse-skip-blocks`, `-fno-expensive-optimizations`, `-fno-schedule-insns`,
  `-fno-schedule-insns2`, `-fcaller-saves` → all 66 (no effect; this is allocation,
  not a flag-gated optimization). The other 3 functions in the TU stay matched
  under each, so a per-TU flag is *available* if a future flag is found.
- **compiler swap** `CC = $(AGBCC_BIN)` (newer agbcc) → 66, others still 0.
- **decomp-permuter** (-j1, ~400 iters): base score **10870**, best **10670** —
  did NOT converge; statement-shuffle/var-scope mutations cannot reach this
  coloring (it never alters the constant-web split). Permuter is a dead end here.
