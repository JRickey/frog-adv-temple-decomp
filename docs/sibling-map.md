## Structural patterns worth recording

1. **Mode-handler class is dominant:** at least 4 of the next 5 targets
   (and likely most through sub_0800a4d0) are per-mode dispatchers
   conforming to the sub_08000EB8/sub_08001508/mode_15 template:
   - `push {r4..rN, lr}` + `sub sp, #FRAME`
   - `ldrb mode, [gGameStuff, #9]` (offset 9 = mode field)
   - check `mode == M || mode == 24`
   - `bl 0x20bc0` (per-frame VBlank tick)
   - `mov pc, jumpTable[localState]` — 9-entry computed jump
   - cases 0..8 fan out to sub_0800A104 input gate, sub_08009D9C scan,
     sub_080004C4 prober, sub_0800E6A8/10694/106B8 commit chain
   - epilogue: `add sp, #FRAME; pop {r4..rN}; pop {r0}; bx r0`
   All ship as NAKED + NON_MATCHING because `mov pc, r0` cannot be
   emitted from agbcc C. **Strong recommendation: scaffold a shared
   `mode_handler_template.h`-style header listing the shared extern
   prototypes** (sub_08020BC0, sub_0800A104, sub_08009D9C, sub_080004C4,
   sub_0800E6A8, sub_08010694, sub_080106B8, sub_080008DC) so each
   new mode handler's NON_MATCHING reference body is a 10-line diff.

2. **Mode parameter (offset 9) is universal:** every mode handler reads
   `gGameStuff.mode` via `ldrb rX, [..., #9]`. Already named in
   include/game.h; future commits should never see naked `[r1, #9]`.

3. **Tick-helper 0x08020BC0 is the gating BL.** Every mode handler
   starts its loop with this BL. Grep for it is the fastest way to
   classify an unknown target as mode-handler vs helper.

4. **sub_08001E24 is NOT a mode handler — it's the extracted probe**
   used by 0x03006110 / 0x030035E0 entity logic inside the mode
   handlers. Different sibling class entirely (helper, not dispatcher).
   Expect more of these as we go deeper.
